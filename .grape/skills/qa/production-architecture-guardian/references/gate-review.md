# Architecture Gate（review 模式）

> 用于 PR / 具体变更的门禁裁决。**三态结论语义与既有版本一致（向后兼容）**：`APPROVED` / `APPROVED WITH CONDITIONS` / `BLOCKED`，不新增第四态、不合并并列。
> 本文件三部分：§1 三态定义 → §2 17 检查面最低证据要求 → §3 BLOCKED 阻断条件清单 → §4 条件通过（APPROVED WITH CONDITIONS）模板摘要 → §5 裁决与命中的映射示例。

## §1 三态结论定义

| 裁决 | 触发条件 | 报告必附 |
|------|----------|----------|
| `APPROVED` | 0 项 `BLOCKED`、0 项 `Critical`；`Medium` 已在首屏清单列出待人工判断 | 四级统计 + Medium 清单 |
| `APPROVED WITH CONDITIONS` | 有可整改的 `Critical`，或仅 `Medium` 需整改；阻断清单未命中 | 逐条条件（条件内容/举证要求/解除条件/跟踪方式） |
| `BLOCKED` | 命中 §3 阻断条件清单任一条 | 具体技术缺陷（规则编号 + `file:line`/`commit sha` + 故障场景），或明确的证据缺失项与所需测量 |

裁决唯一：一次 review 只给一个裁决；`BLOCKED` 与 `APPROVED WITH CONDITIONS` 不得并列。

## §2 17 检查面与最低证据要求

> 前 16 面为既有检查面（口径沿用），第 17 面「数值证据」为本版新增检查面（对应硬规则 1 与规则 B2）。**「最低证据」是判定下限：达不到即该面为「证据不足」，按 §3 第 3 条处理，不得按通过放行。**

| # | 检查面 | 判定问题 | 最低证据要求 |
|---|--------|----------|--------------|
| 1 | 请求生命周期 | 请求从入口到落库/返回的完整路径是否闭合，是否有未覆盖分支 | 入口 → 主链路调用点 `file:line` 串联；分支清单 |
| 2 | 认证 | 身份来源与校验是否统一，是否有匿名可达的敏感路径 | 认证中间件/依赖注入点 `file:line` + 端点鉴权装饰清单 |
| 3 | 鉴权 | 授权判定是否绑定组织/角色/资源归属（含租户维度） | 授权调用点 `file:line` + 资源归属查询条件 |
| 4 | 校验 | 入参/边界/类型/长度校验是否在服务端完成 | 校验层 `file:line`（schema/validator）+ 越界用例 |
| 5 | 数据库访问与查询次数 | 是否有 N+1、循环查询、全表扫描、无界结果集 | SQL/ORM 调用 `file:line` + 执行计划或索引定义 |
| 6 | 事务 | 事务边界是否覆盖多写操作，异常路径是否回滚 | 事务开启/提交点 `file:line` + 异常分支 |
| 7 | 缓存 | 缓存键是否含租户维度，失效/穿透/雪崩是否有防护 | 缓存读写 `file:line` + 失效策略 |
| 8 | 异步任务 | 任务是否幂等、可重试、可观测，队列是否无界 | 任务定义 `file:line` + 重试/背压配置 |
| 9 | 外部 API | 超时/重试/熔断/降级是否齐备，失败是否可观测 | 客户端配置 `file:line` + 超时与重试来源 |
| 10 | 幂等 | 写操作是否有幂等键或去重，重放是否安全 | 幂等实现 `file:line` + 幂等键来源 |
| 11 | 失败模式 | 关键依赖失败的系统行为是否明确，阻断级失败模式有无缓解 | 故障场景表 + 缓解实现 `file:line` |
| 12 | 日志 | 关键路径是否有关键字段日志，外部调用与审计日志是否落 | 日志写入点 `file:line` + 字段清单 |
| 13 | 指标 | Metrics 是否接入且命名/标签规范，告警阈值是否有出处 | 指标定义 `file:line` + 阈值出处（对应 N4） |
| 14 | 安全 | 输入面/密钥/敏感数据/越权/注入面是否覆盖（含隐私加密） | 安全控制点 `file:line` + 加密实现（C1） |
| 15 | 部署影响 | 新增配置项/依赖/迁移顺序是否明确，是否可回退 | 配置定义 `file:line` + 部署步骤与回退路径 |
| 16 | 迁移影响 | 迁移脚本是否双向可回滚，是否有回滚演练证据 | 迁移脚本 `file:line` + 演练记录（G-3/N3） |
| 17 | 数值证据 | 所有新增数字是否有出处或已登记例外/待决策 | `magic_number_audit.py --json` 输出 `unbacked_numbers[]` 逐条结案 |

## §3 BLOCKED 阻断条件清单（命中任一条 → 裁决 `BLOCKED`）

| # | 阻断条件 | 判定口径 | 报告须给出 |
|---|----------|----------|-----------|
| 1 | 命中 BLOCKED 级规则的不符合项 | 规则 A5/A9/A10/A11/A12/A13/A14、B1/B3/B4、D1/D2 中任一条判「不符合」且证据成立 | 规则编号 + `file:line`/`commit sha` + 故障场景 |
| 2 | 阻断级失败模式无缓解方案 | 关键依赖失败会导致数据错误/不可用/数据泄露，且无超时/熔断/降级/隔离措施 | 失败路径 + 缺失的缓解手段 + 影响面 |
| 3 | 证据缺失、无法判定 | 关键检查面（§2 中任一面）达不到最低证据要求，无法判定通过 | 该面 + `INSUFFICIENT DATA TO VERIFY` + **缺哪种测量/文档** |

**口径澄清（防止两条规则互相抵消）**：

- 「无 `file:line` 证据不得判『不符合』」约束的是**指控**：没有证据就不能说代码不合规，此时该项落「证据不足」而非「不符合」。
- 「证据缺失无法判定」约束的是**放行**：关键面无法判定时 Gate 不得给 `APPROVED`/`APPROVED WITH CONDITIONS`，裁决为 `BLOCKED`，并在报告中说明缺失的是测量还是文档。
- 两者并存：**既不冤枉代码，也不放行无据变更。**

非阻断情形（不得据此判 `BLOCKED`）：风格偏好、命名口味、无证据的推测、可整改且不影响功能的 `Critical`（→ `APPROVED WITH CONDITIONS`）、纯 `Medium`/`Informational`（→ 首屏清单 + 人工判断）。

## §4 APPROVED WITH CONDITIONS 条件模板（摘要）

每条条件必须四段齐备，缺段即条件无效、裁决降为 `BLOCKED`：

| 字段 | 要求 | 反例（不成立） |
|------|------|----------------|
| 条件内容 | 要改什么（文件/接口/配置）+ 对应规则编号 | 「优化一下性能」 |
| 举证要求 | 改完后用什么证据证明（测试/压测/演练/代码位置） | 「改完告诉我」 |
| 解除条件 | 满足何种可观测状态即视为解除 | 「尽量」 |
| 跟踪方式 | 跟进载体（PR 评论/后续 commit sha/回归项编号） | 「后续关注」 |

完整可复制模板见 `templates/gate-decision.md` §2。

## §5 裁决映射示例

| 场景 | 检查面结论 | 裁决 |
|------|-----------|------|
| 新增接口无鉴权（A9 不符合，`api/x.py:42`） | 鉴权面不符合（BLOCKED 级规则） | `BLOCKED` |
| 新增表用自增主键（A12 不符合，`migrations/0007.sql:12`） | 迁移影响面不符合 | `BLOCKED` |
| 关键依赖无超时且无降级（阻断级失败模式无缓解） | 失败模式面不符合 | `BLOCKED` |
| 新增数字 7 处未举证且无法补测（数值证据面证据不足） | 数值证据面证据不足 | `BLOCKED`（条件：补测/登记白名单） |
| 有 1 项 `Critical` 可整改（A1 风格偏差，`api/y.py:88`） | 请求生命周期面条件通过 | `APPROVED WITH CONDITIONS` |
| 仅 2 项 `Medium`（A2 未开放 CLI、A7 分区缺说明） | 各面符合，Medium 进首屏 | `APPROVED` + Medium 清单 |
