# 架构规则基线（A/B/C/D 四类 23 条）

> **唯一权威**：Issue #3166 正文「架构守护规则3.1」（用户原文，2026-11-18）。逐条照录口径，不做扩写；原文未给出的细则一律不补写。
> 每条规则标注**结论级别**（唯一取值域：`BLOCKED` / `Critical` / `Medium` / `Informational`，定义见 §1）。
> **双向索引**：规则 → 承载检查项见 §5 表；检查项四段式（检查内容/判定标准/所需证据/结论级别）见 `references/audit-checklists.md`。
> 适用范围：针对「新增/变更」改动；存量遗留（既有基线）不溯及，报告中标注即可。

## §1 四级判定体系（与 Issue 正文一致）

| 级别 | 定义（原文口径） | 合入映射 |
|------|------------------|----------|
| `BLOCKED` | 必须遵循的规则，不符合会影响系统功能，不遵从不建议合入 PR | **不建议合入** |
| `Critical` | 关键规则，不符合会影响系统的持续维护，不遵从不建议合入 PR | 条件整改后可合入（条件未满足前不建议合入） |
| `Medium` | 中等影响规则，对系统架构未来发展有一般程度影响，不遵从人工判断是否合入 | **人工判断**（报告首屏列清单） |
| `Informational` | 提示类规则，不遵从不影响 PR 合入 | 记录备查 |

统计口径：`{N} BLOCKED / {N} Critical / {N} Medium / {N} Informational`。本基线 23 条的级别分布：**BLOCKED 12、Critical 7、Medium 4**（无 Informational 条目；Informational 用于检查项层面的提示性结论）。

## §3 代码架构约束（B1–B4，4 条）

| 规则 | 级别 | 原文口径 | 判定要点（证据形态） | 检查项 |
|------|------|----------|----------------------|--------|
| B1 | `BLOCKED` | 新增 sql 需要同时支持 sqlite 和 mysql 两种模式 | 无单边方言（仅 sqlite 的 `ON CONFLICT`、仅 mysql 的 `ON DUPLICATE KEY` 等） | G-6 |
| B2 | `Critical` | 代码不允许有魔鬼数字 | `scripts/magic_number_audit.py --json` 的 `unbacked_numbers[]` 逐条结案；无出处不得给数字 | H-4 |
| B3 | `BLOCKED` | 代码目录按照现有规划目录存放：`src/api` 放开放接口、`src/domains` 放业务领域、`src/kernel` 放公共能力；**kernel 不可以依赖 domains** | 新增文件落位 + kernel→domains import 检查 | A-3 |
| B4 | `BLOCKED` | 测试目录的测试对象和 `src` 目录结构对齐，测试用例放到对应目录下面 | 新增用例目录与 `src` 变更模块一一对应 | A-4 |

> 原文「代码架构约束」仅 4 条（B1–B4），无 B5；本基线不补写不存在的规则条目。

## §7 与两条硬规则的关系

- 数值证据门（`references/numerical-evidence-gate.md`）是 A3、A4、B2、N4、N5 及所有「数字类检查项」的统一举证口径；**无出处不得给数字**在任何模式下不得降级。
- 结论证据分级（`verified: *` / `measured` / `load-tested` / `plausible` / `INSUFFICIENT DATA TO VERIFY`）适用于本基线每一条规则的判定结论，禁止把 `plausible` 表述为已验证。
