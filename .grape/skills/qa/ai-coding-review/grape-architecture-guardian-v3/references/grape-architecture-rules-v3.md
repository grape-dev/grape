# Grape 架构规则包 v3（架构守护 3.0）

> **唯一权威**：Issue #2403 正文（24 条：A1-A14 设计、B1-B5 代码、C1-C3 可信、D1-D2 UI）。
> 本文件逐条照录原文口径；**原文无内容者（B5）占位标注「内容待补充」，禁止编造条款**。
> 2.0（`grape-architecture-guardian` 的 16 条、`production-architecture-guardian`）**不是**规则权威；2.0 的 7 Gate 仅保留为**审查维度**（§3）。
> **适用范围**：规则针对「新增/变更」改动；存量遗留（白名单/基线已存在）不溯及，报告中标注即可。

## §1 四级判定体系与合入映射

| 级别 | 定义（Issue #2403 原文口径） | 合入映射 |
|------|------------------------------|----------|
| **BLOCKED** | 必须遵循的规则，不符合会影响系统功能 | **不建议合入 PR** |
| **Critical** | 关键规则，不符合会影响系统的持续维护 | **APPROVED WITH CONDITIONS**：列出整改条件；条件未满足前不建议合入 |
| **Medium** | 中等影响规则，对系统架构未来发展有一般程度影响 | **人工判断**是否合入（报告首屏列清单，人工拍板） |
| **Informational** | 提示类规则，不符合不影响 PR 合入 | 不影响合入，记录备查 |

级别统计口径：`{N} BLOCKED / {N} Critical / {N} Medium / {N} Informational`。

> 口径统一：领域细则文件（`references/standards.md` 等沿用上游术语 Blocker/High/Low）映射到本规则包四级——`Blocker→BLOCKED`、`High→Critical`、`Low→Informational`。**报告、发现项与裁决一律只用四级**。

## §2 单条判定四态（每条规则必须落到其中一态）

- **符合**：给出验证方式（脚本输出 / file:line / 配置读取）。
- **不符合**：**必须**给出 `file:line` 或 `commit sha` 证据（见 §8 证据契约）。
- **不适用**：写明理由（本次变更未涉及该维度）。
- **证据不足**：标 `INSUFFICIENT DATA TO VERIFY`，并写清「缺哪种测量/文档」；**不得据此判 BLOCKED**。

## §3 7 Gate（审查维度，继承 2.0，作为规则的组织视角）

| Gate | 名称 | 审查维度 | 对应规则组 |
|------|------|----------|-----------|
| Gate 1 | 核心架构与代码结构 | 服务结构、目录分层、SQL 双后端、部署约束 | B1、B3 |
| Gate 2 | 隔离与安全 | 组织/域隔离、鉴权、审计与接口日志、隐私数据加密 | A9、A11、C1-C3 |
| Gate 3 | 前端与 UI 规范 | 国际化、主题/风格 | D1、D2 |
| Gate 4 | Git 与提交规范 | commit 语义、分支基线（流程维度，无对应规则编号） | — |
| Gate 5 | 测试规范 | 测试目录与用例对齐 | B4 |
| Gate 6 | 数值证据 | 魔鬼数字、性能数值 | A3、A4、B2 |
| Gate 7 | 架构适配性 | API 风格与兼容性、存储、表设计、模块化、观测接入 | A1、A2、A5、A6、A7、A8、A10、A12、A13、A14 |

Gate 适用性按 `scripts/repo_inventory.py` 的技术栈结论选择：无前端 → Gate 3 标「不适用」；非 grape 主仓 → Gate 4/5 按仓库实情标注。

## §4 设计架构约束（A1-A14）

| 规则 | 级别 | 内容（Issue #2403 原文口径） | 审查方式（证据定位） |
|------|------|------------------------------|----------------------|
| A1 | Critical | 新增开放 API 遵循 REST 开放规范，和现有开放 api 风格保持一致 | 对照 `src/api/routes/` 既有端点的资源命名/HTTP 方法/状态码；证据=路由定义 file:line |
| A2 | Medium | 新增开放 API 需要增加对应 grape cli 开放 | 新端点在 grape-cli 契约/命令侧是否有对应开放能力；证据=契约或命令缺失清单 |
| A3 | Critical | 新增接口性能不低于 50tps | **数值来源=明确业务要求（Issue #2403 原文）**，不得表述为实测或行业标准；无压测/设计说明 → `INSUFFICIENT DATA TO VERIFY` |
| A4 | Critical | 新增接口时延 <200ms | 同 A3：来源=明确业务要求（Issue #2403 原文）；不得写成实测值或行业标准 |
| A5 | BLOCKED | 用户文件上传和共享需要支持 OBS 存储 | 用户文件功能是否经 `src/storage/`（local/OBS 双后端）抽象，而非绕过抽象直写本地盘；证据=存储调用点 file:line |
| A6 | Critical | 新增数据库表名符合规则：grape 主控系统 `grape_t_xxx`，grape 运营管理台 `grape_admin_t_xxx`，`xxx` 用英文字母表示数据用途 | 检查新增 `CREATE TABLE`/迁移脚本的表名；证据=DDL file:line |
| A7 | Medium | 大表设计需要支持好分区 | 预估大表（消息/日志/事件类）是否有分区或归档策略说明；证据=DDL 或表设计文档 |
| A8 | Medium | 新增大型特性优先使用模块化设计和接入 | 变更文件是否按 `src/` 模块边界独立成模块，而非在既有模块内膨胀；证据=变更文件清单的模块分布 |
| A9 | BLOCKED | 新增特性的鉴权机制符合 grape 权限机制 | 是否走 `src/auth/`（如 require_org_member）而非自建鉴权旁路；证据=鉴权调用点 file:line |
| A10 | BLOCKED | 运行态服务不可以调用管理态服务 | 检查 runtime 侧代码是否直接调用 admin/mgmt 服务或管理态接口；证据=调用点 file:line |
| A11 | BLOCKED | 每个域的服务（mgmt、runtime、insight）只能访问自己数据库，跨服务数据获取必须通过内部 api | 检查域服务是否直连其他域数据源/表；证据=数据源配置或 SQL file:line |
| A12 | BLOCKED | 新增对象的表唯一键值不能使用自增 id（原文：可以使用雪花算法的 32 的 uuid） | 检查新增表主键/唯一键定义是否为自增（`AUTO_INCREMENT`/`AUTOINCREMENT`/隐式 `rowid`）；替代实现以原文表述为准，不扩大解释；证据=DDL file:line |
| A13 | BLOCKED | 新增特性及服务必须按 grafana 接入规范接入 Metrics（Prometheus）、Logs（Loki）、Traces（Tempo）、profile（Pyroscope） | 四项可观测接入是否齐备（缺项逐项列出）；证据=接入配置或初始化代码 file:line |
| A14 | BLOCKED | 对外开放接口保持兼容 | 是否改动/删除既有开放接口的路径、必填参数、响应字段语义；证据=diff 中的契约变更 file:line |

|------|------|------------------------------|----------------------|
| B1 | BLOCKED | 新增 sql 需同时支持 sqlite 和 mysql 两种模式 | 是否使用了双后端翻译层不覆盖的单边方言（如仅 sqlite 的 `ON CONFLICT`、仅 mysql 的 `ON DUPLICATE KEY`）；证据=SQL file:line |

## §8 发现项证据契约（强制）

每条发现按 `templates/finding.md` 输出，**必含**：
1. 规则编号（A/B/C/D）+ Gate；
2. Severity（取 §1 四级；规则未标注级别则如实写「原文未标注」）；
3. 证据：`file:line` 或 `commit sha` + 最小代码/配置引用；
4. 验证方式（与发现类型匹配）；
5. 修复顺序与依赖关系；
6. 数值依赖（是 → 附 `templates/numerical-recommendation.md`）。

**禁止编造数值风险分**（如「风险 8.5/10」）。无 `file:line`/`commit sha` 证据 → 标「证据不足，需人工复核」，**不得判 BLOCKED**。

## §9 两条硬规则（审查底线，任何模式不得省略）

### 规则 1：数值五源闸门

任何要进入配置、限额或技术建议的数字（超时、TTL、连接池、worker 数、重试、退避、限流、内存/CPU 限额、健康检查间隔、熔断阈值、批大小、保留期、SLO/延迟/吞吐目标等），写之前必须确认来源属于以下五源之一：

1. 本项目已记录该数值（含 rationale）
2. 实际部署厂商的文档默认值/限额
3. 已发布的标准或 RFC
4. 本项目实测数据（生产指标/基准/压测）
5. 明确业务要求

五源都不成立 → **不写最终值**，写占位符并登记待决策：

```
CACHE_TTL_SECONDS=<undecided: 需要命中率与陈旧容忍度测量>
```

并标注 `INSUFFICIENT DATA TO VERIFY`，说明**需要哪种测量**才能定值，列入待决策清单。**看起来合理的数字不能替代缺失的数字**——它会在评审中蒙混过关，比留空更危险。

> 本项目已由 Issue #2403 明确的两项业务要求：A3 `50tps`、A4 `<200ms`。来源标注一律写「明确业务要求（Issue #2403 原文）」，**禁止**表述为实测值、厂商默认值或行业标准。

### 规则 2：结论证据分级（禁止虚假保证）

不得声称「架构安全 / 可扩展 / 生产就绪」，只能声称证据支持的结论，且每个结论标注验证方式：

| 标签 | 含义 |
|------|------|
| `verified: standard` | 由官方标准或 RFC 推出 |
| `verified: vendor` | 由实际部署厂商文档推出 |
| `verified: code` | 读本项目代码确认 |
| `verified: config` | 读本项目配置确认 |
| `measured` | 由本系统生产指标确认 |
| `load-tested` | 由可复现压测确认 |
| `plausible` | 理论上成立，本系统未经实测 |
| `INSUFFICIENT DATA TO VERIFY` | 现有信息无法确认 |

「最佳实践」只有在能指向具名标准、实际部署厂商、所用框架或可复现证据时才可用；否则写「架构建议」并说明其依赖的假设。
