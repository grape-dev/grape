# Spec 文档生成指南

## 执行前提

- 可开发性分析已完成，评级为 `ready`
- 项目知识基线文档已存在
- Issue 的四维分析结论已记录

## Spec 文档模板

```markdown
# Spec: Issue #{number} — {title}

> Generated by Issue Agent | Developability: ready | {datetime}

## Objective
- 要构建什么？
- 为什么要构建？（用户价值 / 业务价值）
- 用户是谁？
- 成功标准是什么？（可量化的指标）

## Scope

### In Scope
- {基于 project-graph.md 分析，明确涉及的功能点}

### Out of Scope
- {明确不做的部分，防止范围蔓延}

## Technical Approach

### 方案概述
{一句话描述技术方案}

### 实现路径
1. {步骤 1：涉及哪个模块，做什么改动}
2. {步骤 2：...}

### 关键设计决策
| 决策 | 选项 | 选择 | 理由 |
|------|------|------|------|
| {决策点} | {选项A/B} | {选择} | {理由} |

## Affected Modules

| 模块 | 改动类型 | 说明 |
|------|---------|------|
| {模块名} | 新增/修改/重构 | {改动说明} |

### 依赖关系
{模块间调用关系，标注新增/变更的调用}

## Acceptance Criteria
- [ ] {可测试的验收条件 1}
- [ ] {可测试的验收条件 2}
- [ ] 所有现有测试通过
- [ ] 新增测试覆盖新功能

## Risks & Mitigations
| Risk | Impact | Mitigation |
|------|--------|------------|
| {风险描述} | {High/Med/Low} | {缓解策略} |

## Open Questions
- 无
```

## 生成流程（按顺序执行）

### Step 1: 收集输入

| 输入 | 来源 | 用途 |
|------|------|------|
| Issue 完整内容 | `GET /repos/{owner}/{repo}/issues/{number}` | Objective + Scope |
| Issue 评论 | `GET /repos/{owner}/{repo}/issues/{number}/comments` | 补充需求细节 |
| 项目架构图 | `data/workspaces/{owner}/{repo}/project-info/project-graph.md` | Technical Approach + Affected Modules |
| 项目能力特性 | `data/workspaces/{owner}/{repo}/project-info/project-capabilities.md` | Technical Approach + Risks |
| 可开发性分析结论 | 上一步输出 | 验证四维全通过 |

### Step 2: 填写 Objective

- **要构建什么**：从 Issue 正文提取核心功能描述
- **为什么**：判断是 Bug 修复（用户受阻）还是 Feature（用户需求）
- **用户是谁**：从 Issue 上下文推断
- **成功标准**：从 Issue 正文的验收标准提取，或基于功能点推导

### Step 3: 填写 Scope

**In Scope**：对照 `project-capabilities.md` 的 Supported Features，每个项必须可映射到 project-graph.md 中的具体模块。

**Out of Scope**：Issue 中提及但非核心的功能，可后续迭代的功能。

### Step 4: 填写 Technical Approach

- **方案概述**：基于 `project-graph.md` 的 Architecture Overview
- **实现路径**：基于 Module Dependency Graph，按依赖顺序列出（底层依赖 → 核心逻辑 → 上层功能）
- **关键设计决策**：识别技术选择点，列出选项和推荐

### Step 5: 填写 Affected Modules

从 `project-graph.md` 提取涉及模块，标注改动类型和依赖关系。

### Step 6: 填写 Acceptance Criteria

- 每个条件必须可验证
- 包含功能正确性、边界条件、错误处理
- 必须包含：所有现有测试通过 + 新增测试覆盖新功能

### Step 7: 填写 Risks & Mitigations

| 风险来源 | 示例 |
|---------|------|
| 架构影响 | 改动涉及核心模块 |
| 外部依赖 | 依赖外部 API 可用性 |
| 数据迁移 | 涉及数据模型变更 |
| 性能影响 | 新增逻辑影响关键路径 |
| 安全风险 | 新增 API 端点或处理用户输入 |

### Step 8: 质量检查

- [ ] Objective 清晰
- [ ] Scope 明确，In/Out 边界清晰
- [ ] Technical Approach 基于项目架构
- [ ] Affected Modules 可映射到 project-graph.md
- [ ] Acceptance Criteria 全部可测试
- [ ] Risks 已识别且有缓解策略
- [ ] 总长度不超过 2000 字

## 发布方式

### 作为 Issue 评论发布

```bash
curl -s -X POST -H "Authorization: Bearer $BOT_GITCODE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "body": "[Issue Agent] 📋 Spec Document\n\n{spec 完整内容}"
  }' \
  https://api.gitcode.com/api/v5/repos/{owner}/{repo}/issues/{number}/comments
```

格式要求：
- 以 `[Issue Agent] 📋 Spec Document` 开头
- Spec 内容使用完整 markdown 格式

### 同时打标签

```bash
curl -s -X PATCH -H "Authorization: Bearer $BOT_GITCODE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"labels": "{原有标签},spec-ready"}' \
  https://api.gitcode.com/api/v5/repos/{owner}/{repo}/issues/{number}
```

新增 `spec-ready` 标签（颜色 `#0075ca`）。

### 分配给机器人

```bash
curl -s -X PATCH -H "Authorization: Bearer $BOT_GITCODE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"assignee": "{BOT_USERNAME}"}' \
  https://api.gitcode.com/api/v5/repos/{owner}/{repo}/issues/{number}
```

使用 Bot 的 GitCode 用户名作为 assignee，表示机器人接管后续开发流程。

## A2A 通知 Coding Agent

```bash
curl -X POST http://localhost:8080/api/a2a \
  -H "Content-Type: application/json" \
  -d '{
    "agent": "coding",
    "payload": {
      "repository": "'"$REPO_FULL_NAME"'",
      "account": "'"$ACCOUNT"'",
      "issue_number": "'"$ISSUE_NUMBER"'",
      "pr_number": "'"$PR_NUMBER"'",
      "context": "Issue #'"$ISSUE_NUMBER"' 已通过深度可开发性分析（评级: ready），Spec 已发布，负责人已分配给机器人。\n\n## Objective\n{spec.objective 摘要}\n\n## Scope (In)\n{spec.in_scope 摘要}\n\n## Technical Approach\n{spec.technical_approach 摘要}\n\n## Affected Modules\n{spec.affected_modules 摘要}\n\n## Acceptance Criteria\n{spec.acceptance_criteria 摘要}\n\n请基于以上 Spec 启动开发实现。完整 Spec 见 Issue 评论。"
    }
  }'
```

⚠️ **字段规则（A2A 服务端强制校验）：** `issue_number` 必填（当前 Issue 的真实编号）；**无法确定 issue_number 就不要调用 A2A**。`pr_number` 有则填（PR 编号）、无则不填（Spec 阶段通常无 PR），严禁将 PR 编号填入 issue_number。
```

### context 构造规则

1. **可开发性评级**：`ready`
2. **负责人已分配给机器人**：coding agent 确认这是机器人接管的任务
3. **Spec 核心摘要**：Objective + Scope + Technical Approach + Affected Modules + Acceptance Criteria
4. **Spec 位置**：告知完整 Spec 在 Issue 评论中
5. **原始 Issue 编号**：coding agent 据此获取完整 Issue 信息

## Spec 版本管理

当用户对已发布 Spec 提出修改意见时：

1. 读取用户评论，理解修改需求
2. 更新 Spec 对应章节
3. 重新发布，标注版本号：

```
[Issue Agent] 📋 Spec Document v2

{更新后的 spec 完整内容}

---
*Updated: {datetime} | Changes: {修改摘要}*
```

4. 通过 A2A 重新通知 coding agent（context 中标注 `Spec v2`）

## Spec 与 implementation skill 的衔接

coding agent 收到 A2A 调用后：

1. 从 A2A context 获取 Spec 摘要
2. 通过 GitCode API 获取 Issue 完整内容（含 Spec 评论）
3. 基于 Spec 执行 `references/new-dev-flow.md` 的开发流程
4. Spec 中的 Technical Approach 对应方案设计
5. Spec 中的 Acceptance Criteria 对应测试用例设计
6. Spec 中的 Affected Modules 对应代码改动范围
