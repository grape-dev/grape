# Issue 无关评论过滤 — 设计文档

- 日期: 2026-08-05
- 项目: gitcode-event-handler(技能脚本 `scripts/gitcode_event_handler.py`)
- 状态: 已获用户批准(2026-08-05)

## 1. 背景与问题

`handle_issue_comment`(逻辑2)目前对 issue 评论的处理:程序自身评论跳过 →
意图1(关闭请求)→ 意图2(need_info 补充升级)→ codeowner 提示 → 无 Multica
提示 → **转发到 Multica 开发小队**。

问题:除"关闭请求"和"need_info 补充"外,**所有**非程序评论(含"好的/收到/
顶/👍/辛苦了/+1"等无实质内容评论、与需求无关的闲聊)都会转发到 Multica,
打扰开发小队。

用户要求:issue 无关的评论需要过滤,不要处理(静默过滤)。

## 2. 需求(用户确认)

1. 短文本/无实质内容评论(好的、收到、顶、👍、辛苦了、+1 等)→ 视为无关
2. 与 issue 主题无关的讨论(聊别的项目/闲聊)→ 视为无关
3. 以上均**静默过滤**:不转发 Multica、不回复
4. 程序自身评论([skills_bot] 前缀)本就不处理(已有)
5. 有实质内容的评论仍转发 Multica(现状保留)
6. 明确意图评论(关闭请求、need_info 补充)不能被误过滤

## 3. 设计(方案 A: 纯规则分级过滤, 预留 LLM 开关位)

### 3.1 插入位置

```
BOT_PREFIX 跳过 → 意图1(关闭请求) → [新增] 无关评论过滤 → 意图2(need_info 补充)
→ codeowner 提示 → 转发 Multica
```

过滤放在**意图1 之后、意图2 之前**:
- 意图1(关闭请求)在过滤**之前**执行 —— 关闭请求("请关闭"等)不含功能词,
  若在过滤之后会被层3 误判为无关, 故豁免(自查发现, 见 §7)
- 过滤在意图2 之前 —— "好的"在 need_info 状态下不会触发意图2 的
  "信息仍不完整"追问
- 明确意图词(请关闭/取消需求等)不含灌水词, 意图1 正则先行命中

### 3.2 组件

**`is_irrelevant_comment(note_body, issue_title, issue_body) -> bool`**

- 层2 短文本: 去除空白/emoji 后 ≤ 8 字 且(命中灌水词集 OR 纯 emoji/符号)
  → 无关
- 层3 需求相关性: 归一化后与需求相关词集合(产品词库 HUAWEI_CLOUD_PRODUCTS
  + 功能词 + issue 标题归一化交集)无任何交集 → 无关
- 两处都不命中 → 视为有实质内容(相关)

**配置项**

| 配置 | 默认 | 说明 |
|---|---|---|
| ENABLE_COMMENT_FILTER | 1 | 无关评论过滤总开关 |
| ENABLE_COMMENT_LLM_FILTER | 0 | LLM 兜底判断开关(预留, 本次不实现调用) |
| IRRELEVANT_COMMENT_WORDS | 见下 | 灌水词集(逗号分隔, 环境变量可覆盖) |

**灌水词集**(IRRELEVANT_COMMENT_WORDS):
好的/收到/顶/辛苦了/👍/+1/明白/了解/ok/OK/可以/行/谢谢/感谢/666/牛/支持/
赞/不错/没问题/收到啦/好的呢/嗯嗯/哦哦/哈哈/了解啦/知道/知晓/确认/收到收到

**功能词集**(评论需求相关性判断用):
查询/列表/创建/删除/修改/修复/问题/bug/报错/错误/支持/希望/需要/补充/
信息/需求/skill/技能/华为云/产品/接口/api/参数/返回/结果/数据/测试/验证/
发布/上线/优化/改进/建议/方案

### 3.3 数据流与错误处理

- 命中无关 → 静默跳过(记 logger 日志: reason=短文本/无关讨论, 不回复不转发)
- `is_irrelevant_comment` 异常 → fail-open(不过滤, 继续原流程, 避免误吞评论)
- 意图1(关闭请求)/意图2(need_info 补充)在过滤之后执行, 明确意图词不含
  灌水词, 不会被误过滤(关闭词如"请关闭"不会被短文本规则命中)

### 3.4 不做的(本次范围外)

- LLM 判断(ENABLE_COMMENT_LLM_FILTER 预留位, 本次只留开关与注释)
- 评论语义级分类(如"用户确认了实现方案"这类上下文评论, 暂按有实质内容转发)

## 4. 测试场景

| 场景 | 输入示例 | 预期 |
|---|---|---|
| 灌水短文本 | "好的" / "收到" / "顶" / "辛苦了" | 过滤(静默) |
| 纯 emoji/符号 | "👍" / "😀" / "!!!" | 过滤(静默) |
| 无关闲聊(较长) | "咱们下周团建去哪?" | 过滤(无需求相关词) |
| 有实质内容 | "请增加按区域筛选功能" | 转发 Multica |
| 关闭请求 | "请关闭这个 issue" | 不误过滤 → 意图1 关闭 |
| need_info 补充 | "补充: 需要支持按名称模糊查询" | 不误过滤 → 意图2 升级 |

## 5. 验收标准

1. 灌水短文本/纯 emoji 评论不再转发 Multica(静默)
2. 与需求无关的长评论不再转发
3. 有实质内容评论仍转发(现状不变)
4. 关闭请求/need_info 补充不被误过滤
5. `ENABLE_COMMENT_FILTER=0` 时完全恢复现状
6. 判定异常 fail-open, 不误吞评论

## 6. 自查记录(2026-08-05)

- **发现**: 关闭请求"请关闭"不含功能词, 若无关过滤放在意图1 之前会被层3
  误判为无关而静默丢弃, 意图1 永不执行。
- **修正**: 过滤插入位置改为意图1 之后、意图2 之前(见 §3.1), 关闭请求由
  意图1 正则先行处理, 天然豁免。
