# 发现输出契约（Findings Format）

工作流审查（能力四）的输出契约。每条发现必须自包含、可验证、可验收。

## 字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `severity` | 是 | `Critical`（阻断）/ `Required`（必须修复）/ `Optional`（建议）/ `Nit`（可选） |
| `dimension` | 是 | 对应五维之一：任务理解 / 受控执行 / 变更验证 / 可靠交付 / 经验沉淀 |
| `evidence_state` | 是 | `observed`（已观察）/ `unobserved`（未观察，需写明原因） |
| `evidence` | 是 | 证据来源：文件路径、行号、会话记录条目；unobserved 写"未获得证据：<原因>" |
| `impact` | 是 | 影响：风险、成本、用户/业务后果，尽量量化 |
| `expected` | 是 | 预期输出：修复后应达到的状态 |
| `scope` | 是 | 修复范围：最小 owner、改动边界（哪些文件/资产） |
| `fix` | 是 | 修复建议：具体动作（可执行） |
| `acceptance` | 是 | 验收检查：可验证的标准，满足即视为修复完成 |

## 严重度判定

| 级别 | 判定 | 是否阻塞 |
|------|------|---------|
| `Critical` | 安全漏洞、数据丢失、功能破坏、工作流存在确定性失败路径 | 阻塞合并 |
| `Required` | 必须修复否则降低质量/可维护性/可复现性 | 必须处理 |
| `Optional` | 值得考虑但不阻塞 | 可选 |
| `Nit` | 风格/格式类 | 可忽略 |

## Markdown 表格格式（用于评论输出）

```markdown
| 维度 | 证据状态 | 严重度 | 发现 | 影响 | 修复 | 验收 |
|------|---------|--------|------|------|------|------|
| 变更验证 | ✅ 已观察 | 🔴 Critical | PR 无测试且 CI 未运行 | 回归风险高 | A2A 补测试并跑 CI | 测试通过且 CI 绿 |
| 经验沉淀 | ⚠️ 未观察 | 🟡 Required | 未发现可复用 skill | 问题易复发 | 沉淀修复为 skill | 新 skill 存在 |
```

## 证据状态写法

- **已观察**：`✅ 已观察 — references/workflow-harness-review.md:12（AGENTS.md 存在）`
- **未观察**：`⚠️ 未观察 — 仓库无 tests/ 目录（GitCode API 遍历 404）`

## 输出纪律

- 每条发现必须能从 `impact → expected → scope → fix → acceptance` 完整走通。
- 无证据的差距宁可标注 `unobserved`，不得用推断补齐。
- 一次优先改进一个问题；发现按杠杆排序（先正确性与验证，后结构与沉淀）。
