# Issue 有效性检查

## 执行前提

仅当 Issue **没有标签**且**没有负责人**时，才需要进行有效性检查。
如果 Issue 已有标签或已分配负责人，说明已处理过，跳过此步骤。

## 检查流程

### 0. 是否与仓库主题相关

读取 Issue 标题和正文，判断内容是否属于该仓库的主题范围：

- 获取仓库信息：`GET /repos/{owner}/{repo}` 返回中的 `description` 和 `topics` 字段
- 对比 Issue 内容与仓库描述/topics 是否匹配

**完全不相关**（如 DevOps 工具仓库收到天气、闲聊、非技术内容）：
→ 标记 `invalid` 标签
→ 关闭 Issue
→ 评论说明该 Issue 与项目无关，已关闭
→ **跳过后续所有步骤**

### 1. 内容质量分析

先深入理解 Issue，再判断后续步骤。读取 Issue 标题和正文，判断 Issue 类型：

| 类型 | 判定线索 |
|------|---------|
| Bug | 标题含"bug/故障/报错/错误/500/异常/不生效/白屏"或正文含堆栈 |
| Feature | 标题含"建议/需求/新增/支持/实现/希望/能不能/优化" |

按检测到的类型执行对应分析：

**Bug 类型：**
| 检查项 | 说明 |
|--------|------|
| 复现步骤 | 是否提供了完整的复现步骤？能否根据描述复现？ |
| 日志/截图/堆栈 | 是否有错误日志、截图或堆栈信息支撑？ |
| 环境信息 | 是否说明了操作系统、版本等环境？ |
| 预期 vs 实际 | 是否说明了预期行为和实际行为？ |

- 信息完整 → 确认是真实 bug，通过检查
- 缺少关键信息 → 标记 `need-info` 并追问，**跳过后续所有步骤**

**Feature 类型：**
| 检查项 | 说明 |
|--------|------|
| 需求描述 | 用户想要什么功能？描述的清晰度如何？ |
| 边界条件 | 是否有模糊表述（如"优化"、"更好"、"支持"等）？ |
| 使用场景 | 是否说明了使用场景和用户故事？ |
| 验收标准 | 是否有可衡量的完成标准？ |

- 需求清晰、边界明确 → 通过检查
- 需求模糊、缺乏场景 → 标记 `need-info` 并追问，**跳过后续所有步骤**

**无法判断类型** → 跳过此步

### 2. 是否已实现

基于对 Issue 的深入理解，用 API 获取最近 commit，搜索 commit message 是否匹配 Issue 标题和核心需求：

```bash
GET /repos/{owner}/{repo}/commits?per_page=20
```

**匹配到相关 commit** → 回复并建议关闭：
> 该功能已在 [`{sha}`](链接) 中实现，建议关闭。
→ **跳过后续所有步骤**

### 3. 是否重复

基于对 Issue 的深入理解，用 API 搜索 open 状态的 Issue，检查标题/正文相似度：

```bash
GET /repos/{owner}/{repo}/issues?state=open&per_page=20
```

**找到重复** → 在重复 Issue 中评论：
> 与 [#N](链接) 重复，已在 #N 中跟进，关闭此 Issue。
→ **关闭并跳过后续所有步骤**

## 总结

| 检查项 | 通过则 | 不通过则 |
|--------|--------|---------|
| 是否与仓库主题相关 | 继续下一步 | 标记 invalid，关闭，跳过 |
| 内容质量分析 | 继续下一步 | 标记 need-info 并追问，跳过；无法判断类型则跳过此步 |
| 是否已实现 | 继续下一步 | 回复建议关闭，跳过 |
| 是否重复 | 进入分诊流程 | 评论并关闭，跳过 |
