# 代码审查

## 场景

当开发者提交代码（push）或发起/更新 Pull Request 时，需要对变更内容进行自动化审查，识别潜在问题并给出改进建议。

## 知识

### 审查维度

1. **正确性**：逻辑是否正确，边界条件是否处理
2. **安全性**：是否存在注入、硬编码密钥、不安全的依赖
3. **可维护性**：命名是否清晰，函数是否过长，是否有重复代码
4. **性能**：是否存在 N+1 查询、不必要的内存分配、阻塞操作
5. **测试覆盖**：变更是否附带测试，测试是否覆盖关键路径

### 常见问题清单

- [ ] 硬编码的 IP、密钥、Token
- [ ] 未处理的 error 返回值
- [ ] 全局变量或可变共享状态
- [ ] 超过 50 行的函数
- [ ] 嵌套超过 3 层的条件逻辑
- [ ] 缺少输入校验
- [ ] SQL/命令拼接而非参数化
- [ ] 未关闭的资源（文件、连接、channel）
- [ ] 缺少并发保护（竞态条件）
- [ ] TODO/FIXME/HACK 注释未跟进

### 语言特定关注点

- **Go**：goroutine 泄漏、context 传递、defer 顺序
- **Python**：异常吞没（bare except）、可变默认参数
- **Java**：资源泄漏（未 close）、线程安全
- **TypeScript**：any 类型滥用、未处理的 Promise

## 步骤

1. 获取本次变更的 diff（`git diff`）
2. 识别变更涉及的文件和模块
3. 逐文件按审查维度检查
4. 标记发现的问题，按严重程度分级：🔴 严重 / 🟡 警告 / 🔵 建议
5. 对每个问题给出具体位置、原因说明和修复建议
6. 总结审查结论：通过 / 需修改 / 需重大修改

## 判断标准

- 严重问题（🔴）数量为 0
- 警告问题（🟡）数量 ≤ 3
- 所有变更文件均已审查覆盖

## 输出规范

```markdown
## 代码审查报告

**结论**: ✅ 通过 / ⚠️ 需修改 / ❌ 需重大修改

### 问题列表

| 级别 | 文件 | 行号 | 问题 | 建议 |
|------|------|------|------|------|
| 🔴 | src/auth.go | 42 | 硬编码密钥 | 使用环境变量 |

### 总结
- 🔴 严重: X 个
- 🟡 警告: X 个
- 🔵 建议: X 个
```
