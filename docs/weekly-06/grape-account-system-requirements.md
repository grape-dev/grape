# Grape 账号体系功能需求文档

## 1. 背景与目标

### 1.1 现状

Grape 当前没有独立的账号体系，用户身份完全依赖第三方平台（GitCode/GitHub）OAuth 登录。存在以下问题：

- 用户必须拥有 GitCode 或 GitHub 账号才能使用 Grape，无法自主注册
- 账号信息与第三方平台强耦合，新增平台需改动账号核心结构
- 平台绑定关系分散在多处，维护成本高
- 无注册策略控制，无法限制谁可以注册
- 无审计日志，无法追溯账号相关操作

### 1.2 目标

建立 Grape 独立账号体系，实现：

- 用户可通过邮箱自主注册 Grape 账号，不依赖任何第三方平台
- 支持用户名和邮箱两种方式密码登录
- 第三方平台登录作为辅助登录方式，插件化扩展，配置即接入
- 账号体系与第三方平台完全解耦，互不依赖
- 完善的注册策略、安全控制和审计能力

### 1.3 参考

- 技术设计文档：docs/weekly-06/grape-account-system-tech-design-v2.md
- 引导页需求文档：docs/weekly-06/onboarding-experience-requirements.md（需求 31）
- 引导页技术设计：docs/weekly-06/onboarding-experience-tech-design.md

| 角色 | 说明 |
|------|------|
| 新用户 | 首次使用 Grape，需要注册账号 |
| 已注册用户 | 已有 Grape 账号，使用用户名或邮箱登录 |
| OAuth 用户 | 通过第三方平台登录的用户，需关联到 Grape 账号 |
| 管理员 | 管理用户账号状态、注册策略的系统管理者 |

## 3. 需求清单

### 需求 1：邮箱注册

**用户故事：** 作为一名新用户，我希望通过邮箱注册 Grape 账号，以便不依赖第三方平台即可使用 Grape。

**业务流程：**

1. 用户在注册页面填写用户名、邮箱、密码、确认密码
2. 前端校验两次密码输入一致，不一致则提示"两次密码输入不一致"
3. 系统校验用户名是否已被占用
4. 系统校验邮箱格式、密码强度、注册策略
5. 若注册策略不允许该邮箱注册，直接拒绝，不发送验证码
6. 系统向用户邮箱发送 6 位数字验证码
7. 用户输入收到的验证码
8. 验证通过后，系统创建账号并自动创建个人工作空间
9. 用户直接登录进入系统

**业务规则：**

- 用户名全局唯一，注册时直接校验并提示"用户名已被占用"（用户名是用户自选的公开标识，直接校验不影响邮箱防枚举设计）
- 用户名规则：3-32 字符，仅允许字母、数字、下划线，保留字（admin、root、system 等）不可使用
- 邮箱格式需符合标准格式
- 密码强度：最少 8 字符，最多 128 字符，不得与用户名或邮箱相同，不可使用常见弱密码（如 12345678、password、qwerty 等，系统维护弱密码列表，不强制要求特殊字符）
- 验证码 10 分钟内有效
- 同一邮箱 60 秒内不可重复发送验证码
- 同一邮箱 10 分钟内最多发送 3 次验证码
- 同一 IP 10 分钟内最多请求 10 次验证码
- 验证码验证失败最多 5 次，超过后作废，需重新发送
- 验证码使用后立即失效，不可复用
- 验证码按场景隔离（注册验证码不可用于密码重置等场景）
- 注册策略校验在发送验证码之前执行

**防枚举设计：**

- 发送验证码接口无论邮箱是否已注册，统一返回"验证码已发送"
- 对未注册邮箱：发送验证码
- 对已注册邮箱：发送"您的邮箱已注册"通知邮件（不发送验证码），接口仍返回"验证码已发送"
- 已注册邮箱的验证码校验必然失败，提示"验证码无效或已过期"，不暴露邮箱已注册状态
- 验证通过后创建账号时若邮箱冲突，提示"该邮箱已注册，请直接登录或重置密码"

**验收标准：**

- 用户名已存在时，提示"用户名已被占用"
- 用户名不满足规则时，提示具体不满足的原因
- 邮箱不在允许注册范围内时，提示"该邮箱不在允许注册范围内"
- 邮箱已注册时，发送验证码阶段仍提示"验证码已发送"
- 已注册邮箱用户输入验证码后，提示"验证码无效或已过期"
- 未注册邮箱用户输入正确验证码后，创建账号成功
- 密码不满足强度要求时，提示具体不满足的原因
- 两次密码输入不一致时，提示"两次密码输入不一致"
- 验证码发送后，页面显示 60 秒倒计时
- 验证码发送提示显示完整邮箱地址（如"验证码已发送到 xxx@xxx.com，请查收邮件"），帮助用户确认邮箱填写无误
- 验证码过期或错误时，提示"验证码无效或已过期"
- 同一验证码连续输入错误 5 次后，提示"验证码已失效，请重新获取"
- 注册成功后，用户自动登录并进入新手引导页（详见需求 17）

### 需求 2：统一密码登录

**用户故事：** 作为已注册用户，我希望使用邮箱或用户名加密码登录 Grape，以便快速访问我的工作空间。

**业务流程：**

1. 用户在登录页输入标识符（邮箱或用户名）和密码
2. 系统根据输入格式自动识别标识符类型（包含 @ 为邮箱，否则为用户名）
3. 系统校验标识符和密码
4. 校验通过，签发登录凭证，进入系统
5. 登录后去向：已有平台绑定 → 上次工作页面；无平台绑定 → 新手引导页（需求 17）
6. 校验失败，返回错误提示

**业务规则：**

- 登录页为单输入框，用户输入邮箱或用户名，系统自动识别格式
- 登录失败统一提示"账号或密码错误"，不泄露标识符是否存在
- 密码校验通过但账号被禁用时，才提示"账号已被禁用"
- 密码校验未通过时，无论账号是否存在或被禁用，统一提示"账号或密码错误"
- 登录失败限流（账号维度）：同一账号 5 分钟内连续失败 5 次，临时锁定 15 分钟，锁定提示文案为"连续登录失败 5 次，账号已临时锁定 15 分钟。可通过邮箱验证码立即解锁。"，提供邮箱验证码自助解锁入口（图形验证码作为 P1 后续迭代，本期不实现）
- 登录失败限流（IP 维度）：同一 IP 10 分钟内连续失败 20 次，临时锁定 15 分钟
- 系统存量用户（旧密码哈希算法）登录成功后自动升级密码哈希算法，用户无感知

**验收标准：**

- 输入正确的邮箱和密码，成功登录进入系统
- 输入正确的用户名和密码，成功登录进入系统
- 输入错误的密码，提示"账号或密码错误"
- 输入不存在的邮箱或用户名，提示"账号或密码错误"
- 被禁用用户输入正确密码时，提示"账号已被禁用"
- 被禁用用户输入错误密码时，提示"账号或密码错误"
- 连续失败 5 次后，临时锁定 15 分钟，可通过邮箱验证码自助解锁（图形验证码 P1 后续迭代）
- 锁定时提示"连续登录失败 5 次，账号已临时锁定 15 分钟。可通过邮箱验证码立即解锁。"
- 登录成功后，已有平台绑定的用户进入上次工作页面，无平台绑定的用户进入新手引导页（需求 17）

### 需求 3：忘记密码（密码重置）

**用户故事：** 作为已注册用户，我忘记了密码，希望通过邮箱重置密码，以便重新登录系统。

**业务流程：**

1. 用户在登录页点击"忘记密码"
2. 用户输入注册邮箱
3. 系统向该邮箱发送验证码
4. 用户输入验证码、新密码、确认新密码
5. 前端校验两次密码输入一致
6. 验证通过后，密码更新成功
7. 该账号在其他设备的登录状态全部失效
8. 用户返回登录页，用新密码登录

**业务规则：**

- 无论邮箱是否注册，系统均返回"验证码已发送"（防止探测邮箱是否已注册）
- 验证码 10 分钟有效，60 秒内不可重复发送，10 分钟内最多 3 次
- 验证码使用后立即失效
- 验证码按场景隔离（密码重置验证码不可用于其他场景）
- 新密码需满足密码强度要求（同需求 1）
- 两次密码输入不一致时提示"两次密码输入不一致"
- 密码重置后，该账号所有已登录设备强制下线
- 密码重置需记录审计日志

**验收标准：**

- 输入已注册邮箱，收到验证码，输入验证码和新密码后，重置成功
- 重置成功后返回登录页，登录页显示"密码已重置，请使用新密码登录"提示
- 输入未注册邮箱，仍提示"验证码已发送"，但不实际发送
- 重置密码后，其他设备的登录状态立即失效
- 验证码过期或错误时，提示"验证码无效或已过期"
- 新密码不满足强度要求时，提示具体不满足的原因
- 两次密码输入不一致时，提示"两次密码输入不一致"

### 需求 4：第三方平台登录（插件化扩展）

**用户故事：** 作为用户，我希望通过 GitCode、GitHub 等第三方平台登录 Grape，以便复用已有账号免注册。

**业务流程（已绑定）：**

1. 用户在登录页点击第三方平台登录按钮
2. 跳转到第三方平台授权页
3. 用户授权后，系统获取第三方平台用户信息
4. 系统按平台用户 ID 查找绑定关系，找到已绑定的 Grape 账号
5. 直接登录进入系统

**业务流程（未绑定）：**

1-4 同上
5. 系统按平台用户 ID 查找绑定关系，未找到绑定
6. 系统自动创建 Grape 账号并绑定第三方身份：
   - 用户名从第三方平台用户名（external_login）自动生成，若冲突则加数字后缀
   - 无密码、无邮箱——纯 OAuth 账号，用户后续可在用户设置补设密码和邮箱
   - 平台返回的邮箱和昵称自动写入账号资料
   - 自动创建个人工作空间
   - 首次自动创建需通过 OAuth 白名单校验（按第三方平台用户名校验，不校验邮箱注册策略）
7. 用户直接登录进入系统，无中间页面

**业务流程（邮箱已注册的场景）：**

1-6 同未绑定流程
7. 若第三方平台返回了已验证邮箱，且该邮箱已被其他 Grape 账号注册：
   - 不自动创建新账号（避免重复账号）
   - 重定向到关联页面，引导用户绑定已有 Grape 账号
   - 绑定已有账号时，必须先验证 Grape 账号身份（输入用户名/邮箱 + 密码）
   - 验证通过后写入绑定关系并登录

**业务规则：**

- OAuth 首次登录优先自动创建账号，不弹注册/关联选择页（业界通用做法，与 GitHub/GitLab 一致）
- 自动创建的账号为纯 OAuth 账号（无密码无邮箱），用户后续可在用户设置补设密码和邮箱（需求 12/13）
- 自动创建的账号用户名从第三方平台用户名（external_login）生成，清理非法字符后不足 3 字符用 user 兜底，冲突加数字后缀
- 平台返回的邮箱自动写入账号资料（不要求用户验证，OAuth 平台已验证）
- 自动创建后自动创建个人工作空间，用户直接登录进入系统
- OAuth 自动创建不受邮箱注册策略限制（不受开放注册开关和白名单影响），仅受 OAuth 白名单控制
- 仅当第三方平台返回的邮箱已被其他 Grape 账号注册时才回退到手动关联流程
- OAuth 流程强制携带 state 参数防 CSRF
- 所有第三方平台共用统一的 OAuth 回调地址，回调后通过 state 参数恢复平台标识和业务上下文（登录或绑定），不需要为每个平台单独配置回调地址
- OAuth 流程 PKCE 策略：标准 OAuth 2.0 平台强制启用；非标准平台按平台配置决定是否启用
- 第三方登录回调后只信任服务端换取的用户信息，不信任前端传入
- 绑定已有 Grape 账号时，必须先验证 Grape 账号身份，不可仅凭 OAuth 返回的邮箱自动关联（防账号劫持）

**插件化扩展规则：**

- 标准 OAuth 2.0 平台：通过配置文件接入，不改代码
- 非标准平台：通过适配器扩展，新增适配器实现
- 平台配置包含：平台名称、OAuth 端点地址、授权范围、字段映射规则、是否启用 PKCE、品牌色、白名单列名、Accept header
- 平台协议配置和平台凭据（client_id/client_secret）分离存储：协议配置以配置文件为真相源，凭据由管理员独立配置
- 旧配置文件和旧数据无需调整，更新代码后已有平台功能正常（代码内置默认配置兜底）
- 前端登录页根据已配置的平台列表自动展示对应登录入口
- 白名单表按平台动态扩展：新增平台时自动创建对应白名单字段，不改表结构定义

**验收标准：**

- 点击 GitCode/GitHub 登录按钮，正确跳转到对应平台授权页
- 已绑定的用户授权后直接登录成功
- 未绑定的用户授权后，系统自动创建 Grape 账号并绑定，直接登录进入系统，无中间页面
- 自动创建后，项目页顶部显示非阻断式补全引导提示条（详见需求 18）
- 自动创建的账号无密码无邮箱，用户名从第三方平台用户名自动生成
- 用户名冲突时自动加数字后缀（如 xiaowu2119 → xiaowu2119_2）
- 平台返回的邮箱和昵称自动写入账号资料
- 若第三方平台返回的邮箱已被其他 Grape 账号注册，重定向到关联页面引导用户绑定已有账号
- 绑定已有账号时，必须验证 Grape 账号身份（用户名/邮箱 + 密码）才可绑定
- OAuth 自动创建不受邮箱注册策略限制，仅受 OAuth 白名单控制
- 标准 OAuth 2.0 平台通过配置文件接入后，登录页自动出现该平台按钮
- 非标准平台通过新增适配器接入
- 前端只展示已配置凭据的平台，未配置的不展示
- 旧配置文件和旧数据不调整，更新代码后已有平台 OAuth 功能正常
- 新增平台只需在配置文件加平台条目 + 可选配置凭据，重启生效，不改代码
- 新增平台时无需在平台侧配置新的回调地址，所有平台共用同一个回调地址

### 需求 5：账号绑定与解绑

**用户故事：** 作为已登录用户，我希望管理已绑定的第三方平台账号，以便灵活控制登录方式。

**业务流程（绑定）：**

1. 用户在用户设置点击"绑定"某第三方平台
2. 跳转到第三方平台授权页
3. 用户授权后，绑定关系写入系统
4. 第三方平台凭据加密存储

**业务流程（解绑）：**

1. 用户在用户设置点击"解绑"某第三方平台
2. 系统检查该账号是否至少保留一种登录方式（Grape 密码 或 ≥1 个第三方绑定）
3. 若用户没有 Grape 密码且这是最后一个第三方绑定，引导用户先设置 Grape 密码（通过邮箱验证码完成）
4. 校验通过，删除绑定关系
5. 记录审计日志

**业务规则：**

- 第三方平台凭据加密存储，与业务凭据（AK/SK 等）物理分离
- 同一第三方账号只能绑定一个 Grape 账号
- 同一 Grape 账号的同一平台只能绑定一个第三方账号
- 解绑前需校验至少保留一种登录方式，防止用户无法登录
- 若用户无 Grape 密码且要解绑最后一个第三方绑定，引导用户先设置 Grape 密码
- 设置密码通过邮箱验证码完成，无需提供旧密码
- 绑定/解绑操作需记录审计日志
- 绑定流程和登录流程共用统一的 OAuth 回调地址，回调后通过授权状态参数区分业务上下文（登录或绑定），不需要为每个平台配置多个回调地址
- 所有平台共用同一个回调地址，新增平台时无需在平台侧额外配置回调地址
- 回调地址由系统根据访问域名自动构造，不在配置中硬编码，避免域名变更后失效

**验收标准：**

- 已登录状态下绑定第三方平台成功后，用户设置显示"已绑定"
- 绑定授权完成后正确回到用户设置并显示成功反馈，不误走登录流程
- 重复绑定同一第三方账号（已被其他 Grape 账号绑定），提示"该平台账号已被绑定"
- 解绑后该平台登录入口不再适用于当前 Grape 账号
- 最后一种登录方式不可解绑，提示"至少保留一种登录方式"或引导设置密码
- 无密码用户解绑最后一个第三方绑定时，引导设置密码；若无邮箱则引导先设置邮箱再设置密码（设置邮箱→设置密码→再解绑）
- 绑定成功后重定向回用户设置并显示成功反馈（需求 25）

### 需求 6：账号体系独立解耦

**用户故事：** 作为系统维护者，我希望 Grape 账号体系与第三方平台完全解耦，以便未来接入新平台时改动最小化。

**业务规则：**

- Grape 账号信息不包含任何第三方平台字段
- 第三方平台绑定关系独立存储，与 Grape 账号信息物理分离
- 第三方平台凭据（OAuth token 等）加密存储在绑定关系中，不混入业务凭据
- 用户账号登录配置与自动化 Bot 运行时配置各自独立管理：账号登录相关的平台配置（登录入口、授权回调地址、登录凭据）和 Bot 运行时相关的配置（任务执行 token、事件通知 token、Bot 身份）是两个不同职责域的配置，各自独立存放、独立变更，一方配置的修改或异常不影响另一方的正常运行
- 已有混合配置无需手动拆分：更新代码后，系统自动识别已有配置中的账号登录相关部分并独立加载，不影响 Bot 运行时配置的正常读取，运维人员无需手动干预
- 第三方登录的 OAuth 流程统一通过平台注册表驱动，按平台标识分流处理，不按平台名硬编码分叉
- 同时支持标准 OAuth 2.0 协议和现有 GitCode/GitHub 模式的平台接入
- 所有平台相关逻辑（白名单检查、凭据读取、旧表同步、token 刷新）通过配置驱动，不硬编码平台名
- 代码保留内置默认配置确保向前兼容，配置文件为协议参数真相源

**数据迁移规则：**

迁移分阶段进行，确保不中断服务：

1. 建新表阶段（不停服）：创建独立账号表和绑定关系表
2. 双写阶段（不停服）：OAuth 登录时同时写入旧结构和新结构，同一事务保证一致性；新注册用户直接写新表
3. 回填阶段（不停服）：执行迁移脚本，将现有平台字段数据回填到绑定关系表，幂等可重复执行
4. 切读阶段（灰度）：OAuth 登录查询切换为查绑定关系表，兼容期同时查旧结构做 fallback；以新表为准，新表无记录时 fallback 到旧结构，并记录不一致日志
5. 废弃阶段（确认稳定）：读写全部切换到新表，老表保持不动（不删字段、不改结构），只读保留做回滚兜底

**迁移冲突处理：**

- 迁移过程中处理平台 ID 与绑定关系表唯一约束的冲突
- 迁移脚本需幂等，可重复执行
- 提供回滚方案：切读阶段可回滚到查旧结构

**验收标准：**

- Grape 账号信息中无任何第三方平台字段
- 标准 OAuth 2.0 平台通过配置文件接入，无需改代码
- 非标准平台通过新增适配器接入，无需改表结构
- 账号登录配置的修改或异常不影响 Bot 运行时功能，反之亦然
- 更新代码后，已有混合配置环境无需运维手动拆分，账号登录和 Bot 运行时均正常工作
- 现有用户数据迁移后，OAuth 登录功能正常，用户无感知
- 迁移脚本可重复执行，不产生重复数据
- 所有平台相关逻辑通过配置驱动，代码中不硬编码平台名做条件分叉
- 旧配置文件和旧数据不调整，更新代码后已有平台功能正常
- 新增平台只需在配置文件加平台条目 + 可选配置凭据，重启生效

### 需求 7：注册策略与白名单控制

**用户故事：** 作为管理员，我希望控制谁可以注册 Grape 账号，以便在开放注册和受限注册之间灵活切换。

**业务规则：**

管理员可配置以下注册策略：

- 开放注册开关：是否允许任意邮箱注册
- 邮箱白名单：仅白名单内邮箱可注册
- 域名白名单：仅白名单内域名可注册（如 @company.com）

核心原则：白名单非空时，白名单限制优先于开放注册开关。

**注册策略判定表：**

| 邮箱白名单 | 域名白名单 | 开放注册 | 结果 |
|-----------|-----------|---------|------|
| 命中 | — | 任意 | 允许 |
| 未命中 | 命中 | 任意 | 允许 |
| 未命中 | 未命中 | 开启 | 允许 |
| 未命中 | 未命中 | 关闭 | 拒绝 |
| 空 | 空 | 开启 | 允许 |
| 空 | 空 | 关闭 | 拒绝 |
| 空 | 非空 | 任意 | 仅域名白名单允许 |
| 非空 | — | 任意 | 仅邮箱白名单允许 |

**补充规则：**

- 邮箱白名单非空时：仅白名单邮箱可注册，开放注册开关不影响结果
- 域名白名单非空且邮箱白名单为空时：仅白名单域名可注册，开放注册开关不影响结果
- 两个白名单均为空时：由开放注册开关决定
- 第三方 OAuth 登录不受邮箱注册策略限制（不受开放注册开关和邮箱白名单影响），仅受 OAuth 白名单控制
- OAuth 白名单与邮箱注册策略独立运作，不混用

**验收标准：**

- 邮箱白名单非空时，仅白名单邮箱可注册，无论开放注册开关状态
- 邮箱白名单为空、域名白名单非空时，仅白名单域名可注册，无论开放注册开关状态
- 两个白名单均为空且开放注册开启时，任意邮箱可注册
- 两个白名单均为空且开放注册关闭时，所有邮箱不可注册
- 第三方 OAuth 登录不受邮箱注册策略影响，即使开放注册关闭也可自动创建账号
- OAuth 白名单拒绝的用户不可自动创建账号

### 需求 8：开发环境验证码便捷机制

**用户故事：** 作为开发者/测试人员，我希望在开发环境中无需真实邮件服务即可完成注册和登录测试，以便快速开发和调试。

**业务规则：**

- 支持通过环境变量配置一个固定验证码，开发环境下所有邮箱均可使用该验证码通过验证
- 固定验证码优先级最高，配置后直接跳过邮件发送环节
- 固定验证码跨所有场景（注册、重置密码、设置密码、解锁账号）通用，但需记录审计日志（标注使用固定验证码）
- 仅在非生产环境生效，生产环境强制禁用此机制
- 邮件发送模式按优先级自动选择：

| 优先级 | 模式 | 触发条件 | 说明 |
|--------|------|---------|------|
| 1 | 固定验证码 | 非生产环境 + 环境变量已配置 | 跳过邮件发送，所有邮箱使用固定码 |
| 2 | SMTP 中继 | 配置了 SMTP 服务地址 | 通过 SMTP 中继发送真实邮件 |
| 3 | 第三方 API | 配置了第三方 API 密钥 | 通过第三方 API 发送真实邮件 |
| 4 | 日志输出 | 以上均未配置 | 验证码输出到日志，开发者从日志获取 |

- 生产环境强制禁用固定验证码和日志输出模式，必须配置 SMTP 或第三方 API
- 生产环境启动时校验邮件服务配置，未配置时拒绝启动
- 固定验证码使用常量时间比较，防时序攻击

**验收标准：**

- 开发环境配置固定验证码后，任意邮箱使用该验证码即可通过验证
- 生产环境即使配置了固定验证码环境变量，也不生效
- 未配置邮件服务且未配置固定验证码时，验证码出现在日志中
- 配置了 SMTP 或第三方 API 后，验证码通过真实邮件发送
- 生产环境未配置邮件服务时，服务拒绝启动
- 使用固定验证码通过验证时，审计日志标注"使用固定验证码"

### 需求 9：JWT 密钥安全门禁

**用户故事：** 作为系统管理员，我希望生产环境使用安全的 JWT 密钥，防止密钥泄露导致的安全风险。

**业务规则：**

- 维护不安全密钥黑名单（空值、代码内默认值、模板占位符等）
- 生产环境启动时校验 JWT 密钥，命中黑名单则拒绝启动
- 开发环境可使用默认密钥，不强制校验
- 支持 JWT 密钥轮换：使用密钥 ID 标识密钥版本，旧密钥用于验签，新密钥用于签发，平滑轮换
- 轮换周期建议 90 天，旧密钥保留 30 天用于验签过渡

**验收标准：**

- 生产环境使用默认密钥启动时，服务拒绝启动并报错
- 生产环境使用自定义安全密钥启动时，正常启动
- 开发环境使用默认密钥启动时，正常启动
- 密钥轮换后，旧 token 仍可验签，新 token 使用新密钥签发

### 需求 10：用户账号禁用与 Token 失效

**用户故事：** 作为系统设计者，我希望账号体系支持账号禁用机制，以便管理员可以禁用违规用户，被禁用用户无法继续使用系统。

**业务流程：**

1. 管理员可在管理后台将用户账号状态设为"禁用"（详见需求 21）
2. 被禁用用户登录时提示"账号已被禁用"（仅当密码正确时才暴露禁用状态）
3. 被禁用用户的登录凭证即时失效
4. 管理员可恢复被禁用账号（详见需求 21）
5. 禁用/恢复操作记录审计日志

**业务规则：**

- 禁用状态持久化，不因服务重启而恢复
- 鉴权中间件每次请求校验用户禁用状态，通过内存缓存优化（最长 5 秒延迟）
- 缓存不可用时，鉴权中间件每次请求查库（不跳过校验）
- 密码重置/密码修改/登出操作触发缓存主动失效

**Token 失效策略：**

| 场景 | access token | refresh token | 说明 |
|------|--------------|---------------|------|
| 忘记密码（密码重置，需求 3） | 即时失效 | 即时拒绝续签 | 全设备下线（用户不在登录态，所有设备凭证失效） |
| 修改密码（需求 11） | 即时失效 | 即时拒绝续签 | 全设备下线，当前设备签发新凭证 |
| 账号禁用（需求 10/21） | 即时失效 | 即时拒绝续签 | 全设备下线 |
| 账号注销（需求 14） | 即时失效 | 即时拒绝续签 | 全设备下线，进入冷静期 |
| 登出 | 即时失效 | 即时拒绝续签 | 当前用户所有设备下线 |

**登录失败锁定与自助解锁：**

- 账号临时锁定后，用户可通过邮箱验证码自助解锁
- 解锁验证码同样受 60 秒/10 分钟限流约束
- 解锁成功后清除失败计数和锁定状态
- 解锁操作记录审计日志

**验收标准：**

- 禁用用户登录时，密码正确则提示"账号已被禁用"，密码错误则提示"账号或密码错误"
- 禁用用户已签发的凭证在 5 秒内失效
- 禁用用户的凭证刷新被拒绝
- 数据模型和中间件校验逻辑已就绪，管理员可在管理后台禁用/恢复用户（详见需求 21）
- 服务重启后，禁用状态保持不变
- 账号锁定后，可通过邮箱验证码自助解锁

### 需求 11：修改密码

**用户故事：** 作为已登录用户，我希望修改自己的密码，以便定期更新密码保障账号安全。

**业务流程：**

1. 用户在用户设置点击"修改密码"
2. 用户输入当前密码、新密码、确认新密码
3. 前端校验两次新密码输入一致
4. 系统校验当前密码是否正确
5. 校验通过，更新密码
6. 该账号所有其他设备登录状态失效
7. 当前设备保留登录状态
8. 记录审计日志

**业务规则：**

- 修改密码需验证当前密码，不可跳过
- 新密码需满足密码强度要求（同需求 1）
- 新密码不可与当前密码相同
- 两次新密码输入不一致时提示"两次密码输入不一致"
- 密码修改后，该账号所有其他设备强制下线，当前设备保留
- 修改密码记录审计日志

**验收标准：**

- 输入正确的当前密码和符合强度的新密码，修改成功
- 输入错误的当前密码，提示"当前密码错误"
- 新密码不满足强度要求时，提示具体不满足的原因
- 新密码与当前密码相同时，提示"新密码不可与当前密码相同"
- 两次新密码输入不一致时，提示"两次密码输入不一致"
- 修改成功后，其他设备需重新登录，当前设备不受影响

### 需求 12：设置密码（无密码用户）

**用户故事：** 作为通过第三方平台注册的无密码用户，我希望主动设置 Grape 密码，以便增加一种登录方式不依赖第三方平台。

**业务流程：**

1. 用户在用户设置点击"设置密码"（仅对无密码用户显示）
2. 系统向用户邮箱发送验证码
3. 用户输入验证码、新密码
4. 验证通过后，设置密码
5. 记录审计日志

**业务规则：**

- 仅对无密码用户显示"设置密码"入口
- 设置密码需通过邮箱验证码验证身份（无需旧密码）
- 新密码需满足密码强度要求（同需求 1）
- 设置密码无确认密码字段（与修改密码不同，减少操作步骤）
- 设置密码后不触发其他设备下线（仅增加一种登录方式）
- 若用户无邮箱，需先完成"首次设置邮箱"流程：用户输入邮箱地址 → 系统向该邮箱发送验证码 → 验证通过后绑定邮箱 → 然后才能设置密码
- "首次设置邮箱"与"邮箱变更"不同：首次设置不需要验证旧邮箱（因为没有旧邮箱），直接向新邮箱发验证码验证所有权
- 设置密码记录审计日志

**验收标准：**

- 无密码用户在用户设置可看到"设置密码"入口
- 有密码用户不显示"设置密码"入口
- 输入正确验证码和符合强度的密码，设置成功
- 设置成功后，用户可用邮箱/用户名 + 密码登录
- 设置密码后，已登录设备不受影响

### 需求 13：邮箱变更

**用户故事：** 作为已登录用户，我希望更换绑定的邮箱地址，以便使用新的邮箱登录和接收通知。

**业务流程：**

1. 用户在用户设置点击"更换邮箱"
2. 用户输入新邮箱地址
3. 系统向新邮箱发送验证码
4. 用户输入验证码
5. 验证通过后，系统向旧邮箱发送"邮箱已变更"通知邮件
6. 更新账号邮箱，完成变更
7. 记录审计日志

**业务规则：**

- 新邮箱需全局唯一，校验冲突
- 新邮箱需通过验证码验证所有权
- 验证码限流归属当前用户账号（非新邮箱），防止用他人邮箱触发验证码发送
- 邮箱变更后，向旧邮箱发送通知邮件（告知邮箱已被更换，若非本人操作请联系管理员）
- 邮箱变更后，用户可用新邮箱登录，旧邮箱不可登录
- 邮箱变更不触发设备下线（仅影响登录标识，不影响已签发凭证）
- 邮箱变更记录审计日志

**验收标准：**

- 输入未注册的新邮箱，收到验证码，验证通过后邮箱变更成功
- 输入已注册的新邮箱，提示"该邮箱已被占用"
- 邮箱变更后，旧邮箱收到"邮箱已变更"通知邮件
- 邮箱变更后，新邮箱可登录，旧邮箱不可登录
- 邮箱变更后，已登录设备不受影响

### 需求 14：账号注销

**用户故事：** 作为已注册用户，我希望可以注销自己的 Grape 账号，以便在不再使用时删除个人数据。

**业务流程：**

1. 用户在用户设置点击"注销账号"
2. 系统要求用户重新认证（输入密码或邮箱验证码）
3. 认证通过后，系统检查用户是否有未完成的资源（如进行中的任务、负责的项目）
4. 若有未完成资源，提示用户先处理或确认强制注销
5. 用户确认后，系统将账号标记为"已注销"（软删除），进入 30 天冷静期
6. 冷静期内用户可联系管理员恢复账号
7. 冷静期结束后，系统匿名化或删除用户个人工作空间和相关数据
8. 解绑所有第三方平台绑定关系
9. 用户账号登录凭证全部失效
10. 记录审计日志

**业务规则：**

- 注销前必须重新认证，确认是账号本人操作
- 重新认证方式根据用户已有登录方式动态选择：有密码→输入密码；有邮箱→邮箱验证码
- 无密码且无邮箱的用户，需先在用户设置设置邮箱或密码后才能注销（先设置邮箱→再设置密码→然后注销）
- 注销采用软删除，账号标记为"已注销"，进入 30 天冷静期
- 冷静期内账号不可登录，但管理员可恢复
- 冷静期结束后，个人数据匿名化或删除，邮箱释放可重新注册
- 冷静期内邮箱仍占用，不可用于注册
- 注销后第三方绑定关系在冷静期内保留，冷静期结束后清除
- 注销操作不可由用户自行撤销，需联系管理员在冷静期内恢复
- 管理员账号需先转移管理员权限才可注销
- 注销操作记录审计日志

**验收标准：**

- 注销前要求输入密码或邮箱验证码
- 无密码无邮箱用户注销时提示"请先设置邮箱或密码后再注销"
- 注销后该账号无法登录

### 需求 17：未绑定第三方平台的用户引导

**用户故事：** 作为通过邮箱注册的 Grape 用户，我没有绑定任何第三方代码托管平台（GitCode/GitHub），我希望在进入 Grape 后看到清晰的绑定引导，直接绑定平台开始使用，以便最快速度进入工作状态。

**业务背景：**

Grape 的核心 DevOps 能力依赖代码仓库，而代码仓库来自第三方代码托管平台（GitCode/GitHub）。未绑定平台的用户需要先完成平台绑定才能使用项目、工作台等功能。

当前问题：
- 未绑定用户进入系统后看到的是"有仓库"的页面布局——显示"我的项目(0)""已托管(0)"等空数据，以及无法操作的项目模板，体验空洞
- 绑定引导卡片夹在空的项目列表和项目模板之间，用户不知道该做什么
- 依赖仓库的功能（场景·技能市场、知识库等）在未绑定时可见，但进入后无法操作或报错
- 不同平台的仓库混合在一个列表里，用户心智不清晰

**业务流程：**

用户注册成功并登录后：

1. 系统查询用户的平台绑定状态
2. 系统根据绑定状态决定首页内容：
   - 已绑定至少一个平台 → 进入项目页，展示所有已绑定平台的仓库列表（混合展示，平台切换栏作为筛选功能，默认展示全部）
   - 未绑定任何平台 → 进入新手引导页
3. 用户在新手引导页选择绑定一个平台 → 完成 OAuth 授权 → 系统自动切换到项目页，展示刚绑定平台的仓库列表
4. 用户在未绑定状态下可使用不依赖仓库的功能（Agent 运行时、设备监控、仓库设置、组织管理）
5. 用户在未绑定状态下尝试使用依赖仓库的功能时 → 系统引导其返回新手引导页完成平台绑定
6. 用户在项目选择页点击"工作台"tab → 直接进入第一个已托管仓库的工作台 Dashboard，不经过平台选择中间页

**首页三种状态：**

| 状态 | 判定条件 | 首页内容 |
|------|---------|---------|
| 未绑定任何平台 | 未绑定任何第三方平台 | 新手引导页（欢迎语 + 平台绑定入口） |
| 已绑定但无仓库 | 已绑定平台，但该平台无托管仓库 | 项目页（空态引导"去该平台托管仓库"） |
| 已绑定有仓库 | 已绑定平台且有托管仓库 | 项目页（仓库列表正常展示） |

**新手引导页：**

未绑定时，系统不展示"项目/项目模板/工作台"等需要仓库的功能区域，改为展示专门的新手引导页（详见需求 31）：

- 欢迎语 + 产品定位语
- 平台绑定入口：展示已配置的平台列表，每个平台一张卡片（平台图标 + 名称 + "绑定"按钮），未配置的平台不展示
- 底部小提示：绑定后自动进入工作台，可在用户设置管理绑定
- 用户头像下拉菜单提供"用户设置"和"登出"入口

**项目页仓库展示：**

已绑定平台后，项目页展示所有已绑定平台的仓库列表，混合展示：

- 项目页顶部展示平台切换栏（"全部" + 每个已绑定的平台），作为筛选功能，默认展示全部
- 仓库卡片显示平台图标和平台名称，用户可直观区分每个仓库所属平台
- 切换到某个平台时只展示该平台的仓库，切换回"全部"展示所有仓库
- 侧边栏仓库下拉框按平台分组（optgroup），用户切换仓库时可按平台分组查找

**工作台与平台的关系：**

工作台的所有功能（需求中心、项目场景、流水线、自动化、各 Agent、知识库）都基于当前选中的仓库，而仓库归属某个平台：

- 用户在项目页选中某个平台的某个仓库 → 进入工作台
- 工作台所有功能基于该仓库的数据
- 用户切换平台 → 回到项目页，展示新平台的仓库列表，重新选择仓库进入工作台

**多平台场景：**

- 用户可同时绑定多个平台（如同时绑定 GitCode 和 GitHub）
- 每个平台独立展示仓库，项目页按平台切换，不混合

**业务规则：**

- 未绑定时展示新手引导页，不展示项目列表、项目模板、工作台、场景·技能市场、知识库等需要仓库的功能

- 平台绑定/解绑管理在用户设置操作，不在项目页面

### 需求 18：OAuth 登录用户账号补全引导

**用户故事：** 作为通过第三方平台（GitCode/GitHub）OAuth 登录的用户，我首次登录 Grape 后没有 Grape 密码和邮箱，我希望系统引导我补全账号信息，以便我不只依赖第三方平台登录，也能使用密码登录和验证码相关功能（忘记密码、设置密码、账号注销等）。

**业务背景：**

OAuth 登录用户通过第三方平台首次登录 Grape 时，系统自动创建 Grape 账号并绑定第三方平台。但此账号存在以下信息缺失：

- 无 Grape 密码 — 用户只能通过 OAuth 登录，无法使用密码登录
- 无邮箱（或邮箱未验证）— 无法使用验证码相关功能（忘记密码、设置密码、邮箱变更、账号注销等）
- 账号安全完整性不足 — 只有一种登录方式，解绑第三方平台后无法登录

需要引导用户补全账号信息，但不阻断用户使用系统。

**用户场景：**

| 场景 | 用户状态 | 系统引导 |
|------|---------|---------|
| OAuth 首次登录 | 无密码、无邮箱 | 引导设置密码 + 补填邮箱（非阻断） |
| OAuth 首次登录 | 无密码、有平台返回邮箱 | 引导设置密码（邮箱已自动写入，非阻断） |
| 已绑定一个平台，想加绑另一个 | 有/无密码 | 用户设置提供绑定入口 |
| OAuth 用户想换平台 | 只有一个平台绑定、无密码 | 先设置密码 + 绑定新平台，再解绑旧平台 |
| OAuth 用户解绑最后一个平台 | 无密码 | 阻止解绑，引导先设置密码（需求 5 已覆盖） |

**业务流程：**

OAuth 登录的账号关联原则：

- **首次 OAuth 登录**：系统自动创建 Grape 账号 + 绑定第三方平台 + 签发登录凭证 + 标记首次登录（需求 4 自动创建流程）
- **非首次 OAuth 登录**：系统直接关联到已有 Grape 账号 + 签发登录凭证，不重复创建账号
- **密码登录后绑定第三方平台**：用户先通过邮箱注册了 Grape 账号，后绑定 GitCode，后续 OAuth 登录时关联到同一个 Grape 账号
- **关联唯一依据**：第三方平台的用户标识是 OAuth 登录关联到 Grape 账号的唯一依据

OAuth 首次登录后的补全引导：

1. 系统自动创建 Grape 账号 + 绑定第三方平台 + 签发登录凭证（现有逻辑不变）
2. 系统检查账号信息完整度：
   - 是否已设置 Grape 密码
   - 是否已绑定邮箱
3. 若信息不完整 → 在项目页顶部显示非阻断式补全引导
4. 用户可选择立即补全或跳过，跳过后引导消失，用户设置持续显示完整度状态

**补全引导设计：**

账号信息完整度分为三个等级：

| 完整度等级 | 判定条件 | 引导内容 |
|-----------|---------|---------|
| 不完整 | 无密码 且 无邮箱 | 引导设置密码 + 补填邮箱（优先级：密码 > 邮箱） |
| 部分完整 | 有密码 但 无邮箱，或 无密码 但 有邮箱 | 引导补全缺失项 |
| 完整 | 有密码 且 有邮箱 | 无引导 |

**引导展示位置：**

1. **项目页**：OAuth 首次登录后，在项目页顶部显示轻量提示条（非弹窗、非阻断）："为了账号安全，建议设置 Grape 密码和绑定邮箱"，带"去设置"按钮
2. **用户设置**：安全子页面中持续显示完整度状态和补全入口
3. **侧边栏**：不显示补全提示，保持干净

**引导规则：**

- 补全引导为非阻断式 — 用户可跳过，不影响正常使用系统
- 首次 OAuth 登录时在项目页显示补全提示条，用户跳过后记录状态，后续登录不再显示
- 用户设置始终显示完整度状态，与是否首次登录无关
- 用户完成全部补全后（有密码 + 有邮箱），引导完全消失
- 非首次 OAuth 登录不弹任何引导，直接进入上次工作页面
- OAuth 登录用户的行为流程与密码登录用户一致，不因登录方式不同而限制功能

**OAuth 用户的邮箱处理：**

- 若第三方平台返回了邮箱：自动写入账号邮箱，无需用户再次验证（需求 4 自动创建时写入）
- 若第三方平台未返回邮箱：邮箱留空，引导用户在用户设置补填（需求 13 首次设置邮箱流程）
- 补全引导为非阻断式，用户可跳过，不影响正常使用系统

**多平台绑定场景：**

- OAuth 登录用户已天然绑定一个平台，如需绑定另一个平台：在用户设置第三方账号子页面操作
- 绑定新平台后不影响已有仓库和工作流，仅扩展可用平台范围

**验收标准：**

- GitCode OAuth 首次登录后，项目页显示账号补全引导提示条
- 引导提示条包含"去设置"按钮，点击后跳转用户设置
- 用户跳过后引导条消失，记录状态，后续 OAuth 登录不再显示
- 非首次 OAuth 登录不弹任何引导，直接进入上次工作页面
- 用户设置始终显示完整度状态：无密码时显示"设置密码"，无邮箱时显示"设置邮箱"
- 设置密码后引导提示更新，邮箱补全后引导消失
- 平台返回邮箱时自动写入账号，无需用户验证
- 平台未返回邮箱时邮箱留空，用户可在用户设置补填
- OAuth 用户在用户设置可绑定另一个平台
- OAuth 用户体验与密码登录用户一致，功能不受限
- OAuth 非首次登录正确关联到已有 Grape 账号，不重复创建账号
- 密码注册用户后绑定 GitCode，OAuth 登录时关联到同一个 Grape 账号

### 需求 19：注册接口 IP 维度限流

**用户故事：** 作为系统管理者，我希望注册接口具备 IP 维度限流能力，以便防止攻击者用不同邮箱批量消耗验证码资源和邮件发送配额。

**业务背景：**

当前注册流程的限流仅在验证码层面：同一邮箱 60 秒内不可重复发送、10 分钟内最多 3 次。但攻击者可以切换不同邮箱绕过邮箱维度限流，用同一 IP 大量调用注册接口，消耗验证码生成资源和邮件发送配额。

**业务规则：**

- 同一 IP 10 分钟内最多请求 5 次注册验证码，超过后提示"请求过于频繁，请稍后再试"
- IP 限流与邮箱限流独立计算，不互相影响
- IP 限流触发后，即使更换邮箱也无法继续请求
- IP 限流计数与验证码 IP 限流计数共享（同一 IP 的验证码请求统一计数，包含注册、密码重置等场景）
- 管理员可配置 IP 限流阈值（本期固定值，不实现管理界面）

**验收标准：**

- 同一 IP 10 分钟内请求 5 次注册验证码后，第 6 次被拒绝，提示"请求过于频繁"
- IP 限流触发后更换邮箱仍被拒绝
- 不同 IP 互不影响
- 邮箱维度限流正常生效，与 IP 限流独立

### 需求 20：Token 续期校验账号状态

**用户故事：** 作为系统管理者，我希望用户在登录凭证续期时系统校验账号状态，以便被禁用或已注销的用户无法通过续期旧凭证继续访问系统。

**业务背景：**

需求 10 要求"被禁用用户的登录凭证在刷新时被拒绝"。但当前 token 续期（refresh_token 换新 access_token）只校验 token_version，不校验账号禁用状态。被禁用用户在 access_token 过期后，仍可通过 refresh_token 续期获取新的 access_token。

**业务规则：**

- token 续期时必须校验账号当前状态（正常/禁用/冷静期/已注销）
- 账号被禁用时，token 续期被拒绝，返回"账号已被禁用"，前端跳转登录页
- 账号处于冷静期或已注销时，token 续期被拒绝，返回"账号不可用"
- token_version 校验和状态校验同时进行，任一不通过即拒绝
- 续期时的状态校验使用鉴权中间件相同的内存缓存机制（TTL 5 秒），避免每次续期查库
- 账号禁用/恢复时主动失效缓存，确保续期校验实时生效

**验收标准：**

- 被禁用用户的 access_token 过期后，refresh_token 续期被拒绝
- 被禁用用户续期失败时返回"账号已被禁用"
- 处于冷静期的账号续期被拒绝
- 正常用户续期不受影响
- 禁用操作后 5 秒内续期校验生效

### 需求 22：账号注销冷静期管理

**用户故事：** 作为注销了账号的用户，我希望在 30 天冷静期内可以联系管理员恢复账号，以便在我改变主意时能够找回账号和数据。

**业务背景：**

需求 14 设计了 30 天冷静期机制：注销后进入冷静期，冷静期内管理员可恢复，冷静期结束后数据匿名化。但缺少冷静期到期处理的业务规则和管理员恢复的完整流程。

**业务规则：**

**冷静期内：**

- 账号状态为"冷静期"，不可登录
- 个人工作空间和第三方绑定关系保留
- 管理员可在管理后台恢复账号，恢复后状态设为正常
- 恢复时清除登录凭证（token_version +1），用户需重新登录
- 邮箱仍占用，不可用于注册新账号
- 恢复操作记录审计日志

**冷静期到期：**

- 冷静期到期后（30 天），系统自动将账号状态设为"已注销"
- 已注销状态的账号数据匿名化：用户名改为"已注销用户"，邮箱清空，密码哈希清空，昵称清空
- 第三方绑定关系清除
- 个人工作空间删除
- 邮箱释放，可被重新注册
- 匿名化操作记录审计日志

**管理员恢复流程：**

1. 管理员在管理后台查看处于冷静期的账号列表
2. 管理员选择恢复指定账号
3. 系统将账号状态恢复为正常
4. 清除登录凭证（token_version +1）
5. 通知用户账号已恢复（如有邮箱）
6. 记录审计日志

**验收标准：**

- 冷静期内账号不可登录
- 管理员可恢复冷静期内的账号，恢复后可正常登录
- 恢复后第三方绑定关系保留
- 冷静期到期后账号自动匿名化，邮箱释放
- 匿名化后该邮箱可被重新注册
- 匿名化后个人工作空间和数据已删除
- 恢复和匿名化操作均记录审计日志

### 需求 23：并发注册冲突处理

**用户故事：** 作为系统管理者，我希望系统正确处理并发注册场景，以便同一邮箱被多个请求同时注册时不会产生重复账号。

**业务背景：**

防枚举设计下，注册发送验证码阶段不检查邮箱是否已注册，统一返回"验证码已发送"。验证码验证通过后创建账号时才检查邮箱冲突。如果两个请求用同一邮箱同时通过验证码验证，可能产生并发冲突。

**业务规则：**

- 验证码验证通过后，创建账号时通过数据库唯一约束兜底
- 同一邮箱并发注册时，第一个请求创建成功，第二个请求因唯一约束冲突
- 唯一约束冲突时，返回明确的业务提示"该邮箱已注册，请直接登录或重置密码"，而非系统错误
- 同一用户名并发注册时，同理返回"用户名已被占用"
- 防枚举设计不受影响：验证码发送阶段仍统一返回"验证码已发送"

**验收标准：**

- 同一邮箱并发注册时，只有一个请求成功创建账号
- 失败的请求返回"该邮箱已注册，请直接登录或重置密码"，不返回系统错误
- 同一用户名并发注册时，失败请求返回"用户名已被占用"
- 防枚举设计不受影响

### 需求 24：未绑定状态返回引导提示条

**用户故事：** 作为尚未绑定平台的用户，我在未绑定状态下使用不依赖仓库的功能（Agent 运行时等）时，希望页面顶部有明确的提示告诉我还没绑定平台，并能方便地返回引导页完成绑定，以便我不会忘记这一前置步骤。

**业务背景：**

未绑定平台的用户可以使用部分不依赖仓库的功能（Agent 运行时、设备监控、仓库设置、组织管理）。用户在使用这些功能时需要一个明确的"返回完成绑定"入口，避免用户在不依赖仓库的功能中逗留后忘记绑定平台。

**业务流程：**

1. 用户从新手引导页进入不依赖仓库的功能（Agent 运行时、设备监控、仓库设置、组织管理）
2. 页面顶部显示轻量提示条"还未绑定代码托管平台，点击此处完成绑定"
3. 用户点击提示条返回新手引导页
4. 用户完成绑定后提示条消失

**业务规则：**

- 返回引导提示条仅在未绑定时显示，已绑定后不显示
- 提示条不阻断用户使用当前功能
- 提示条为轻量设计，不占用过多页面空间
- 未绑定时用户头像下拉菜单提供"用户设置"和"登出"入口

**验收标准：**

- 未绑定用户在不依赖仓库的功能页面中看到"返回完成绑定"提示条
- 点击提示条返回新手引导页
- 已绑定后提示条消失
- 未绑定时用户下拉菜单包含"用户设置"和"登出"
- 未绑定时无法进入场景·技能市场、知识库等依赖仓库的功能

### 需求 25：敏感操作反馈

**用户故事：** 作为已登录用户，我在用户设置完成修改密码、更换邮箱、绑定/解绑第三方等操作后，我希望系统给我明确的成功反馈和下一步指引，以便我确认操作生效。

**业务背景：**

当前账号体系的敏感操作（修改密码、邮箱变更、绑定/解绑第三方、注销账号）完成后，只有 API 返回成功，前端缺少明确的成功反馈和下一步指引。用户操作完成后不确定"改成功了吗？下一步该做什么？"。

**敏感操作反馈规则：**

| 操作 | 页面反馈 |
|------|---------|
| 修改密码 | 成功提示 + "其他设备已下线" |
| 邮箱变更 | 成功提示 + "旧邮箱已不可登录" |
| 绑定第三方 | 成功提示 + "可用该平台快捷登录" |
| 解绑第三方 | 成功提示 + "该平台登录已失效" |
| 设置密码 | 成功提示 + "可用密码登录" |
| 注销账号 | 成功提示 + "进入 30 天冷静期" |

**页面反馈设计：**

每个敏感操作完成后，在当前页面显示明确的成功反馈：
- 绿色成功提示条（toast），显示操作结果摘要
- 提示条下方显示"下一步"引导文案（如"其他设备已下线，当前设备保持登录"）
- 提示条 3 秒后自动消失，或用户点击关闭
- 操作完成后自动刷新当前子页面的数据（如解绑后刷新第三方账号列表）

**业务规则：**

- 所有敏感操作完成后必须显示页面成功反馈
- 提示条自动消失不影响页面其他操作
- 操作完成后当前子页面数据自动刷新

**验收标准：**

- 修改密码后显示绿色成功提示 + "其他设备已下线"
- 邮箱变更后显示成功提示 + "旧邮箱已不可登录"
- 绑定第三方后显示成功提示 + "可用该平台快捷登录"
- 解绑第三方后显示成功提示 + "该平台登录已失效"
- 注销账号后显示成功提示 + "进入 30 天冷静期"
- 操作完成后当前子页面数据自动刷新

## 4. 验证码场景汇总

为避免不同场景验证码混用，统一定义验证码场景：

| 场景 | 用途 | 有效期 | 限流 | 消费方式 |
|------|------|--------|------|---------|
| 注册 | 邮箱注册 | 10 分钟 | 60秒/3次(邮箱) 10次/10分钟(IP) | 验证通过后创建账号 |
| 重置密码 | 忘记密码 | 10 分钟 | 同上 | 验证通过后允许设置新密码 |
| 设置密码 | 设置密码（无密码用户） | 10 分钟 | 同上 | 验证通过后允许设置密码 |
| 变更邮箱 | 邮箱变更 / 首次设置邮箱 | 10 分钟 | 同上 | 验证通过后更换/绑定邮箱 |
| 解锁账号 | 账号解锁 | 10 分钟 | 同上 | 验证通过后清除锁定状态 |
| 注销账号 | 账号注销重认证 | 10 分钟 | 同上 | 验证通过后允许注销账号 |

所有场景验证码均遵循统一安全规则：6 位数字、使用后立即失效、按场景隔离、存储层不可用时拒绝验证（不降级）。

| 安全性 | 密码使用安全哈希算法加密存储，不存明文；登录凭证复用现有双 token 机制；OAuth 回调只信任服务端换取的用户信息；验证码使用常量时间比较防时序攻击；OAuth 强制 state + PKCE（标准平台）；第三方凭据加密存储；审计日志不可篡改 |

| 扩展性 | 标准 OAuth 2.0 平台配置即接入，不改代码；非标准平台通过适配器扩展，不改表结构；表结构始终保持稳定 |
| 向后兼容 | 现有用户凭据（AK/SK 等）保留不变；用户 ID 保持一致；迁移期间旧功能不受影响；老表保持不动，只读保留做回滚兜底 |
| 审计 | 认证相关事件全量审计，日志不可篡改，保留至少 180 天 |
| 性能 | 鉴权中间件校验禁用状态时使用内存缓存优化，缓存变更时主动失效，最长 5 秒延迟窗口；缓存不可用时降级查库 |

## 7. OAuth 授权弹窗模式（2026-10-13）

### 7.1 用户故事

作为 Grape 用户，我希望在绑定第三方平台（GitCode/GitHub）时不需要离开当前页面，在弹窗中完成 OAuth 授权后自动刷新绑定状态，不会丢失当前操作上下文。

作为 Grape 用户，我希望在登录时通过弹窗完成 OAuth 授权，授权完成后自动登录，不需要整页跳转后等待加载。

### 7.2 业务流程

1. 用户在账号设置页点击"授权绑定 GitCode/GitHub"按钮
2. 浏览器打开弹窗，展示第三方平台授权页
3. 用户在弹窗中完成授权（或取消授权）
4. 弹窗自动关闭，父窗口刷新绑定状态并显示结果
5. 如果绑定命中历史绑定（转移场景），父窗口展示转移确认弹窗

登录场景同理：用户在登录页点击 OAuth 登录按钮 → 弹窗授权 → 弹窗关闭 → 父窗口完成登录。

### 7.3 业务规则

- OAuth 授权在弹窗中完成，不离开当前页面
- 弹窗关闭后父窗口通过调用后端接口确认最终状态，不直接信任弹窗回传的成功信号
- 转移绑定票据（binding_ticket）不通过弹窗回传，留在服务端与用户会话绑定，父窗口用 JWT 从后端获取
- 弹窗被浏览器拦截时，自动降级为整页跳转（原有流程），用户体验不中断
- 弹窗中 window.opener 为 null 时（跨域重定向后浏览器清除 opener / 隐私模式等），中间页显示操作指引提示页，不跳转首页
- 弹窗打开后 120 秒未收到结果，提示用户超时重试
- 整页跳转模式（非弹窗）完全保留，向后兼容
- 首次绑定的平台不强制 prompt，用户可直接在已登录的第三方平台完成授权
- 登录场景使用全页重定向（不使用弹窗），保证兼容性和稳定性
- 绑定场景使用弹窗模式，保持用户在设置页的操作上下文
- 部分平台仓库拉取失败时，保留旧缓存中失败平台的仓库，不用不完整数据覆盖缓存
- 绑定成功后强制同步仓库列表（不走缓存），确保新平台仓库立即出现
- 会话隔离与绑定冲突处理（prompt=login 触发条件、占位账号定义与自动转移、后端冲突检测三层处理、转移票据安全）详见第 8 节（OAuth 会话隔离与绑定冲突处理）

### 7.4 验收标准

- 点击"授权绑定"按钮后弹出弹窗，当前页面不跳转
- 弹窗中完成授权后弹窗自动关闭，父窗口显示绑定成功
- 弹窗中取消授权后弹窗自动关闭，父窗口显示错误提示
- 绑定命中历史绑定时，弹窗关闭后父窗口展示转移确认弹窗
- 弹窗被拦截时自动降级为整页跳转，正常完成绑定
- 弹窗中 window.opener 为 null 时，弹窗显示操作指引提示页，用户可关闭弹窗

- 父窗口收到弹窗消息后调用后端接口确认最终状态
- 已绑定平台点击"重新授权"时，弹窗中要求用户重新登录第三方平台（prompt=login）

- 手动令牌绑定和转移绑定成功后与 OAuth 绑定行为一致（统一反馈+统一跳转）

## 8. OAuth 会话隔离与绑定冲突处理（2026-10-13）

### 8.1 用户故事

作为 Grape 用户，我在账号设置页点击"绑定 GitCode/GitHub"时，弹窗打开第三方平台授权页。如果浏览器里已经登录了 GitCode/GitHub，弹窗会直接复用已有会话跳过登录步骤，我无法选择切换到另一个账号。如果这个第三方账号已经被其他 Grape 账号绑定了，我会看到"已被绑定"的冲突提示，不知道该怎么办。

作为 Grape 用户，我希望系统能自动处理这种情况——已绑定时强制重新登录第三方平台让我选择正确账号，冲突时自动转移可安全转移的绑定或提示我确认转移。

### 8.2 业务流程

1. 用户在账号设置页点击"授权绑定"或"重新授权"按钮
2. 系统检测该平台是否已绑定：
   - 首次绑定：打开弹窗，不强制重新认证（用户可能已在第三方平台登录）
   - 已绑定重新授权：打开弹窗，附加 `prompt=login` 参数强制第三方平台重新认证
3. 弹窗中用户完成第三方平台登录/授权
4. 后端回调时检测第三方账号是否已被其他 Grape 账号绑定：
   - 无冲突：直接创建绑定，弹窗关闭，父窗口刷新绑定状态
   - 活跃绑定属于其他用户但对方是占位账号（系统自动创建的空账号）：自动转移绑定，不需要用户确认
   - 活跃绑定属于其他用户且对方不是占位账号：返回绑定冲突错误
   - 历史绑定（已解绑）属于其他用户：生成转移票据，父窗口展示转移确认弹窗，用户确认后转移
5. 弹窗关闭，父窗口通过后端接口确认最终状态

### 8.3 业务规则

- **prompt=login 触发条件**：仅在该平台已有绑定时（重新授权/换绑场景）附加 `prompt=login` 参数。首次绑定不附加——因为用户可能本来就需要登录第三方平台
- **prompt=login 的作用**：强制第三方平台不复用浏览器已有会话，要求用户重新输入账号密码。这是 OAuth 2.0 / OpenID Connect 标准参数
- **弹窗模式与全页跳转的场景区分**：
  - 绑定场景使用弹窗模式（用户已登录在设置页操作，保持上下文不丢失）
  - 登录场景使用全页重定向（兼容性最强，不受弹窗拦截/跨域 opener 丢失影响）
- **弹窗无法隔离会话**：弹窗与主页面共享浏览器 Cookie，弹窗模式本身不能解决"复用已有会话"问题，必须配合 `prompt=login`
- **后端冲突检测三层处理**：
  - 活跃绑定属于其他用户 + 对方是占位账号且无业务数据 → 自动转移（条件：无密码、无其他绑定、无业务数据）
  - 活跃绑定属于其他用户 + 对方是占位账号但有业务数据 → 生成转移票据，前端展示转移确认弹窗，用户确认后转移绑定+业务数据
  - 活跃绑定属于其他用户 + 对方不是占位账号 → 返回绑定冲突错误
  - 历史绑定（已解绑 status=0）属于其他用户 → 生成转移票据，前端展示转移确认弹窗，用户确认后转移
- **占位账号定义**：系统通过 OAuth 自动创建的空邮箱账号（`email_is_placeholder=1 + created_by_oauth=1`），无密码、无其他绑定、无业务数据
- **转移票据安全**：不通过弹窗 postMessage 传递，留在服务端与用户 JWT 绑定，父窗口用 JWT 从后端获取
- **弹窗被拦截时**：自动降级为整页跳转，已绑定时仍传 `prompt=login`
- **移动端**：直接全页跳转（移动端弹窗体验差），已绑定时仍传 `prompt=login`
- **业务表清单维护**：占位账号自动转移前检查 11 张业务表（user_repos/agent_tasks/chat_agent_session/chat_conversations/issue/user_feedback/user_credentials/api_tokens/session_api_tokens/scene_likes/skill_likes）。新增任何包含 user_id 列的业务表时，必须同步更新 `grape_account_db.py` 中 `_BUSINESS_TABLES` 清单和设计文档第 27.6 节，否则占位账号自动转移可能遗漏该表的数据检查导致数据丢失

### 8.4 验收标准

- 首次绑定某平台时，弹窗直接打开第三方授权页，不强制重新登录
- 已绑定平台点击"重新授权"时，弹窗中要求用户重新登录第三方平台（prompt=login 生效）
- 绑定的第三方账号已被其他用户的占位账号绑定时，如果占位账号无业务数据，自动转移成功，不需要用户确认
- 绑定的第三方账号已被其他用户的占位账号绑定时，如果占位账号有业务数据（托管仓库/任务/对话等），弹窗关闭后父窗口展示转移确认弹窗
- 转移确认通过后，绑定和业务数据从原账号转移到当前账号，原账号标记为 merged
- 绑定的第三方账号已被其他真实用户活跃绑定时，显示绑定冲突错误
- 绑定的第三方账号曾被其他用户绑定但已解绑时，弹窗关闭后父窗口展示转移确认弹窗
- 转移确认通过后，绑定从原账号转移到当前账号
- 弹窗被拦截时降级为整页跳转，已绑定时仍强制重新认证
- 移动端绑定时全页跳转，已绑定时仍强制重新认证

2. env 默认为 development
3. JWT 密钥：security.json 未配 → JWT_SECRET 环境变量未配 → 使用默认开发密钥
4. 凭据加密密钥：security.json 未配 → 从 JWT_SECRET 派生 → 仍为空 → 使用默认测试密钥
5. 安全门禁：只 warning 不阻断
6. 邮件服务：未配 → 固定验证码 / LOG_ONLY

**生产环境（创建 security.json，env=production）**：
1. 运维人员创建 configs/security.json，填入 env=production + JWT 密钥池 + 凭据加密密钥
2. 系统启动时读取 security.json
3. 安全门禁：JWT_SECRET 在黑名单 → 拒绝启动；邮件服务未配 → 拒绝启动
4. JWT 签发：使用 security.json 中的密钥池（kid 轮换）
5. 凭据加密：使用 security.json 中的 credential_keys

**密钥轮换流程**：
1. 在 security.json 的 jwt.secret_keys 中添加新密钥（新 kid）
2. 修改 jwt.kid_current 为新 kid
3. 重启服务（或热加载）
4. 旧密钥保留 30 天（仍在 secret_keys 中）用于验签旧 token
5. 30 天后从 secret_keys 中移除旧密钥

### 11.3 业务规则

- **配置优先级**：configs/security.json > 默认值（无文件即开发模式）
- **环境标识**：security.json 的 env 字段 > 默认 development
- **JWT 密钥**：security.json 的 jwt.secret_keys > JWT_SECRET 环境变量（仅此一个保留）> 默认开发密钥
- **凭据加密密钥**：security.json 的 credential_keys > 从 JWT_SECRET 派生 > 默认测试密钥
- **crypto.json 废弃**：原 configs/crypto.json 中的凭据密钥值迁入 security.json 的 credential_keys 字段，crypto.json 不再使用
- **环境变量废弃**：APP_ENV / JWT_SECRET_KEYS / JWT_KID_CURRENT / GRAPE_CREDENTIAL_KEYS 四个环境变量全部废弃，不再作为 fallback。安全配置只从 security.json 读取，无文件则用默认值
- **安全门禁**：生产环境（env=production）启动时检查 JWT_SECRET 安全性（黑名单 + 长度）、邮件服务配置；非生产环境只 warning 不阻断
- **热加载**：security.json 修改后支持热加载（不重启服务生效），用于密钥轮换场景
- **文件安全**：configs/security.json 加入 .gitignore，仓库内只提供 configs/security.example.json 模板

### 11.4 配置文件结构

configs/security.example.json（仓库内模板）：

```json

  "env": "development",
  "jwt": {
    "secret_keys": "",
    "kid_current": ""
  },
  "credential_keys": ""

```

### 11.5 验收标准

- 不创建 security.json 时系统正常启动，全部使用默认值，安全门禁只 warning
- 创建 security.json 且 env=production 时，安全门禁生效（JWT_SECRET 黑名单 → 拒绝启动）

## 附录A.1. OAuth 安全加固（2026-10-12）

### A.1.1 用户故事

作为 Grape 用户，我希望通过 GitCode/GitHub OAuth 登录时，我的账号不会被其他人通过同名用户名劫持，以便我的账号安全得到保障。

作为 Grape 用户，我希望已经登录后再点第三方登录按钮时，系统自动把第三方身份绑定到当前账号，而不是创建一个新账号，以便我不会意外产生重复账号。

作为 Grape 用户，我希望 OAuth 登录成功后我的访问令牌不会出现在浏览器地址栏里，以便令牌不会被日志或 Referer 泄露。

### A.1.2 业务流程

**OAuth 回调状态机（按顺序判断）：**

1. 查 external_identities(provider, external_id) → 已存在 → 直接登录对应 user_id
2. 未绑定 + 当前请求已登录（有效 JWT）→ 转绑定流程，绑定到当前账号
3. 未绑定 + 未登录 + 邮箱无冲突 → 静默自动创建新账号并登录
4. 未绑定 + 未登录 + 邮箱已存在 → 跳关联页，要求证明已有账号所有权
5. 未绑定 + 未登录 + 邮箱未验证/为空 → 创建受限账号（email_verified=0），登录后引导绑定邮箱

**核心原则：用户名同名绝不作为绑定依据；邮箱命中已有账号绝不静默登录。**

### A.1.3 业务规则

- 用户名同名不自动绑定（P0-1：账号劫持漏洞修复）
- /login/{provider} 检测已登录态，已登录时自动转绑定流程（P0-2）
- access_token 不通过 URL 传递，改用一次性 exchange code（10 秒过期，POST 交换）（P0-3）
- 第三方邮箱未验证时创建受限账号，标记 email_verified=0（P0-4）
- 邮箱验证码注册的账号 email_verified=1（邮箱已通过验证码验证）
- OAuth 端点 IP 限流：/login 10 次/分钟，/auth/exchange 30 次/分钟
- 自动创建账号时绑定失败回滚（软删除账号，不留孤立记录）
- OAuth 错误消息用错误码替代中文（前端 I18N 翻译）

### A.1.4 验收标准

- 同名账号不再自动绑定
- 未绑定 + 未登录 + 邮箱无冲突 → 静默自动创建并登录
- 未绑定 + 未登录 + 邮箱冲突 → 跳关联页，验证所有权后绑定
- 未绑定 + 已登录 → 绑定到当前账号，不创建新账号
- 已登录点第三方登录，不会覆盖当前登录态
- exchange_code 一次性、10 秒过期，前端 POST 换 JWT
- email_verified=0 创建受限账号，登录后弹窗提示绑定邮箱
- 所有绑定/创建行为有审计日志
- OAuth 端点有限流
- 已有用户登录不受影响（向后兼容）
