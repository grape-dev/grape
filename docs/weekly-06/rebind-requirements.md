# 重新绑定体验 — 需求文档

## 第12节：解绑后重新绑定体验

### 12.1 用户故事

作为用户，当我解绑了某个第三方平台后再次用该平台登录时，我希望系统自动恢复我之前的绑定，直接登录到原账号，不创建新账号，不丢失原有数据和仓库配置。

### 12.2 业务流程

用户通过 OAuth 登录时，系统按以下顺序判断：

1. 查活跃绑定 → 找到则直接登录
2. 查历史绑定（软删除记录）→ 找到且原账号有效则自动恢复绑定并登录
3. 无历史绑定 → 查邮箱冲突 → 邮箱被占用则跳关联页（验证所有权）
4. 邮箱无冲突 → 自动创建新账号

历史绑定优先于邮箱冲突判断。一旦命中历史绑定，不再走邮箱冲突逻辑。

### 12.3 自动恢复绑定流程

当检测到历史绑定且原账号状态正常时：

1. 系统自动恢复绑定（status 0→1），更新为最新 OAuth token
2. 签发 JWT，登录到原账号
3. 用户无感知，直接进入系统

原账号状态异常时不恢复：
- status=0（禁用）→ 提示"原账号已被禁用，请联系管理员"
- status=3（注销冷静期）→ 提示"原账号已注销，无法恢复"
- 账号不存在 → 提示"原账号不存在"

不提供"创建新账号"选项，避免产生重复账号。

### 12.4 业务规则

- 历史绑定记录保留 provider + external_id（明文），但 access_token 和 refresh_token 必须清空（解绑后不可用旧 token）
- 恢复绑定前必须检查原账号状态：
  - status=1（正常）→ 自动恢复
  - status=0（禁用）→ 拒绝恢复，提示"原账号已被禁用，请联系管理员"
  - status=3（注销冷静期）→ 拒绝恢复，提示"原账号已注销，无法恢复"
- 被封禁/注销的账号不可通过恢复绑定绕过限制
- 恢复绑定后记录审计日志：用户、provider、IP、时间
- 恢复绑定是原子操作：status 0→1 + 更新 token + 签发 JWT
- 第三方身份信息（external_id）来自 OAuth 回调，不可由前端传入
- external_id 明文存储（第三方平台公开标识，非机密凭据）
- placeholder 邮箱判断结合 email_source 字段，不仅靠域名硬编码
- 邮箱冲突检查忽略 placeholder 邮箱（noreply.gitcode.com / noreply.github.com），不参与冲突判断

### 12.5 关联页验证（邮箱冲突时跳关联页）

当 OAuth 登录命中邮箱冲突（用户用邮箱注册过 Grape 账号，现在用同一第三方平台 OAuth 登录）时：

- 不自动关联，不创建新账号
- 跳关联页，要求用户验证对已有账号的所有权
- 支持多种验证方式（任选其一）：
  - 密码验证：输入用户名/邮箱 + 密码
  - 邮箱验证码验证：输入邮箱 + 验证码（发送到该邮箱）
- 验证通过后检查目标账号状态：
  - status=1（正常）→ 绑定并登录
  - status=0（禁用）→ 拒绝，提示"账号已被禁用"
  - status=3（注销）→ 拒绝，提示"账号已注销"
- 防用户枚举：发送验证码时统一返回"验证码已发送"，不暴露邮箱是否已注册
- 关联页限流：复用 OAuth 登录限流
- 提供取消出口：取消 → 返回登录页，不创建、不绑定
- 不提供"创建新账号"选项

### 12.6 自动创建边界

| 场景 | 处理 |
|------|------|
| 邮箱已验证且非 placeholder | 创建完整账号 |
| 邮箱未验证或 placeholder | 创建受限账号（email_verified=0），引导后续绑定真实邮箱 |
| 无邮箱 | 创建账号，用 (provider, external_id) 登录 |

### 12.7 邮箱注册账号用 OAuth 登录

用户用邮箱注册了 Grape 账号（有密码），然后用同一第三方平台 OAuth 登录：
- 无活跃绑定、无历史绑定
- OAuth 返回的邮箱与已注册邮箱一致 → 跳关联页，要求输入 Grape 账号密码验证所有权
- OAuth 返回的是 placeholder 邮箱 → 不冲突，自动创建新账号
- 验证所有权后关联绑定，后续 OAuth 登录直接走活跃绑定

### 12.8 审计与限流

- 解绑、恢复绑定、创建账号均记录审计日志
- OAuth 登录、exchange code 均限流（复用现有 login_throttle）

### 12.9 验收标准

- 解绑后 external_identities 表中记录不删除，status 改为 0，access_token/refresh_token 清空
- 再次 OAuth 登录同一第三方账号时，自动恢复绑定并登录到原账号
- 恢复绑定后 status 改为 1，token 更新为最新 OAuth token
- 原账号被禁用或注销时，不恢复绑定并给出明确提示
- 解绑后该第三方账号的活跃绑定（status=1）仍受 UNIQUE 约束保护，不可被两个账号同时绑定
- 解绑后该第三方账号可被其他 Grape 账号通过转移绑定流程绑定（见第13节）
- 邮箱冲突检查忽略 placeholder 邮箱
- 邮箱注册账号用 OAuth 登录时，邮箱一致则跳关联页验证所有权，不自动关联
- 关联页支持密码和邮箱验证码两种验证方式
- 关联页发送验证码时统一返回"已发送"，不暴露邮箱是否已注册
- 关联验证通过后检查账号状态，封禁/注销不可登录
- 关联页提供取消出口
- placeholder 判断结合 email_source 字段
- 恢复绑定、解绑均记录审计日志
- 所有新增 UI 文案走 i18n，不允许硬编码中文

## 第13节：转移绑定 — 解绑账号绑给其他用户

### 13.1 用户故事

作为用户B，我已登录 Grape 账号，想绑定一个第三方平台账号（通过输入 token 或 OAuth 授权）。系统检测到该第三方账号曾绑定过另一个 Grape 账号（用户A，已解绑）。我希望系统明确告知我该账号有绑定历史，让我选择是否将其转移到当前账号，而非静默转移或直接拒绝。

### 13.2 业务流程

用户B通过 token 绑定或 OAuth 关联时，系统按以下顺序判断：

1. 查活跃绑定（status=1）→ 属于用户B → 直接更新 token
2. 查活跃绑定（status=1）→ 属于其他用户A → 拒绝，提示"已被其他账号绑定"
3. 查活跃绑定无结果 → 查历史绑定（status=0）
   - 历史绑定属于用户B → 直接恢复（复用 create_external_identity UPSERT）
   - 历史绑定属于其他用户A → 进入转移确认流程
4. 无历史绑定 → 正常创建新绑定

### 13.3 转移确认流程

当检测到历史绑定属于其他用户A时：

1. 系统生成一次性 binding_ticket（10分钟过期，绑定当前会话用户B）
2. 票据内含已验证的 provider、external_id、access_token、original_user_id
3. 前端展示转移确认页面：
   - 标题："绑定转移确认"
   - 提示："该{平台}账号曾绑定过其他 Grape 账号。是否将其转移到当前账号？"
   - 补充说明："转移后，原账号将无法使用该平台登录。如果原账号没有其他登录方式，转移将被拒绝。"
   - 按钮："确认转移" / "取消"
4. 用户B确认 → 调用转移 API，携带 binding_ticket
5. 系统校验票据 → 检查原账号A是否还有其他登录方式 → 原子转移 → 审计日志

### 13.4 安全规则

- binding_ticket 是一次性消费的（查+删），不可重放
- binding_ticket 绑定 initiating_user_id，攻击者无法用他人的票据
- binding_ticket 不暴露裸 external_id 给 API，前端只传票据
- 转移前必须检查原账号A是否有其他可用登录方式（密码或其他活跃 OAuth 绑定）
  - 有其他登录方式 → 允许转移
  - 无其他登录方式 → 拒绝，提示"原账号无其他登录方式，转移会导致账号无法访问，请联系客服"
- 转移是原子操作：旧绑定 status→0 + 清 token + 新绑定 INSERT，在同一事务内
- 转移后清理两个用户的 user_repos 缓存
- OAuth 登录的自动恢复（第12节）不受影响——转移确认只在主动绑定时触发

### 13.5 防枚举

- 转移确认页面提示文案不暴露原账号的具体信息（用户名、邮箱等）
- 只提示"曾绑定过其他 Grape 账号"

### 13.6 审计

转移绑定操作记录审计日志：
- 事件类型：transfer_bind
- 记录：操作者（用户B）、原账号（用户A）、provider、external_id、IP、时间

### 13.7 验收标准

- 用户B通过 token 绑定时，检测到历史绑定属于其他用户A → 返回 409 + binding_ticket + need_transfer=true
- 用户B通过 OAuth 绑定时，检测到历史绑定属于其他用户A → 重定向到前端展示转移确认页（URL 参数传递 binding_ticket）
- 用户B通过 OAuth 关联时，检测到历史绑定属于其他用户A → 返回 409 + binding_ticket + need_transfer=true
- 三种绑定路径（token / OAuth 绑定 / OAuth 关联）的转移确认逻辑一致
- 前端展示转移确认页面，用户可选择确认或取消
- 用户确认 → 转移成功，用户B获得该第三方账号绑定
- 原账号A无其他登录方式 → 转移被拒绝，提示联系客服
- 原账号A有密码或其他 OAuth → 转移成功，原账号A失去该平台绑定，但账号本身仍可用
- binding_ticket 不存储 access_token/refresh_token，避免凭据泄露
- binding_ticket 过期或 reused → 返回 410，要求重新操作
- binding_ticket 用户不匹配 → 返回 410（不暴露具体原因）
- 转移后原账号A的 external_identities 记录 status=0、token 清空，账号本身不受影响
- 转移后用户B的 external_identities 记录 status=1、access_token 留空（下次 OAuth 登录自动刷新）
- OAuth 登录自动恢复（第12节）不受影响
- 转移操作记录审计日志
- 所有新增 UI 文案走 i18n，不使用 isZh 硬编码判断

## 第14节：绑定/解绑交互体验统一

### 14.1 用户故事

作为用户，无论我从引导页还是设置页绑定第三方平台，我希望获得一致的交互体验：点击后有即时反馈、操作中有加载状态、成功后有明确的视觉确认。我不希望页面突然跳转或卡住无响应。

### 14.2 交互规范（Apple HIG）

| 阶段 | 感知延迟 | 要求 |
|------|----------|------|
| 点击按钮 | <100ms | 按钮 :active 缩放 scale(0.97)，即时视觉反馈 |
| 操作进行中 | 100ms-1s | 按钮内嵌微型 spinner + 文字变化，不禁用页面 |
| 模态框打开/关闭 | 0.2s | opacity + scale 渐入渐出，cubic-bezier 弹性 |
| Tab 切换 | 0.2s | opacity fade 过渡，非 display 硬切 |
| 成功反馈 | 0.5-0.6s | 弹窗内显示绿色勾 + 文案，再平滑关闭跳转 |
| 降低动效 | prefers-reduced-motion | 所有动画禁用 |

### 14.3 引导页与设置页统一

引导页的绑定按钮（`app.bindProvider`）复用设置页的绑定模态框（`_accountBindProvider`），两个入口提供完全一致的交互：

- OAuth 授权 + 手动输入令牌两种方式
- 按钮即时反馈 + spinner
- 转移确认弹窗（第13节）
- 成功内联绿色勾 + 延迟跳转
- 模态框渐入渐出动画

### 14.4 转移确认弹窗统一

转移确认弹窗使用 `_accountShowModal`（和绑定/解绑弹窗统一风格），不再手写 overlay：
- 标题 + 提示 + 补充说明 + 错误区域 + 取消/确认按钮
- 确认按钮内嵌 spinner
- 成功后弹窗内显示绿色勾 0.6s 再关闭跳转
- 失败时弹窗内显示错误文案，不关闭弹窗

### 14.5 验收标准

- 引导页和设置页点击绑定按钮后弹出相同的模态框
- 模态框提供 OAuth 授权和手动输入令牌两种方式
- 按钮点击后有 :active 缩放反馈
- 操作进行中按钮显示内嵌 spinner
- 模态框打开和关闭有 0.2s 渐入渐出动画
- Tab 切换有 0.2s opacity 过渡
- 绑定/转移成功后弹窗内显示绿色勾 0.5-0.6s 再跳转
- 转移确认弹窗和绑定弹窗风格统一
- 所有动画在 prefers-reduced-motion 时禁用
- 所有文案走 I18N.t()，不使用 isZh 硬编码判断
