# 跨域访问通道优化分析（服务接口 / lib 引用模式）

| 项 | 内容 |
| --- | --- |
| 版本 | v1.1（新增 lib 写通道） |
| 日期 | 2026-11-13 |
| 关联 | `docs/weekly-11/independent-rds-upgrade-plan.md`（主方案）、`cross-domain-disposition.csv`（70 表处置）、`cross-domain-write-channel.csv`（30 张跨域写表的通道分配） |
| 结论摘要 | 跨域问题的根因不是"通道选哪个"，而是**表归属与代码归属错位**；先修归属（30 表），剩余 30 张跨域写里 **16 张适合 lib 同步写**（带 outbox 兜底）、9 张走 outbox、4 张回归属域、1 张禁止（迁移账本）；剩余 7 张纯跨域读仍用服务接口即可 |

## 1. 问题重述

原方案的口径是「跨域读写全部走服务接口」，评审意见补充为「**或者走 lib 库引用模式**」。两种机制都能让进程读到别的域的数据，但代价完全不同：

| 维度 | 服务接口（GSB `/internal/*`） | lib 库引用（目标域 public 契约 + 自有 DSN） |
| --- | --- | --- |
| 调用形态 | HTTP 跨进程/跨机 | 进程内函数调用 → 目标库连接 → SQL |
| 写能力 | 通过目标域写端点（推荐） | 调目标域 public 写函数（v1.1 允许，受控） |
| 单次开销 | 1 RTT + JSON 序列化 + 鉴权中间件（内网约 0.5–2 ms） | 1 RTT（跨实例）或本地（同实例），无序列化（约 0.2–1 ms） |
| 多语句/ JOIN | 必须先在服务端做成聚合端点 | 可在调用方自由组合 SQL |
| 事务 | 单库事务在服务端内部；跨域无事务 | 单库事务可用；跨域同样无事务 |
| 边界强制 | 强（网络 + 鉴权 + 契约） | 弱（靠代码纪律 + DB 授权 + arch 守卫） |
| 审计/限流 | 天然集中（中间件、指标、trace） | 需自己埋点；慢 SQL 直接拖垮调用方进程 |
| 耦合 | 契约耦合（可版本化） | 代码耦合（lib 版本必须与调用方一起发布） |
| 运维 | 连接池在服务端，调用方无感 | 调用方要为目标域维护连接池（域数 × pool） |

**关键判断**：lib 的收益只体现在「高频 + 多语句/复杂 JOIN + payload 小」的组合上；一旦读路径做成**聚合端点**（一次请求一次返回），服务接口与 lib 的差距会缩到 1–2 ms 量级，而安全、审计、故障隔离的差距是数量级。

**这张表推翻了「通道优先」的假设**：

1. **60/70 张表存在跨域写**——这不是"该用 API 还是 lib"的问题，而是"这张表为什么会让别人写"的问题。写路径一旦不在归属域，任何通道都只是把越界合法化。
2. 跨域写的最大写方是 **api 层（191 处）** 和 **kernel（77 处）**：api 是历史上的"薄 Web 层直接写表"，kernel 是一堆共享工具函数（`repo_cleanup`、`featured_order`、`domain_read` 等）在替各域做数据维护。
3. 把归属修正之后，真正剩下的跨域读只有 **7 张表、10 处**——服务接口完全覆盖，lib 没有刚需场景。

## 4. 通道决策树（优化后的口径）

```
跨域访问请求
├─ 1. 是写吗？
│   ├─ 写路径能否搬进归属域（路由/服务本来就是该域的业务）？
│   │    └─ 能 → W1 域内直连：搬完就是域内写，不走任何通道
│   └─ 不能（跨域状态同步、级联、配额）→ 看是否"必须同步"：
│        ├─ 是（读己之写 / 并发正确性 / 用户即时反馈）且满足 10.2 五条 →
│        │     W2 lib 同步写（调目标域 public 写函数，本地先写 + outbox 兜底）
│        ├─ 否（日志/流水/派生/可延迟）→ W3 outbox + 补偿
│        └─ 账本类（grape_t_schema_migrations）→ X 禁止跨域（每域独立账本）
├─ 2. 是读吗？
│   ├─ 消费方是 insight（分析面）→ E 事件/宽表（不同步读运行库）
│   ├─ 消费方是 kernel → D 模块归位（kernel 不得持有域数据访问）
│   ├─ 高频（QPS ≥ 50）或单请求需要 ≥3 条 SQL / 跨表 JOIN，且 payload 小 →
│   │    → A lib 只读（**需满足 5.1 的四个前置条件**）
│   └─ 其余 → B 服务接口（聚合端点，一次一屏）
└─ 3. 读己之写（刚刚改完马上读）→ 回写方端点读（服务接口），不做双写
```

**硬规则（写进 arch 守卫）**

| 编号 | 规则 | 违反后果 |
| --- | --- | --- |
| H1 | 非归属域不得出现裸 `INSERT/UPDATE/DELETE <外域表>`；只能调目标域 public 写函数或 outbox | 直接红 |
| H2 | kernel 不得 import 任何 `domains/*`，也不得写域表 | R1 红 |
| H3 | lib 通道只能调 `domains/<d>/public/` 暴露的函数，禁止 import 域内部模块 | 新增 R8 守卫 |
| H4 | lib 读给只读账号（列级 `SELECT`）；lib 写给"插入/更新列级"账号（无 DELETE、无 DDL） | 授权审计 |
| H5 | 每个 public 读函数必须有行数上限与超时（默认 500 行 / 800 ms） | 代码评审 + 单测 |
| H6 | 跨域调用必须带 `trace_id`，指标区分 `channel=api / lib_read / lib_write / outbox` | 看板缺失即视为未接入 |
| H7 | 禁止在调用方未提交的事务内调 lib 写（跨库长事务） | 代码扫描 + 评审 |
| H8 | lib 写函数内禁止再调其他域的 lib 写（禁止扇出） | 代码扫描 |

## 5. lib 读通道：允许，但定位为"受控例外"

### 5.1 启用条件（四条全部满足才可用 lib）

1. **频次**：该读路径 QPS ≥ 50，或位于任务主循环内（每条任务都会调用）；
2. **形状**：单次请求需要 ≥3 条 SQL 或跨表 JOIN，且**无法**用一次聚合端点表达（例如动态维度组合、分页游标 + 计数 + 关联表拼装）；
3. **数据量**：单次返回 ≤ 500 行、payload ≤ 256 KB；
4. **位置**：调用方与目标库同地域内网（RTT ≤ 1 ms 量级）。

任一条不满足 → 走服务接口。

### 5.2 安全与治理约束

| 项 | 要求 |
| --- | --- |
| 账号 | 每个 (调用域 → 目标域) 一个**只读**账号：`GRANT SELECT (col1, col2, ...) ON <target_db>.<table> TO <lib_user>`；列级授权，禁止 `SELECT *` |
| 契约 | 只能调 `domains/<d>/public/__init__.py` 里显式导出的函数（`__all__`），函数签名与返回值即契约；版本变化遵循语义化版本 |
| 限额 | 函数级 `max_rows` / `timeout_ms` / `max_payload`；超限抛错而不是截断 |
| 熔断 | 调用方对每个 lib 目标维护失败率窗口（30s，阈值 20%）→ 熔断 30s，回退服务接口（若存在）或返回 503 |
| 审计 | 每次 lib 读记 `(caller_domain, target_domain, fn, rows, elapsed_ms, trace_id)` 到本地日志 + 指标 |
| 连接池 | 每进程最多 2 个 lib 目标（域只有 3 个，自身除外），pool_size ≤ 5；`innodb_read_only` 会话 |
| 禁止 | lib 内不得有 DDL、不得写、不得长事务（> 1s 拒绝）、不得 `SELECT *`、不得跨库 JOIN |

### 5.3 何时该把 lib 降级为接口

- 目标表结构频繁变化（lib 版本被迫与所有调用方同步发布）→ 改接口；
- 调用方数量 > 3（连接池 × 进程数爆炸）→ 改接口；
- 需要跨机调用（RTT > 2 ms 或跨地域）→ 改接口；
- 需要审计到字段级（合规要求）→ 改接口（中间件统一记录）。

## 7. 性能与容量测算（决定是否值得开 lib）

以"任务列表页需要 3 类数据（任务 20 条 + 引擎状态 + 事件计数）"为例：

| 方案 | RTT | 序列化 | 端到端（内网，P50） | 备注 |
| --- | --- | --- | --- | --- |
| 细粒度服务接口（3 次调用） | 3 | 3 | ~4–6 ms | N+1，最差 |
| 聚合端点（1 次调用） | 1 | 1 | ~1.5–2.5 ms | **推荐默认** |
| lib 只读（3 条 SQL，单连接） | 3 | 0 | ~1.5–3 ms | 与聚合端点持平，但省了端点开发 |
| lib 只读 + 预编译语句复用 | 3 | 0 | ~1–2 ms | 高频场景才体现优势 |

**要点**：lib 的优势来自"省掉 JSON + 复用连接"，而不是"省掉 RTT"。如果读路径本来就是 1 次聚合调用，两者差别在 1 ms 内，**不值得为此引入第二种凭据、第二种连接池、第二种故障模式**。

容量：若开 lib，每进程新增 ≤ 2 个连接池 × 5 连接 = 10 连接；两机四进程 → 目标库最多多 40 连接（占当前实例连接数的 5–10%）。这是可以接受的，但必须纳入 `max_connections` 预算。

## 9. 风险与对策（与通道相关）

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 归属重定引发回归 | 路由从 api 挪进 runtime，URL/鉴权/错误码可能变 | 保持对外 `/api/*` 契约不变（内部转发），只挪实现 |
| lib 变相成为"第二套直连" | 有人拿 lib 账号做 `SELECT *` 拼 SQL | 列级授权 + public 契约 + R8 守卫 + 季度授权审计 |
| 双通道并存导致口径不一 | 同一数据一处走 API 一处走 lib，缓存/超时策略不同 | 每个表**只允许一个通道**，在处置 CSV 里锁定 |
| 补偿与直读的时序 | outbox 尚未应用，读方已查到旧值 | 读方读 owner 端点（强一致）；不接受"读自己的补偿日志" |
| 连接池预算失控 | 多域 lib 连接叠加 | `GRAPE_LIB_TARGETS` 白名单 + 每进程 ≤ 2 目标 + `max_connections` 预留 15% |

## 10. lib 写模式：准入、编排与边界（v1.1 新增）

### 10.1 三种写通道

| 通道 | 语义 | 一致性 | 延迟 | 可靠性来源 |
| --- | --- | --- | --- | --- |
| **W1 域内直连** | 归属修正后，写路径与表同域 | 强（单库事务） | 最低 | 数据库本地事务 |
| **W2 lib 同步写** | 调目标域 `public` 写函数（目标库账号） | 强（目标域内原子） | 1 RTT（0.5–2 ms） | 失败即整体失败 + outbox 兜底 |
| **W3 outbox** | 本地写意图行 + 异步补偿 | 最终一致（秒级） | 最低（不阻塞） | 重试 + 死信 + 对账 |

**W2 的存在理由**：有些跨域写**必须同步**——并发正确性（租约抢占）、读己之写（刚绑定会话就要用）、用户交互即时反馈（改配置马上生效）。这类写用 outbox 会造成"用户点了没反应"，用 W1 又因为归属不改不了。

### 10.2 W2 准入门槛（五条全部满足才允许）

1. **单目标**：一次调用只写一个域（不允许一个函数里写两个域）；
2. **幂等**：目标写必须能重放（业务唯一键约束，或 `UPDATE ... WHERE status='old'` 条件更新）；
3. **必须同步**：读己之写、并发正确性、或用户可见的即时反馈，三者至少占一条；
4. **失败可整体化**：目标写失败时，调用方可以把自己的事务回滚（不做"我成功它失败"的静默容忍）；
5. **可控规模**：单次影响行数 ≤ 100、执行时间 ≤ 300 ms、调用方 ≤ 3 个域。

任一条不满足 → 走 W3 outbox。

### 10.3 事务编排（关键：默认「本地先写 + outbox 兜底」）

```
A 方案（默认，推荐）
  ① 本地事务：写业务行 + 写 grape_t_xwrite_log(status=pending)  → COMMIT
  ② 提交后同步调 lib 写：
       成功 → xwrite_log 置 applied
       失败/超时 → 保留 pending，交给补偿循环（30s 退避，5 次后死信）
  优点：不丢写、用户立即看到本地结果、失败自动兜底
  代价：目标域最多滞后 30s 才一致（补偿窗口）

B 方案（仅当"目标必须先变"且操作可逆）
  ① 先调 lib 写（如抢占租约）
  ② 成功 → 本地提交；本地失败 → 调 lib 反向操作释放
  禁止用于不可逆操作（扣减、发送、删除）

C 方案（纯 outbox）
  派生数据（日志、指标、流水），允许延迟，不在乎"点了马上有"
```

**硬禁令**：
- 禁止在调用方**尚未提交的事务内**调 lib 写——会形成跨库长事务与死锁（`H7`）；
- 禁止 lib 写函数内部再调其他域的 lib 写（扇出放大，`H8`）；
- 迁移账本 `grape_t_schema_migrations` 任何情况下不得跨域写（`X`）——每域独立账本。

### 10.4 失败矩阵

| 场景 | 数据结果 | 处理 |
| --- | --- | --- |
| 本地失败、目标未调用 | 无副作用 | 直接报错 |
| 本地成功、目标失败 | 本地新值 / 目标旧值 | A 方案：outbox 补偿；用户可见本地结果 |
| 本地成功、目标超时但实际成功 | 等价（幂等） | 幂等键保证重放安全 |
| 目标成功、本地回滚 | 目标脏写 | 只可能发生在 B 方案，需反向补偿 |
| 补偿重试 5 次仍失败 | 死信 | 告警 + 人工/对账脚本 |

### 10.5 安全模型（lib 写比只读更严）

| 项 | 要求 |
| --- | --- |
| 账号 | 每 (caller → target) 独立写账号：`GRANT INSERT, UPDATE (col...) ON <db>.<table>`；**不给 DELETE、不给 DDL**；删除类操作走目标域端点（可审计、可软删） |
| 接口面 | 只能调 `public` 里的写函数（函数内 SQL 固定，不接受调用方传表名/列名/SQL 片段） |
| 审计 | 目标域在**同一事务内**写审计行：`(caller_domain, fn, business_key, trace_id, before/after 摘要)`；缺审计行即视为函数未合规 |
| 限流 | 每 caller ≤ 50 写/秒、≤ 100 行/次；超限直接拒绝（不排队，避免雪崩） |
| 锁 | 写函数必须带主键/唯一键条件；禁止无 `WHERE` 的批量更新；`innodb_lock_wait_timeout` ≤ 3s |
| 顺序 | 两域互相写时按固定顺序（domain 字典序）避免环状死锁；超时后最多重试 1 次（仅幂等操作） |

### 10.6 幂等实现清单

| 手法 | 适用 | 例子 |
| --- | --- | --- |
| 业务唯一键 + `INSERT ... ON DUPLICATE KEY UPDATE` | 有自然唯一键 | 渠道去重表（`(channel, msg_id)`） |
| 条件更新 `WHERE status='pending'` | 状态机流转 | 租约抢占、任务状态 |
| 幂等表（`grape_t_xwrite_log` 同库） | 无自然唯一键 | 日志类写入（键 = hash(payload)） |
| 版本号（`WHERE version < ?`） | 并发覆盖 | 配置项更新 |

### 10.7 观测与验收

| 编号 | 判据 | 采集 |
| --- | --- | --- |
| A13 | 100% 的 lib 写函数具备幂等实现（唯一键或条件更新） | 代码评审清单 + 重放测试 |
| A14 | lib 写失败后 100% 存在对应 outbox pending 行 | `xwrite_log` 与失败日志对账 |

### 10.9 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 爆炸半径扩大 | 调用方持有目标域**写**凭据，一个 bug 可污染别的域 | 列级授权 + 函数化（无裸 SQL）+ 目标域审计 + 季度权限复核 |
| 跨域死锁 | A 域事务等 B 域行锁，B 域反向等待 | 固定加锁顺序、单次 ≤300ms、超时即失败不走重试风暴 |
| 补偿滞后可见 | A 方案下目标域最多滞后 30s | UI 以本地域为准；跨域读一律走 owner 端点（强一致） |
| 幂等实现偷懒 | 直接 `INSERT` 导致重放双写 | 写函数模板 + 评审清单 + 重放测试（A13） |
| lib 写被滥用为"直连" | 有人绕过 public 函数拼 SQL | R8 守卫（禁止 import 域内部模块）+ 写账号只授列级 + 代码扫描 `cursor.execute` 在 lib 调用路径 |

## 11. 结论

1. **归属仍是第一优先**：60/70 张表的跨域写在告诉我们"归属错了"，先把 api 的直写路径挪进归属域、把 kernel 的数据维护模块归位（30 张表，覆盖 786 处跨域读中的大部分），跨域面会从 2691 处降到个位数。
2. **跨域写按三种语义分流**（30 张）：4 张回归属域（W1）、**16 张走 lib 同步写（W2，本地先写 + outbox 兜底）**、9 张走 outbox（W3，派生数据）、1 张禁止（X，迁移账本）。判断依据不是"哪条通道更先进"，而是**是否必须同步**（读己之写 / 并发正确性 / 用户即时反馈）。
3. **lib 写不是"直连"，是"目标域的写函数"**：调用方不写 SQL，只调 `public` 里语义化的函数（如 `claim_channel_lease()`、`bind_chat_session()`）；目标域用列级授权的写账号 + 同事务审计行兜住边界；删除类操作仍走目标域端点（可软删、可审计）。
4. **服务接口仍是默认读通道**，用聚合端点消除 N+1。lib 只读继续作为受控例外：当前 7 张纯跨域读表没有一张满足启用条件（QPS ≥ 50 + 多语句/JOIN + 小 payload + 同地域），所以第一阶段不开。
5. **每张表只允许一个通道**（在处置 CSV 里锁定），避免同一数据出现两套缓存/超时/审计口径。
6. **验收要多两条**：A13（lib 写 100% 幂等）与 A14（写失败必有 outbox pending 兜底）——这两条是"允许 lib 写"的唯一安全阀。
