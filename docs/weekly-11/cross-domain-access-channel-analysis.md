# 跨域访问通道优化分析（服务接口 / lib 引用模式）

| 项 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 日期 | 2026-11-13 |
| 关联 | `docs/weekly-11/independent-rds-upgrade-plan.md`（主方案）、`cross-domain-disposition.csv`（70 表处置） |
| 结论摘要 | 跨域问题的根因不是"通道选哪个"，而是**表归属与代码归属错位**；先修归属，剩余跨域面只有 7 张表 10 处引用，服务接口足够覆盖，lib 模式定位为**受控例外通道** |

---

## 1. 问题重述

原方案的口径是「跨域读写全部走服务接口」，评审意见补充为「**或者走 lib 库引用模式**」。两种机制都能让进程读到别的域的数据，但代价完全不同：

| 维度 | 服务接口（GSB `/internal/*`） | lib 库引用（目标域 public 契约 + 自有 DSN） |
| --- | --- | --- |
| 调用形态 | HTTP 跨进程/跨机 | 进程内函数调用 → 目标库连接 → SQL |
| 单次开销 | 1 RTT + JSON 序列化 + 鉴权中间件（内网约 0.5–2 ms） | 1 RTT（跨实例）或本地（同实例），无序列化（约 0.2–1 ms） |
| 多语句/ JOIN | 必须先在服务端做成聚合端点 | 可在调用方自由组合 SQL |
| 事务 | 单库事务在服务端内部；跨域无事务 | 单库事务可用；跨域同样无事务 |
| 边界强制 | 强（网络 + 鉴权 + 契约） | 弱（靠代码纪律 + DB 授权 + arch 守卫） |
| 审计/限流 | 天然集中（中间件、指标、trace） | 需自己埋点；慢 SQL 直接拖垮调用方进程 |
| 耦合 | 契约耦合（可版本化） | 代码耦合（lib 版本必须与调用方一起发布） |
| 运维 | 连接池在服务端，调用方无感 | 调用方要为目标域维护连接池（域数 × pool） |

**关键判断**：lib 的收益只体现在「高频 + 多语句/复杂 JOIN + payload 小」的组合上；一旦读路径做成**聚合端点**（一次请求一次返回），服务接口与 lib 的差距会缩到 1–2 ms 量级，而安全、审计、故障隔离的差距是数量级。

## 2. 先看数据：跨域面到底有多大、卡在哪

基于现网实测（`independent-rds-foreign-table-matrix.csv` + `cross-domain-disposition.csv`）：

| 指标 | 数值 |
| --- | --- |
| 跨域视图 | 182 个（覆盖 91 张表） |
| 代码仍有外域引用的表 | **70** 张，合计 2691 处 SQL 引用 |
| 其中**跨域读**（`FROM/JOIN`） | 796 处 / 65 张表 |
| 其中**跨域写**（`INSERT/UPDATE/DELETE`） | **390 处 / 60 张表** |
| 跨域写按写方 | api 191 / kernel 77 / mgmt 70 / runtime 51 / insight 1 |
| 跨域读按读方 | api 320 / mgmt 159 / runtime 118 / insight 100 / kernel 98 / contracts 1 |
| **只有跨域读、没有跨域写**的表 | **7 张 / 10 处引用**（全部 < 10 处） |

**这张表推翻了「通道优先」的假设**：

1. **60/70 张表存在跨域写**——这不是"该用 API 还是 lib"的问题，而是"这张表为什么会让别人写"的问题。写路径一旦不在归属域，任何通道都只是把越界合法化。
2. 跨域写的最大写方是 **api 层（191 处）** 和 **kernel（77 处）**：api 是历史上的"薄 Web 层直接写表"，kernel 是一堆共享工具函数（`repo_cleanup`、`featured_order`、`domain_read` 等）在替各域做数据维护。
3. 把归属修正之后，真正剩下的跨域读只有 **7 张表、10 处**——服务接口完全覆盖，lib 没有刚需场景。

## 4. 通道决策树（优化后的口径）

```
跨域访问请求
├─ 1. 是写吗？
│   ├─ 写路径能否搬进归属域（路由/服务本来就是该域的业务）？
│   │    ├─ 能 → D/C1 归属重定：搬完就是域内写，不走任何通道
│   │    └─ 不能（跨域状态同步、级联、配额）→ C2 outbox + 补偿（唯一允许的跨域写）
│   └─ lib 直写：**禁止**（写必须可重放、可审计、可对账）
├─ 2. 是读吗？
│   ├─ 消费方是 insight（分析面）→ E 事件/宽表（不同步读运行库）
│   ├─ 消费方是 kernel → D 模块归位（kernel 不得持有域数据访问）
│   ├─ 高频（QPS ≥ 50）或单请求需要 ≥3 条 SQL / 跨表 JOIN，且 payload 小 →
│   │    → A lib 只读（**需满足 5.1 的四个前置条件**）
│   └─ 其余 → B 服务接口（聚合端点，一次一屏）
└─ 3. 读己之写（刚刚改完马上读）→ 回写方端点读（服务接口），不做双写
```

**硬规则（写进 arch 守卫）**

| 编号 | 规则 | 违反后果 |
| --- | --- | --- |
| H1 | 非归属域不得出现 `INSERT/UPDATE/DELETE <外域表>` | 直接红（除非登记 outbox 动作） |
| H2 | kernel 不得 import 任何 `domains/*`，也不得写域表 | R1 红 |
| H3 | lib 通道只能调 `domains/<d>/public/` 暴露的函数，禁止 import 域内部模块 | 新增 R8 守卫 |
| H4 | lib 通道只给**只读**账号（`SELECT`，列级授权），写一律 outbox | 授权审计 |
| H5 | 每个 public 读函数必须有行数上限与超时（默认 500 行 / 800 ms） | 代码评审 + 单测 |
| H6 | 跨域调用必须带 `trace_id`，并在指标里区分 `channel=api / lib / outbox` | 看板缺失即视为未接入 |

## 5. lib 通道：允许，但定位为"受控例外"

### 5.1 启用条件（四条全部满足才可用 lib）

1. **频次**：该读路径 QPS ≥ 50，或位于任务主循环内（每条任务都会调用）；
2. **形状**：单次请求需要 ≥3 条 SQL 或跨表 JOIN，且**无法**用一次聚合端点表达（例如动态维度组合、分页游标 + 计数 + 关联表拼装）；
3. **数据量**：单次返回 ≤ 500 行、payload ≤ 256 KB；
4. **位置**：调用方与目标库同地域内网（RTT ≤ 1 ms 量级）。

任一条不满足 → 走服务接口。

### 5.2 安全与治理约束

| 项 | 要求 |
| --- | --- |
| 账号 | 每个 (调用域 → 目标域) 一个**只读**账号：`GRANT SELECT (col1, col2, ...) ON <target_db>.<table> TO <lib_user>`；列级授权，禁止 `SELECT *` |
| 契约 | 只能调 `domains/<d>/public/__init__.py` 里显式导出的函数（`__all__`），函数签名与返回值即契约；版本变化遵循语义化版本 |
| 限额 | 函数级 `max_rows` / `timeout_ms` / `max_payload`；超限抛错而不是截断 |
| 熔断 | 调用方对每个 lib 目标维护失败率窗口（30s，阈值 20%）→ 熔断 30s，回退服务接口（若存在）或返回 503 |
| 审计 | 每次 lib 读记 `(caller_domain, target_domain, fn, rows, elapsed_ms, trace_id)` 到本地日志 + 指标 |
| 连接池 | 每进程最多 2 个 lib 目标（域只有 3 个，自身除外），pool_size ≤ 5；`innodb_read_only` 会话 |
| 禁止 | lib 内不得有 DDL、不得写、不得长事务（> 1s 拒绝）、不得 `SELECT *`、不得跨库 JOIN |

### 5.3 何时该把 lib 降级为接口

- 目标表结构频繁变化（lib 版本被迫与所有调用方同步发布）→ 改接口；
- 调用方数量 > 3（连接池 × 进程数爆炸）→ 改接口；
- 需要跨机调用（RTT > 2 ms 或跨地域）→ 改接口；
- 需要审计到字段级（合规要求）→ 改接口（中间件统一记录）。

## 7. 性能与容量测算（决定是否值得开 lib）

以"任务列表页需要 3 类数据（任务 20 条 + 引擎状态 + 事件计数）"为例：

| 方案 | RTT | 序列化 | 端到端（内网，P50） | 备注 |
| --- | --- | --- | --- | --- |
| 细粒度服务接口（3 次调用） | 3 | 3 | ~4–6 ms | N+1，最差 |
| 聚合端点（1 次调用） | 1 | 1 | ~1.5–2.5 ms | **推荐默认** |
| lib 只读（3 条 SQL，单连接） | 3 | 0 | ~1.5–3 ms | 与聚合端点持平，但省了端点开发 |
| lib 只读 + 预编译语句复用 | 3 | 0 | ~1–2 ms | 高频场景才体现优势 |

**要点**：lib 的优势来自"省掉 JSON + 复用连接"，而不是"省掉 RTT"。如果读路径本来就是 1 次聚合调用，两者差别在 1 ms 内，**不值得为此引入第二种凭据、第二种连接池、第二种故障模式**。

容量：若开 lib，每进程新增 ≤ 2 个连接池 × 5 连接 = 10 连接；两机四进程 → 目标库最多多 40 连接（占当前实例连接数的 5–10%）。这是可以接受的，但必须纳入 `max_connections` 预算。

## 8. 对主方案的修订

| 章节 | 原口径 | 修订后 |
| --- | --- | --- |
| 3.3 跨域访问只允许两条路 | 服务接口 + 事件 | **域内直连（首选，靠归属重定达成）/ 服务接口（默认只读通道）/ lib 只读（受控例外，满足 5.1 四条）/ outbox（唯一跨域写）** |
| 4 设计决策 D2 | 禁止 lib 模式 | **允许 lib，但只读 + 列级授权 + public 契约 + 限额熔断；写一律 outbox**；`GRAPE_DOMAIN_LIB` 由"全局开关"改为"按目标域的白名单"（`GRAPE_LIB_TARGETS=runtime,mgmt`） |
| 5 依赖矩阵 | 按"域 → 域"汇总 | 增加**处置分类**（D/C1/C2/B/E/A），施工按处置而非按域排期 |
| 6 接口补齐 | 13 个端点 | 端点数量不变，但优先级重排：C1 涉及的路由搬迁优先，端点其次 |
| 9 分阶段 | P1 只读接口 → P2 写 | **P1 归属重定 + 模块归位（30 表，最大收益）→ P2 outbox（30 表）→ P3 剩余读接口化（7 表）→ P4 实例搬迁 → P5 收敛** |
| 10 验收 | 额外增加 | A11：lib 通道调用必须 100% 有 `channel=lib` 指标与审计记录；A12：不存在"lib 直写"（静态扫描 + DB 授权双重验证） |

### 工期变化

| 阶段 | 原估算 | 修订估算 | 原因 |
| --- | --- | --- | --- |
| P1 | 3–4 周（只读接口） | **3 周（归属重定 + 模块归位）** | 收益更大：30 张表的跨域读写一次性变域内 |
| P2 | 2–3 周（写 outbox） | **2–3 周（outbox 30 表）** | 范围收敛（C2） |
| P3 | — | **1–2 周（7 表接口化）** | 新增，但很小 |
| 合计 | 9–11 周 | **9–10 周** | 风险前移：早期解决归属问题，后期只剩收敛 |

## 9. 风险与对策（与通道相关）

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 归属重定引发回归 | 路由从 api 挪进 runtime，URL/鉴权/错误码可能变 | 保持对外 `/api/*` 契约不变（内部转发），只挪实现 |
| lib 变相成为"第二套直连" | 有人拿 lib 账号做 `SELECT *` 拼 SQL | 列级授权 + public 契约 + R8 守卫 + 季度授权审计 |
| 双通道并存导致口径不一 | 同一数据一处走 API 一处走 lib，缓存/超时策略不同 | 每个表**只允许一个通道**，在处置 CSV 里锁定 |
| 补偿与直读的时序 | outbox 尚未应用，读方已查到旧值 | 读方读 owner 端点（强一致）；不接受"读自己的补偿日志" |
| 连接池预算失控 | 多域 lib 连接叠加 | `GRAPE_LIB_TARGETS` 白名单 + 每进程 ≤ 2 目标 + `max_connections` 预留 15% |

## 10. 结论

1. **通道选择不是主要矛盾**：60/70 张表的跨域写在告诉我们"归属错了"，先把 api 的直写路径挪进归属域、把 kernel 的数据维护模块归位（30 张表），跨域面会从 2691 处降到个位数。
2. **服务接口作为默认读通道**，用聚合端点消除 N+1；这是唯一能同时满足安全、审计、故障隔离和独立实例演进的方案。
3. **lib 保留为受控例外**：只读、列级授权、public 契约、限额与熔断、每表只允许一个通道。当前 7 张纯跨域读表没有一张满足启用条件——所以第一阶段不要开 lib，把开关与守卫先建好，等真实高频路径出现再启用。
4. **跨域写只有 outbox 一条路**，lib 与接口都不允许直写。
