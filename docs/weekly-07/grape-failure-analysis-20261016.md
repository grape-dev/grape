## 三、逐类分析与设计

### A+B 派发层判死家族（44 条，66.7%，本次最大头）

**出错的逻辑**：两条路径。A：`src/api/event_pipeline.py:1886-1890`——webhook 收到事件后按 scene+agent_type 绑定引擎，绑定集为空/全离线时直接 `_fail_event`，不入队；SRE 场景绑定的引擎自 00:34 起大面积离线，全天产生 29 条失败（devkit-test、skill-registry、gallery、open-mcp 等仓库的 tag/release/PR 事件持续踩中）。B：`src/runtime/service.py` 的 pool 派发路径——引擎不可达或健康分不足等待 120s 未恢复即判死（Issue #253 口径），15 条。service.py 有 pool 兜底但 scene 绑定路径不覆盖（已知缺口）。

**修正后的逻辑**：① 派发层增加「延迟入队 + 重试」而非立即 fail：引擎全离线时事件转 `queued`，按退避（如 5/15/60min）重试派发，超过 N 小时才 fail；② scene 绑定路径复用 pool 兜底：绑定集全离线时回退到带对应标签的 pool 引擎；③ 对 SRE 离线潮增加告警（连续 M 条 A 类失败即通知值班），本次 29 条从早持续到晚无人干预。

**影响面评估**：event_pipeline.py/webhook.py 是主服务入口，双主需同步发版；queued 重试需要新的状态机分支，注意 events.status 枚举兼容（老前端可能不显示 queued）；重试会产生事件重复消费风险，需幂等（按 seq+agent_type 去重）。改动中等，但修好即清零 44 条/天。

**测试用例设计**：
1. 模拟 scene 绑定引擎全部离线 + pool 有同标签引擎 → 期望回退 pool 派发成功，事件不 failed。
2. 模拟全离线 → 期望事件转 queued，5min 后引擎恢复自动派发成功。
3. 模拟持续离线超过上限（如 2h）→ 期望最终 failed 且 result 提示引擎离线时长。
4. 重试幂等：同一 seq 重试 3 次仅产生 1 条 agent_task。
5. 老前端兼容：queued 状态事件在 dashboard/列表接口不报错。

### C+D+E 超时家族（18 条，27.3%）

**出错的逻辑**：三个子类同根——长任务耗时超过上限。C：`src/runtime/agent.py:2128` 外层 `RUNTIME_TASK_TIMEOUT`（3600s，部分场景 1200s）到期主动 fail（5 条，含 13103：任务实际已产出结论 JSON 却在回复阶段超时，属「临门一脚超时」）；D：`src/agent/executor.py` 静默窗口 SIGTERM 后 grace tail 有半截文本（7 条，多为 grape-dev/grape 自身的 coding/qa 长审查任务）；E：-9 无收尾输出（6 条，VOD-Project、open-capability-home 的 vod 长任务）。

**修正后的逻辑**：① tool_use 阶段（长 bash/git/测试）放大静默窗口或检测进程组 CPU/IO 活性，避免「命令在跑但 stdout 静默」被误杀；② 13103 类「工作已完成、只差回报」的任务：executor 检测到已有结构化结论时优先把结论写回再退出，不判 fail；③ 按任务类型分级 timeout（coding 3600s、sre 部署 1200s 已分化的基础上，允许 skill 声明 expected_duration 覆盖默认值）。

**影响面评估**：executor.py/agent.py 均为 worker 端核心，13 台内部 worker（114-126）需批量升级（scp 分发 + 重启，低峰执行）；双主副本需 scp 同步；timeout 分级改动只影响派发参数，风险小。

**测试用例设计**：
1. bash sleep 超过 `_silent_window×3`（进程活着）→ 不被 kill，任务正常完成。
2. 真挂死进程 → `_silent_window` 后 SIGTERM/SIGKILL，exit=-9 且 result 含 stderr 尾部。
3. 模拟「结论已生成 + 回复阶段超时」→ 任务记 completed，结论落库。
4. skill 声明 expected_duration=7200 → 外层 timeout 取 7200 而非默认 3600。

### F 手动终止误记 failed（1 条，口径问题）

**出错的逻辑**：`src/api/routes/events.py:344-351` 手动终止路径将 event 写为 failed（result='用户手动终止'）；而 `src/api/routes/runtime.py:809` 同语义操作写 cancelled。两条路径口径不一致，12861 应属 cancelled。

**修正后的逻辑**：events.py 终止路径统一写 cancelled，统计口径即刻对齐。

**影响面评估**：单文件小改动，仅影响手动终止的展示口径，无兼容风险。

**测试用例设计**：
1. 运行中任务手动终止 → event/task 均为 cancelled，result='用户手动终止'。
2. 统计接口：cancelled 不计入失败率。

### G 引擎环境/上游配额（3 条）

**出错的逻辑**：12837——单台 worker 的 `opencode not found`（引擎二进制丢失，环境损坏，exit=-1）；13051/13072——上游 tokenhub `429 Too Many Requests` / `Token日限额超限（已用 50007146 / 限额 50000000）`，日配额打满后所有依赖该上游的 sre 部署任务连环失败。

**修正后的逻辑**：① 上游配额类错误（429/日限额）识别为可重试/可路由错误：切换备用模型端点或延迟到次日自动重试，而非直接 fail；② worker 引擎健康检查纳入「二进制存在性」探测，opencode 丢失时自动从镜像恢复；③ 配额使用量接近限额（如 95%）时提前告警。

**影响面评估**：429 识别改动在 agent/executor 的错误分类层，小；配额告警需接入监控，中等。

**测试用例设计**：
1. mock 上游 429 → 任务进入延迟重试而非 failed。
2. worker 删除 opencode 二进制 → 健康检查报 unhealthy 并触发恢复。
3. 配额用到 95% → 触发告警通知。

## 四、优先级排序

1. **A+B 派发层延迟入队 + pool 回退**（修好即清零 44 条/天，改动中等，最高收益）
2. **F 手动终止口径统一**（行级改动，即刻修复）
3. **G-上游 429 可重试识别**（止血当日配额打满的连环失败）
4. **C+D+E 超时家族**（worker 端批量升级成本高，需排期低峰执行）
