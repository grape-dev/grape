# 观测云二次深度调研（2026-10-17）——能力矩阵、差距与规划输入

> 目的：第一次调研（见主设计文档 §10）只做了"开源边界 + 大方向取舍"。本次**逐模块深挖观测云的能力结构**，

> 1. 我们（grape 内建可观测性）现在**还缺什么**？

> 3. 下一阶段该做什么、不做什么？

> 结论用于修订 `observability-redesign-design.md`（§10.5 差距表、§11 实施路线）。

### 1.1 三处值得单独记下的设计细节

**① 告警治理是三层，不是一层**
```
检测层  规则检测（阈值/突变/区间） + 智能检测（历史周期与趋势基线）
告警层  告警策略：事件级别（Critical/Severe/Important/Warning/Data Gap/Info）
        通知对象、通知时区、自定义通知时段
        告警升级（同级别短时间多次 → 自动升级为紧急并换人）
        重复告警抑制（同事件 N 分钟内只记录不重复通知）
        聚合模式（不聚合/按规则/智能/AI）+ 聚合周期
治理层  静默规则（按规则/告警策略/标签/自定义 + 高级过滤 attribute:value
        + 生效范围"是否也静默事故"）
        SLO / 错误预算
```
**② SLO 的扣减口径**：以固定周期检测，异常事件的**覆盖时长**按实际起止合并（重叠只算一次）从
容忍时长里扣除；剩余即错误预算。SLI 可以基于监控器指标定义（成功率、时延）。
**③ 事件中心只聚合不产生**，每条事件带来源标记（`df_source`）与
`df_issue_start_time / df_issue_duration`（本轮故障首次发生时间与持续时长）——**同一异常反复触发时，
"首次发生"与"已持续多久"是比"当前值"更有用的信息**。

### 1.2 开源边界（复核，与一次调研一致）

| 开源（MIT 等） | 闭源 |
|---|---|
| `datakit`（采集器，305★，MIT）、端侧 SDK、`pipeline-go`（数据处理管道）、`scheck`（拨测）、AI OTel 插件 | 平台后端、控制台、GuanceDB、DQL、智能检测/巡检算法、Obsy AI |

结论不变：**"采集端开源 + 平台闭源变现"**。我们是自建产品，全套自研，不引入其组件。

## 二、行业标准的两个新信号（本次调研新增）

| 标准 | 状态 | 对我们的意义 |
|---|---|---|
| **OTel GenAI 语义约定**（`gen_ai.*`：`gen_ai.request.model` / `gen_ai.usage.input_tokens|output_tokens` / `gen_ai.token.type`（含 cache）/ `gen_ai.client.operation.duration`） | **Development**（未稳定，已迁到独立仓库 `semantic-conventions-genai`） | 我们已有 `obs_llm_usage`（input/output/cache_read/cache_write/reasoning + model_key）——**语义已对齐**，字段命名未对齐。稳定前**不追**，但保留映射层（导出时改字段名即可） |
| **OTel CI/CD 语义约定**（`cicd.pipeline.run.*`、`cicd.pipeline.task.run.*`、VCS 资源属性；metrics 侧 `cicd.pipeline.run.duration` / `.active`） | **spans = Release Candidate，metrics = Mixed**（比 GenAI 成熟） | 我们是**编排平台**：issue → 任务流水线 → PR 合并，天然就是 CI/CD 语义。对齐它能让我们既"说行业语言"，又拿到通用平台拿不到的语义（它们不知道 issue/stage 的含义） |

**判断（有取舍价值）**：对我们而言，**CI/CD 语义对齐的优先级高于 GenAI 语义对齐** ——
前者标准更成熟、且贴合我们的核心业务对象（issue/任务/流水线）；后者我们语义已对齐、只等标准稳定。

| 16 | 基数控制 / 采样 | ❌ | 指标维度白名单与上限（防基数爆炸）、日志采样/分级留存 |
| 17 | 审计事件进观测面 | 🟡 | `audit_logs`（含 hash 链）已存在，但没进观测/事件视图（L2 可选） |
| 18 | Profiling / 火焰图 | ⏸ | 不做：无 C 端、无长驻服务栈，收益远小于成本 |
| 19 | RUM / 会话重放 / 移动端 | ⏸ | 不做：无 C 端场景 |
| 20 | 安全监测 CSPM/SIEM | ⏸ | 不做：不是 grape 的产品边界（已有白名单/稽核，属另一条线） |
| 21 | 统一查询语言 DQL | ⏸ | 不做：结构化筛选 + 保存视图足够；学习成本 vs 收益不划算 |

## 四、我们的三个结构性优势（通用平台做不到，别丢）

1. **语义深度**：我们知道"任务属于哪个 issue、哪个 stage、哪个场景、哪个引擎、哪个 worker、
   花了多少 token、改了哪些提交"。通用平台只能看到"一个 HTTP 服务"。
   → 因此：**SLO 应该按"任务成功率/交付前置时间"定义，而不是按"接口可用率"**；
   **告警应该能一跳直达任务时间线**。
2. **编排即观测对象**：流水线（vod→issue→coding→qa→sre）本身就是可观测单元，
   `pipeline_trace_id` 已在做这件事；下一步是把它变成**交付效能指标**（DORA）。
3. **跨机零依赖**：全部自建、MySQL + 文件、worker 复用既有通道（无新组件、无外部 SaaS），
   这在私有化/内网场景是硬优势 —— 设计时**不要为了对标而引入 SDK/时序库**。

## 五、归属分析：这些缺口放用户面还是管理台？（2026-10-17 新增）

> 起因：缺口里有些放进 **grape-admin 管理台**比塞进主服务用户面更合适。
> 完整逐项矩阵与实现落点见主设计文档 **§5.4**；这里只留结论。

**两端的天然分工**

| | 主服务·用户面（:3000） | grape-admin 管理台（:8081） |
|---|---|---|
| 受众 / 视角 | 仓库成员、研发团队 / **我的** | 平台运营、管理员 / **全局**（不按仓库过滤） |
| 能力 | 可观测性三分区 + 告警横幅与面板 | 健康中心（任务列表/设备监控/基础设施监控）、告警中心、设备/引擎/Agent/用户/组织/仓库管理、全局统计 |
| 数据获取 | `/api/obs/*`（强制可见范围过滤） | **已直连主控库**（`GRAPE_DB_URL`）→ 读 `obs_*` 无需新接口（健康中心已有先例） |

**归属五原则**：① 含跨租户/平台基础设施信息 → 只能管理台；② 平台运营动作（定义规则、定目标基线、
配置策略、审计）→ 管理台；③ 用户自助消费（我的仓库/任务/设备）→ 用户面；④ 两端都有消费方 → **双端**
（数据同源、管理台=**全局视图**、页面不共享）；⑤ 拿不准且用户面价值不明显 → 先只进管理台（用户面要精简）。

**结论表（缺口 → 落点）**

| 缺口 | 落点 | 一句话理由 |
|---|---|---|
| 告警治理增强（级别/升级/重复抑制/聚合/通知时段/批量静默） | **管理台为主**，用户面只读级别 + 自助静默 | 通知策略＝平台运营动作 |
| 数据缺失（Data Gap）+ 突变检测 | **双端** | 用户关心自己仓库；平台要全局静默名单 + 阈值配置 |
| `obs_metric_rollup` 完整版 | **主服务**（数据面）；配置入口在管理台 | 数据面在主服务，配置面在管理台 |
| 统一事件视图 + 下钻 | **双端**（`audit` 来源只在管理台） | 跨租户/审计信息只在管理台 |
| **SLO / 错误预算** | **双端**：目标设定在**管理台**，用户面只读达成态 | 目标基线＝运营口径，统一设定防"两个真相" |
| **交付效能 / DORA** | **双端**：用户面只看自己仓库；**排行只在管理台** | 避免用户面横向比较 |
| 变更事件叠加 | **双端** | 排障第一问"是不是刚发的版本"两端都需要 |
| 定期巡检报告 | **双端，分两份** | 仓库日报 ≠ 平台日报，受众不同 |
| 保存视图 / 自定义面板、基数保护 | **双端各自实现**；基数配置在管理台 | 受众与数据范围不同，共享组件反而耦合 |
| 可用性拨测 | **双端**（探测执行放 worker 节点） | 用户测自己的服务；平台测自身端点（就近探测） |
| 日志解析管道、审计入事件、值班轮值 | **管理台** | 平台配置/运营动作 |
| LLM 内容级观测 | **双端**（跨租户检索只在管理台 + 必记审计） | 高敏感，跨租户必须留痕 |
| 成本 / 定价（暂缓） | **双端** | 成本敏感：用户面只显示自己范围内 |

**实现落点总原则**：**数据面在主服务，配置面在管理台，消费面各自前端**。
即计算/采集/求值（rollup、SLO、事件聚合、Data Gap、拨测执行）在主服务；
策略/目标/参数（告警策略、SLO 目标、检测阈值、留存与基数白名单、解析管道）写进主控库、入口在管理台；
两端页面各写各的，只共享**同一份聚合口径**（防"两个真相"）。

## 六、结论：下一阶段重新规划（替代原 P1/P2 草案）

> 规划原则：① 先补"治理层"（我们最落后、且用户会被误导的地方）；② 再做**差异化**（DORA/交付效能、
> 变更关联）；③ 通用平台的"广度"一律不做；④ 定价（成本）用户已明确**暂缓**，仅保留字段与设计位。

### P1（先做，1~1.5 周量级）—— 补治理层与数据质量

> 落点（见 §五）：**P1-1 → 管理台为主**（用户面只读级别）；**P1-2 → 主服务**（数据面）；
> **P1-3 / P1-4 → 双端**（管理台全局视图）。

| # | 交付 | 为什么现在做 | 量级 |
|---|---|---|---|
| P1-1 | **告警治理增强**：事件级别分级 + 重复抑制间隔 + 聚合（按规则/周期）+ 自定义通知时段 + 告警升级 | 我们只有"静默"，一旦真报警就会刷屏；这是用户最早会抱怨的点 | 3d |
| P1-2 | **`obs_metric_rollup` 完整版留存**：分钟聚合表 + 采样器写入 + 清理；总览/趋势改读 rollup | 现在总览直查 `agent_tasks`（307 行没事，量表一大就慢）；也是 SLO 的底座 | 2d |
| P1-3 | **数据缺失（Data Gap）+ 突变检测**：引擎/仓库"该报数却没报"、成功率环比突变 | 观测云把 Data Gap 单列为事件级别不是偶然：**静默失效**是最危险的故障 | 1d |
| P1-4 | **告警 → 任务/trace 下钻 + 处置建议**：事件带"下一步"（跳时间线/日志/相关 issue） | 把已有的时间线/日志串成排障动线，成本低收益高 | 1d |

### P2（差异化，2 周量级）

> 落点（见 §五）：**全部双端**；其中 **SLO 目标设定**与 **DORA 排行**只在管理台，
> 用户面只读自己的仓库。

| # | 交付 | 为什么值得 | 量级 |
|---|---|---|---|
| P2-1 | **SLO / 错误预算**：SLI 三选（任务成功率、排队时延 P95、引擎可用率）+ 目标 + 错误预算 + 达成率面板；扣减口径按"异常事件覆盖时长合并" | 把"我们的健康"从一堆数字变成**一个可否决的结论**；也可用于对内承诺 | 4d |
