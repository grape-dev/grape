## C1 派发层判死：绑定引擎全部不可达（任务级 8 / 事件级 2，占比最大）

**一句话根因**：场景把任务绑死到某一台引擎（issue→opencode，sre/qa→codex），该引擎离线/心跳过期/无对应标签时，claim 路径直接把任务判死，而 service.py 主循环里"清空 pool_engine_ids 放行全站"的兜底没有覆盖 scene 绑定路径。

### 出错的逻辑
- `src/runtime/service.py:113-133`（Issue #253 改动2）：`claim / claim_by_tag` 认领时发现 pool_engine_ids 内引擎全部不可达（离线/心跳过期/无对应标签/满载）→ 任务诚实失败，errors 记为"绑定的 N 台引擎（xxx）全部不可达……标签=xxx"。
- 主循环兜底（service.py:1121-1138、1392-1409）只对"派发中任务"清空 pool_engine_ids 放行；走 claim/claim_by_tag 的 scene 绑定任务不经过该兜底。
- 本窗口表现：issue 通道 4 条（opencode 引擎不可达，01:00-01:02 UTC 集中爆发）；qa/sre 通道 4 条（codex 引擎不可达，07:12-14:40 UTC 分散出现）。13 台 worker（114-126）本身在池中可用，问题是标签绑定把可用引擎排除在外。

### 修正后的逻辑
claim/claim_by_tag 发现绑定引擎全部不可达时，不立即判死，改为：① 若任务无严格亲和性要求（scene 仅偏好而非强制），退化为全站池认领（与主循环兜底同一把尺子，service.py:50-58 的可达判定）；② 确需亲和的任务进入"限时等待引擎恢复"队列（复用 #253 改动3 的 wait 机制，service.py:161-180），超时再诚实失败。errors 文案需区分"物理不可达"与"健康分不足"。

### 影响面评估
- worker 端无需改动（13 台 114-126 不涉及批量升级）；改动集中在 service.py 派发层，风险中等。
- status 枚举不变（仍走 failed），前端/统计口径兼容。
- 双主场景：service.py 变更需要双主 scp 同步流程，避免两台主派发行为不一致。
- 需要新增配置项区分"强制绑定 / 软绑定" scene，存量 scene 默认软绑定，避免行为突变。

### 测试用例设计
1. mock 绑定引擎 offline，软绑定任务 → 应被池内其他在线引擎认领成功。
2. mock 绑定引擎 offline，硬绑定任务 → 应进入等待队列，超过等待窗口后 failed 且 errors 含"物理不可达"。
3. 绑定引擎恢复上线后，等待队列中的硬绑定任务应在下一个 claim 周期被认领。
4. 13 台 worker 全部 offline 时，任务失败文案应包含池级信息而非单引擎信息。
5. 回归：绑定引擎在线时，任务仍只派发给绑定引擎（不因改动泄漏到全站）。

## C2 运行时超时（事件级 2 / 任务级 1）

**一句话根因**：任务实际执行时间超过 RUNTIME_TASK_TIMEOUT，外层统一 kill：9963 是收尾窗口无输出的静默超时；10067 是 SIGTERM 后 grace tail 仍有半截文本、最终仍超时。

### 出错的逻辑
- `src/runtime/agent.py:1892-1902`：`task timed out after Ns, killing child processes and failing` → `client.fail(_tid, ..., exit_code=-1)`。
- 9963：vod 任务 05:21:23 开始，约 5 分钟后被 kill，result 只有 "engine exit_code=-1, errors:"，无任何工作痕迹——典型的无输出静默超时（正常应触发 -9/no output 判定，此处走到外层 RUNTIME_TASK_TIMEOUT，说明在收尾窗口内有非实质输出维持了活性，见 executor.py:439 附近对上层误报的说明）。
- 10067：sre deploy 任务 18:10:35 开始，约 16.5 分钟超时，result 里已有大量有效的排查文本（AK/SK 核对、部署路径确认），属于"工作有价值但没跑完"。

### 修正后的逻辑
- 10067 这类"有持续产出的长任务"：超时前若有新增输出，允许一次性宽限（grace extension）或把超时上限按 skill（deploy-cli 类）单独配置；至少在 result 中保留完整 grace tail 而非截断。
- 9963 这类"无实质输出"：把"活性判定"从"有任何字节输出"收紧为"有非心跳/非空白输出"，避免空转任务拖满整个 timeout 窗口。

### 影响面评估
- worker 端 executor/agent 有变更 → 涉及 13 台 worker（114-126）批量升级，需要灰度。
- 双主 scp 同步不涉及（主端只读结果）。
- 超时语义变化需与前端展示对齐（超时 vs 失败文案）。

### 测试用例设计
1. 任务持续输出有效文本且超过 timeout → 触发一次性宽限，宽限期内完成则 completed。
2. 任务仅输出心跳/空白 → 提前按"无实质输出"路径判死，总耗时 < timeout。
3. deploy-cli skill 单独配置更大 timeout → 不被全局值 kill。
4. 超时任务的 result 必须包含完整 grace tail 文本（回归 10067 场景）。
5. kill 后子进程无残留（ps 校验无孤儿进程）。

## C3 华为云 AK/SK 未注入（事件级 1 / 任务级 1）

**一句话根因**：deploy-cli 部署链路需要的华为云凭据没有注入到执行环境，代码侧全部验证通过（pytest 54 passed、前端回归 8 passed），部署动作被阻塞，任务以 exit 1 失败。

### 出错的逻辑
- seq 10084 / t_ecc0c683245f（21:20 完成）与 seq 10067（C2 超时，同样卡在 AK/SK）：sre 在 vod-001/build-005 目标确认后，因凭据缺失无法执行任何 hcloud/ECS 操作，只能把"部署阻塞"作为失败结论回帖。
- 凭据注入属于环境配置问题，非代码缺陷；但任务被记为 failed 而非 blocked/waiting，污染了失败率统计。

### 修正后的逻辑
- 部署类任务前置检查凭据可用性（hcloud 配置存在性校验），缺失时任务进入 blocked 状态（或带 `missing_credentials` 标签的失败子类），并在 Issue 回帖中给出明确补救指引，而非消耗完整执行窗口后失败。
- 平台侧提供凭据注入的配置入口与健康检查（settings 通道）。

### 影响面评估
- 新增 blocked 状态需前端/统计口径同步（status 枚举兼容：旧客户端见到未知 status 应兜底显示）。
- 不涉及 worker 升级。

### 测试用例设计
1. 凭据缺失 + deploy 任务 → 前置检查即返回 blocked，不启动引擎执行。
2. 凭据存在但过期 → 首次 hcloud 调用失败后转 blocked 并带原因。
3. 凭据补齐后 blocked 任务可重新触发并成功部署。
4. 旧版前端拉到 blocked 状态 → 兜底渲染为"等待中"不报错。
5. 统计接口把 blocked 与 failed 分开计数。

## C4 评论发布接口 405（事件级 1 / 任务级 1）

**一句话根因**：skill 指定的评论 POST 接口返回 405 Method Not Allowed，Agent 无法把验收结论回帖到 Issue，任务以 exit 1 失败——接口地址/方法与平台实际路由不匹配。

### 出错的逻辑
- seq 10042 / t_d2d11a11214a：forest-v2-codex-sre-test 技能按用户指定的 POST 接口发布评论，返回 405；结论本身（"接受现状"）已完成，只是回帖动作失败，整任务被判 failed。

### 修正后的逻辑
- skill 文档中的接口清单与平台路由对齐（核对 grape-main 实际 POST /comments 路由）；Agent 端在 405/404 时做一次接口发现兜底（GET 根路径/OpenAPI）再重试。
- "结论已产出、仅回帖失败"应允许降级为 completed-with-warning 或重试回帖，而非整任务 failed。

### 影响面评估
- 改动集中在 skill 文档 + Agent 提示词，无服务端代码变更；风险低。
- 状态细分（completed-with-warning）如采用，需同 C3 一起做枚举兼容。

### 测试用例设计
1. 正确路由 POST 评论 → 成功发布。
2. 405 响应 → 触发接口发现并重试一次，仍失败则降级状态而非 failed。
3. 结论文本在回帖失败时仍完整保留在 result_text。
4. 重复回帖幂等（同 content 二次 POST 不产生重复评论）。

## C5 SSH 嵌套引号被转义破坏（任务级 1）

**一句话根因**：t_c54ed2a08254（event_seq 338）通过 SSH 执行远端命令时，嵌套引号被层层转义破坏（日志原话"SSH 嵌套引号被转义破坏了（grep/t…"），命令没跑成，任务 exit -1 失败。

### 出错的逻辑
- Agent 生成 `ssh host "bash -c '...grep \"x\"...'"` 形式命令时引号层数超出转义能力，远端收到语法错误的命令。
- 属于工具使用/提示词层面问题：应改用 heredoc、base64 载荷或 scp 脚本后执行，避免多层嵌套引号。

### 修正后的逻辑
- 在 sre/deploy 类 skill 中固化规范：复杂远端命令一律走"本地写脚本 → scp/base64 → 远端 bash 执行"，禁止三层以上嵌套引号；简单命令用单层引号模板。

### 影响面评估
- 纯 skill 文档/提示词变更，无代码风险。

### 测试用例设计
1. 含双引号/单引号/管道/grep 的复杂命令 → heredoc 方式远端执行成功。
2. 三层嵌套引号场景 → 触发规范降级为脚本方式。
3. scp 方式脚本执行后远端清理临时文件。

## C6 口径问题：event_seq 333-338 悬空（数据一致性，0 条计入失败）

agent_tasks 中有 4+1 条失败行引用 event_seq 333-338，但 events 表中这些 seq 不存在（`count(*) where seq between 333 and 338` = 0）。这些任务由本轮 issue 通道触发却指向早已不存在/被重建的事件行，说明 events 表发生过重置（seq 从 9000+ 重新计数）而 agent_tasks 未同步清理，或跨环境写入了同一库。建议：任务写入时校验 event_seq 存在性；对悬空行做一次性数据修复并加唯一性/外键约束。

## 优先级排序（修好即清零、改动小优先）

1. **C4 评论接口 405**：改 skill 文档即可，一次修复清零该类。
2. **C5 SSH 引号转义**：同上，纯 skill 规范。
3. **C1 引擎不可达判死**：占失败大头（8/12），改动集中在 service.py，修好后软绑定任务不再因单引擎离线失败。
4. **C3 AK/SK 前置检查 + blocked 状态**：避免浪费执行窗口，需枚举兼容设计。
5. **C2 超时宽限**：涉及 13 台 worker 批量升级，放最后灰度。
6. **C6 悬空 event_seq**：数据修复 + 约束，随 C1 一起做。

## 一句话总结（大白话版）

- C1：任务被"包办婚姻"绑死在一台引擎上，那台机器一掉线任务就陪葬——改成"绑定的机器不在就让池子里其他机器顶上，实在不行等一等再失败"。
- C2：任务没在规定时间干完被掐掉——干活有产出的给宽限，光喘气不出活的早点掐。
- C3：要部署才发现钥匙没带——出发前先检查钥匙，没钥匙直接报"blocked"别白跑一趟。
- C4：回帖接口地址写错了（405）——对一下地址表，回帖失败别把整个任务判死刑。
- C5：远端命令引号套太多层把命令搞坏了——以后复杂命令打包成脚本再送过去执行。
