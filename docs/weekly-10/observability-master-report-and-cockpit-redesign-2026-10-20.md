## 1. 洞察汇总（九条，全部有证据支撑）

### 洞察 1：AI 时代的可观测核心矛盾 = 行为不确定性 × Token 成本
观测云 2026 路线图、OTel GenAI 语义约定、LinearB 基准报告三方独立收敛：传统 CPU/内存监控无法反映 AI 业务健康度，**Token 成本归因 + Agent 行为追踪**才是主线。grape 三级归因设计已在主线上。

### 洞察 2：业界标准已收敛到 OpenTelemetry GenAI 语义约定
`gen_ai.usage.input_tokens/output_tokens`、`invoke_agent/execute_tool` span 树、token 分列存储（input/output/cache_read/cache_write/reasoning 各自独立，合并即不可逆）已被 Datadog/Arize/Langfuse/Google/Azure 全部采纳。grape 的 `obs_llm_usage` 列设计**天然对齐**，但字段命名未标准化。

### 洞察 3：归因必须在调用边界当场完成
上下文（哪个 agent/工具/步骤/用户）只在调用瞬间可得，事后不可重建。grape 的 usage_collect"基线差值"法与业界"调用点拦截"法是同一问题的两种解法，均可继续，但**异步上报必须带去重键**（traceId+callId+attempt），防重试双计。

### 洞察 4：宽表 + 冗余上下文是存储终局（Langfuse v4 实证）
Langfuse 放弃 trace 表 JOIN，单一 ClickHouse 宽表每行冗余 user/session/tags，大项目加载 10x 提升。grape 的 MySQL events 表已是宽表模式；当前量级（<1000 行/天）远未触顶，**暂不迁移**，schema 演进往"每行自带全上下文"方向走。

### 洞察 5：AI 参与度已成为用户洞察的独立维度（LinearB 8.1M PR 数据）
PR 三分类（Unassisted / AI-assisted / Agentic）：AI 辅助 PR 30 天合并率 32.7% vs 人类 84.5%；agentic PR pickup 时间 4.6-5.3 倍。**"谁在用 AI"已不重要，"AI 产出能否走完交付链路"才是组织分水岭**。grape 场景 agent 密度远高于普通仓库，这个维度价值更大。

### 洞察 6：bot 过滤是 AI 密集仓库用户洞察的硬前提
GitHub 原生 Insights 无 bot 过滤是社区公认缺陷；Flyte Pulse 等社区方案标配：`[bot]` 后缀 + GraphQL Bot 类型 + 配置名单，bot 的 PR/commit/review 全部单列。grape 所有 agent 任务天然带 bot 身份，**不过滤的用户指标全部失真**。

### 洞察 7：个人绩效指标有滥用史，产品定位必须是"协作洞察"
DX Core 4 / LinearB 明确警告：PR 数类指标只做组织级平均、不做个人排名。展示定位、默认聚合粒度、可见范围都按此约束设计。

### 洞察 8：按结果采样而非固定比例，内容脱敏在导出前
业界共识：100% 保留错误/超时/超贵/eval 失败的 run，正常流量采 5-10%；prompt 内容生产默认只记元数据，脱敏在采集侧完成。grape 目前 task_messages 全量记且无脱敏策略——上量前必须补。

### 洞察 9：grape 数据基础盘点——用户维度数据已在库，缺展示层
- `events.actor`（行为）✅、`agent_tasks.user_id/account`（任务发起）✅
- `obs_llm_usage`：`user_id/repo_key/agent_type/engine_id` + token 六分列 + cost ✅
- `unified_user_mapping`（身份归一表）已建
- **唯一缺口**：聚合查询 + 页面；PR 粒度质量指标未指标化

## 2. 重设计总方案：运行驾驶舱 2.0

### 2.1 从"三页合一"到"四区一体"

1.0 驾驶舱分区是**运行视角**：总览 / 设备与引擎 / 任务与日志。重设计追加**第四个视角——参与洞察**（用户/贡献/成本归属）：

- **总览页**增加"参与者与成本"区（驾驶舱一眼看到"谁在用、花了多少"）
- **仓库详情页**新增「参与洞察」入口（用户偏好：功能入口放详情页内），承载完整的用户维度下钻
- 设备与引擎 / 任务与日志两分区**不动**（已定稿实现，不返工）

```
侧栏（变更后）：

可观测性                        ← 一级分类（不变）
 ├ 📊 总览                      (observability/overview)      + 参与者与成本区
 ├ 💻 设备与引擎                (observability/devices)       不变
 └ ▶ 任务与日志                 (observability/inspect)       不变

仓库详情页                      ← 新增页内 Tab（非侧栏）
 └ 👥 参与洞察                  (repo/insights?repo=<k>)      用户维度完整下钻
```

**设计理由**：运行健康是平台视角（所有人共享一份），参与洞察是仓库视角（每仓各自一份）——数据源重叠但聚合粒度和受众不同，硬塞进侧栏一个入口会让总览页承担两种互相打架的过滤语义（全平台 vs 单仓）。

### 2.2 总览页 2.0 布局（在已定稿布局上扩两行）

沿用 overview-page-design 的 12 列栅格、时间/仓库全局过滤、ECharts 选型与语义色板，在第 ⑥ 区后新增：

```
┌───────────────────────────────────────────────────────────────────────────────┐
│ 可观测性 · 总览          [仓库 ▾ 全部]   [1h│6h│24h│7d│30d]  [⟳ 30s ▾]  [刷新]   │
├───────────────────────────────────────────────────────────────────────────────┤
│ ⚠ 告警横幅（不变）                                                              │
├───────────────────────────────────────────────────────────────────────────────┤
│ KPI 行（不变：队列深度 / 成功率 / P95 耗时 / 引擎在线）                          │
├───────────────────────────────────────────────────────────────────────────────┤
│ ①-⑥ 六张图（不变：任务量与结果 / 引擎健康分 / 耗时构成 / 队列与在跑 /            │
│    日志错误趋势 / 我的设备资源）                                                │
├───────────────────────────────────────────────┬───────────────────────────────┤
│ ⑦ Token 消耗与成本     6 列                    │ ⑧ 参与者活跃度   6 列          │
│   堆叠柱(input/output/cache 分列,按 agent)     │   堆叠柱(按用户: 触发事件+     │
│   + 折线(日成本) + p99 标注                    │   发起任务, bot 灰色单列)      │
│   点击 → 任务与日志(带过滤)                     │   点击 → 仓库参与洞察页        │
├───────────────────────────────────────────────┴───────────────────────────────┤
│ ⑨ 最近异常任务（不变，表格 5 行）                                        查看 → │
└───────────────────────────────────────────────────────────────────────────────┘
```

新增两图口径：

| 图 | 指标 | 数据源 | bot 处理 |
|---|---|---|---|
| ⑦ Token 与成本 | 日 token 堆叠（input/output/cache_read/cache_write/reasoning 五列）+ 日成本折线 + 单任务 p99 标记点 | obs_llm_usage | 全量含 agent（成本本就该算 agent） |
| ⑧ 参与者活跃度 | 按用户堆叠（触发事件数 + 发起任务数），Top 10 + "其他" | events + agent_tasks | **bot 身份灰色单列不计入 Top 排序** |

时间窗 30d 进入全局切换（⑧ 最低粒度是天，1h/6h 窗口下显示"无数据"而非报错）。

### 2.3 「参与洞察」页设计（仓库详情内，新页面）

四段式（URL `/repo/insights?repo=<repo_key>`，默认 30 天）：

```
┌───────────────────────────────────────────────────────────────────────────────┐
│ 参与洞察 · grape-dev/grape          [7d│30d│90d]   [导出 CSV]                   │
├───────────────────────────────────────────────────────────────────────────────┤
│ A. 参与者总览（表格，每行一个用户，默认按活跃度降序）                             │
│ ┌────────┬────────┬────────┬────────┬──────────┬─────────┬────────┐          │
│ │ 用户    │ 活跃天数 │ 触发事件│ 发起任务│ 任务成功率 │ Token消耗 │ 引擎偏好│          │
│ │ [头像]  │  12     │  48    │  23    │ 87% ▇▆   │ 1.2M    │ oc/ai  │          │
│ │ 🤖agent │  单独一行灰色，标注"bot 身份"，不计入人类排名                        │
│ └────────┴────────┴────────┴────────┴──────────┴─────────┴────────┘          │
├───────────────────────────────────────────────────────────────────────────────┤
│ B. 贡献质量（点击用户行展开）                                                    │
│    PR 创建数/合并率（人 vs agent 产出分列）· review 参与度 · pickup 时间         │
│    agentic PR 占比 · AI 辅助率（LinearB 三分类口径）                            │
├───────────────────────────────────────────────────────────────────────────────┤
│ C. 成本洞察（用户 × agent_type 热力矩阵）                                       │
│    谁在哪个环节烧钱；点击格子 → 任务与日志(带 user+agent 过滤)                   │
├───────────────────────────────────────────────────────────────────────────────┤
│ D. 趋势（选中用户的 token/任务/成本 30 天折线，无选中时显示仓库合计）              │
└───────────────────────────────────────────────────────────────────────────────┘
```

交互与边界规则：
- A 表行点击 → 展开 B；B 内 PR 指标点击 → GitCode PR 列表
- C 热力格色阶复用语义色板（成本高=红，但**仅工具提示显示具体金额**，不做排名视觉——呼应洞察 7）
- 未归属（user_id 为空的 usage 行）单独显示"未归属"桶，不摊派
- 权限：仓库成员看 A/B/D 全量；C（成本明细）仅仓库管理员+平台管理员
- 导出 CSV 与 admin 侧"内测申请导出"复用同一套导出件

### 2.4 数据层增量（不新建表）

| 项 | 设计 | 备注 |
|---|---|---|
| 聚合 API | `GET /api/obs/insights/overview?repo=&days=`（A/B/D 一次返回）+ `GET /api/obs/insights/cost-matrix`（C） | 5 分钟缓存（machine-health 同模式） |
| 归一 | 全部查询先过 `unified_user_mapping` | 未映射的 actor 落"待归一"桶并提示可绑定 |
| bot 判定 | `user_accounts.kind`（新增列，bot/ai/human）+ agent 任务 user_id 为空视为 agent 触发 | 名单配置化，防误杀 |
| PR 指标化 | events 表 pull_request_* 事件的指标化查询（不落新表，聚合时算） | 量小可行 |
| obs_llm_usage 补强 | 历史行 user_id 回填任务（从 agent_tasks 关联补） | 缩小"未归属"桶 |

### 2.5 与 1.0 的兼容性

- 三支柱分区、统一事件视图、数据缺失检测、stuck 检测全部保留
- 告警面板不动；可新增"单用户单日成本超阈值"告警规则（P3）
- ECharts vendored 通道复用（⑦⑧ 不引入新库）

## 3. 落地路线（合并全部子文档排期）

| 阶段 | 内容 | 依赖 | 量级 |
|---|---|---|---|
| **P1** | 总览页 ⑦⑧ 两图 + 参与 API（A/D 段）+ bot 判定 | 无新表，纯查询层 | 2-3 天 |
| **P2** | 参与洞察页 B 段（PR 质量指标化）+ C 段成本矩阵 | P1 | 3-4 天 |
| **P3** | 身份归一自动补全 + user_id 历史回填 + 成本告警规则 | P1 | 1-2 天 |
| **P4** | obs_llm_usage 字段名 OTel 化（视图层别名，不改存储）+ 采样/脱敏策略 | 独立 | 择机 |
| **远期** | ClickHouse/TimescaleDB 迁移（宽表冗余模式）、DX Core 4 团队对比视图、观测云式 Session 下钻 | 数据量触发 | — |

每阶段独立可验收（强断言）：P1 = 总览页 30d 窗口两图出数 + bot 行灰色单列 + 点击跳转链路通；P2 = 某真实仓库参与洞察页全四段有数且与 DB 手工查询一致。

## 4. 风险清单（汇总）

1. **绩效滥用**：产品文案锁定"协作洞察"；个人明细默认仅本人+管理员（洞察 7）
2. **bot 误杀/漏杀**：判定名单配置化 + 页面可见（可纠正）
3. **归因断链**：未归属桶显式展示，绝不摊派
4. **成本口径**：token 分列存储已就位，rate card 版本化（定价表带 effectiveDate），不事后 reconcile
5. **数据量**：MySQL 聚合 + 5 分钟缓存在当前量级绰绰有余，监控点（聚合查询 P95 > 1s 触发告警）作为迁移远期触发器
