## Objective

- 要构建什么：让 `_count_issues` 的失败日志自带实际连接目标（域路由/库名，脱敏）+ `pid` + `host`；把
  `_DomainDbProxy` 的「缺 DSN 即静默回落进程主库」分支收口到内核 `db_registry.route_of()` 契约
  （三库拓扑缺 `GRAPE_DSN_RUNTIME` 时显式抛 `DomainUnavailable`）；完成全仓 `COUNT(*) FROM issue`
  站点审计与静态守护。
- 为什么：上一轮修复（#3771，`36157553e`）在生产未闭环，4 台主控仍 2,204 条/小时刷同一条
  `issues mine: count failed`；「旧进程未重启」与「新代码仍打 mgmt 库」在日志上同形、不可区分，
  导致验收反复失效。
- 用户是谁：主控运维/发布责任人——需要一眼判定「哪台主机、哪个进程、连的哪个库」。
- 成功标准：出现该 WARNING 时，单行日志即可回答 host/pid、`domain` 还是 `local` 路由、目标库名，
  据此外推「重启即可」或「代码缺陷」，不再依赖事后推断。

## Technical Approach

### 方案概述

「issue 域该连哪个库」只由 `kernel.db_registry.route_of()` 判定；`_DomainDbProxy` 不再自带第二套
回落语义。COUNT 失败日志附带路由与目标库事实，使「部署问题」与「代码问题」在日志层即可分流。

### 实现路径

1. `_count_failure_context()`：`route_of("runtime")` → `domain` 取 `database_of("runtime")`，
   `local` 取 `DEVOPS_DB_NAME`（空则 `(process main)`），`DomainUnavailable` 记
   `route=unavailable target_db=-`；另附 `os.getpid()` + `socket.gethostname()`。
2. `_DomainDbProxy._route()`：`route_of("runtime")` 的薄包装；`DomainUnavailable` 对
   `commit/rollback` 视为「无连接可提交/回滚」的 no-op（debug 记录），**绝不回落主库**；
   `cursor()` 直接上抛（异常可辨识，供调用方降级）。
3. `_count_issues`：`except` 分支 `log.warning(f"{label}: count failed: {e} " + context)`。
4. 测试：新增 `tests/runtime/test_issue_3826_count_no_fallback.py`，沿用 `db_registry` 既有三库
   拓扑 seam（先例 `tests/runtime/test_3350_runtime_domain_db_routing.py`、
   `tests/runtime/test_issue_3771_mine_count_domain.py`）；`session_manager.db` 换成「触达即失败」
   的哨兵，证明不回落。

### 关键设计决策

| 决策 | 选项 | 选择 | 理由 |
|------|------|------|------|
| 缺跨域 DSN | 回落进程主库 / 显式失败 | 显式失败 | 回落会读错库且与「数据不存在」不可区分（`DomainUnavailable` 文档契约） |
| `commit/rollback` 遇 `DomainUnavailable` | 上抛 / no-op | no-op + debug | `cursor()` 已上抛由调用方降级；在 `except` 里调 rollback 时再抛会掩盖原始异常，且此时并无连接可回滚 |
| COUNT 失败降级 | 返回 0 / 返回 None | 返回 None | 虚假 0 会让 `total`/`has_more` 双双失真，正是本 Issue 原始症状 |
| 日志字段 | 仅异常文本 / 附带路由+目标库+pid+host | 附带全部 | 异常文本里的 schema 名是唯一线索，恰好无法区分「旧进程/新代码」 |

## 全仓 COUNT 站点审计（`COUNT(*) FROM issue`，src/ 全量）

| 位置 | 形态 | 结论 |
|------|------|------|
| `src/domains/runtime/routes/issues.py` `_count_issues` | `SELECT COUNT(*) FROM issue WHERE {where}` | ✅ 唯一的路由层 issue COUNT，收口点 |
| `src/domains/runtime/migrations_ddl.py:157` `SELECT_ISSUE__TASKS_TO_ISSUE_RENAME_PRE_CR` | 迁移前置探测（`tasks`→`issue` 重命名） | ✅ 迁移期在本域进程内执行，不经 mgmt 路由 |
| `src/domains/runtime/public/__init__.py:3162` `issue_vcs_checked_count` | runtime 域 public 原语（VCS 索引台账） | ✅ 已走域 public 连接（#995 收口），非裸 SQL |

结论：**路由/API 层的 issue COUNT 仅 `_count_issues` 一处**，无第三处裸 SQL；
`issue_state`/`issue` 联表的 `COUNT(*)`（`migrations_ddl.py:320/325`）不计入 issue 表 COUNT。
