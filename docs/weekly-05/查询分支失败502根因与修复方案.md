# 查询分支 502（GitHub API 404）根因与修复方案

> 日期：2026-09-30
> 现象：`GET https://www.grapedev.cn/api/scenes/branches/github%3Ahuaweicloud-mate/hdkitservice` 返回
> `{"detail":{"code":502,"message":"查询分支失败: GitHub API GET https://api.github.com/repos/github:huaweicloud-mate/hdkitservice/branches?per_page=100&page=1 failed (404): {\"message\":\"Not Found\",...}"}}`

---

## 一句话结论

前端把**带 `github:` 前缀的 repo_key 整个当成了 owner** 拼进 URL 路径，后端原样转发给 GitHub API（`repos/github:huaweicloud-mate/hdkitservice/branches`），GitHub 上当然没有叫 `github:huaweicloud-mate` 的用户，返回 404，被包装成 502。

## 触发链路（完整调用链）

```
① GET /api/dashboard/huaweicloud-mate/hdkitservice
   └─ dashboard.py:1207  返回 "repo": _actual_repo_key
      = "github:huaweicloud-mate/hdkitservice"   ← 带前缀（DB 里实际使用的 repo_key）

② 前端 dashboard.js 进入场景创建/高级选项（enterCreateMode / renderSceneDetailLocal）
   └─ app.currentRepo() 不可用时走兜底：
      dashboard.js:54 / 466 / 1192
      const parts = (data.repo || '').replace(/^gitcode:/, '').split('/');
      → 只剥 gitcode:，不剥 github:
      → owner = "github:huaweicloud-mate"（污染）, name = "hdkitservice"

③ dashboard.js:1303  API.get('/scenes/branches/' + owner + '/' + name)
   → GET /api/scenes/branches/github:huaweicloud-mate/hdkitservice   ← 用户报错的 URL

④ 后端 scenes.py:772 list_repo_branches
   └─ _detect_repo_provider("github:huaweicloud-mate", "hdkitservice")
      to_repo_key() 对已含 ":" 的串幂等返回 → 拼出的 key 恰好等于
      managed_repos 里真实的 "github:huaweicloud-mate/hdkitservice"
      → 误打误撞命中 DB，判定 provider="github"（路由"正确"，但污染未清洗）

   └─ scenes.py:790  url = https://api.github.com/repos/{owner}/{repo}/branches
      → https://api.github.com/repos/github:huaweicloud-mate/hdkitservice/branches
      → GitHub 404 Not Found
   └─ repo_manager.py:661  raise RuntimeError("GitHub API ... failed (404): ...")
   └─ scenes.py:804  包装成 502 "查询分支失败: ..."
```

**为什么只有 GitHub 仓库出事、GitCode 仓库没事**：`data.repo` 对 GitCode 仓库是 `gitcode:owner/repo`，`replace(/^gitcode:/)` 恰好剥得掉；`github:` 前缀是跨平台支持新引入的，前端这些老代码写的时候只有 gitcode，从没更新。

**架构违规点**：`src/repo_key.py` 模块头部明确约定「外部/前端：一律无前缀」，但 `dashboard.py:1207` 直接把带前缀的 `_actual_repo_key` 塞进了 `repo` 字段（对比 `pipeline.py:360` 的正确写法 `"repo": from_repo_key(_actual_repo_key)`）。前端被迫自行剥前缀，剥漏了就是本次事故。

---

## 修复方案

### 第一层：前端根治（必改）——统一剥两种前缀

所有 `.replace(/^gitcode:/, '')` 改为 `.replace(/^(gitcode|github):/, '')`：

| # | 文件 | 行号 | 上下文 |
|---|------|------|--------|
| 1 | `src/api/static/js/pages/dashboard.js` | 54 | `renderDashboard` 兜底拆 owner/name |
| 2 | `src/api/static/js/pages/dashboard.js` | 466 | `renderSceneDetailLocal` 兜底 |
| 3 | `src/api/static/js/pages/dashboard.js` | 1192 | `enterCreateMode` 兜底 |
| 4 | `src/api/static/js/pages/observability.js` | 931 | `_timelineGlobalRepoPath` |
| 5 | `src/api/static/js/pages/observability.js` | 988 | `repoPath`（issue 跳转） |
| 6 | `src/api/static/js/pages/pipeline.js` | 385 | 跳事件页的 repo 拆分 |

建议不逐处改字面量，而是在 `app.js` 加一个工具函数统一收口（后续再增平台不再漏）：

```js
// app.js —— repo_key 前缀统一剥离（对应后端 src/repo_key.py 的 from_repo_key）
function stripRepoPrefix(s) {
  return String(s || '').replace(/^(gitcode|github):/, '');
}
window.stripRepoPrefix = stripRepoPrefix;
```

6 处调用点改用 `stripRepoPrefix(...)`。注意 `dashboard.js:402-406`（已同时剥两种前缀并用 `startsWith('github:')` 判 host）保持不动，它是正确范例。

### 第二层：后端防御（强烈建议）——branches 端点入口归一化 owner

前端改完只是治了已知来源；`/api/scenes/branches/{owner}/{repo}` 是路径参数接口，任何客户端都可能再传进带前缀的 owner（本次线上 URL 即实证）。在 `scenes.py` 两个端点入口清洗：

```python
# scenes.py —— 放在 _detect_repo_provider 定义之前
def _normalize_owner_repo(owner: str, repo: str) -> tuple[str, str]:
    """清洗路径参数中的 provider 前缀污染（如 owner="github:foo"）。

    to_repo_key 对已带冒号的串幂等返回，会掩盖污染并让 DB 查询
    "碰巧"命中；必须在拼外部 API URL 前把前缀剥掉。
    """
    if ":" in owner:
        prefix, _, rest = owner.partition(":")
        if prefix in ("github", "gitcode", "gitlab"):
            owner = rest
    return owner, repo
```

`list_repo_branches`（scenes.py:772）和 `create_repo_branch`（scenes.py:848）函数体第一行调用：

```python
owner, repo = _normalize_owner_repo(owner, repo)
provider = _detect_repo_provider(owner, repo)
```

POST 创建分支同样受益：其 GitHub 路径 `scenes.py:872/881` 直接用 owner/repo 拼 `api.github.com` URL，污染同样会 404。

### 第三层（二期，契约统一）：dashboard 响应去掉前缀

`dashboard.py:1207` 改为与 `pipeline.py:360` 一致：

```python
return {
    "repo": from_repo_key(_actual_repo_key),      # 对外无前缀，符合 repo_key.py 约定
    "repo_key": _actual_repo_key,                 # 新增显式字段，供需要前缀语义的消费方
    ...
}
```

**联动改动**：`dashboard.js:406` 目前用 `(dashData.repo || '').startsWith('github:')` 判断 issue 链接跳 github.com 还是 gitcode.com，`repo` 去前缀后此判断失效，必须同步改为读 `dashData.repo_key`：

```js
const _issueHost = String(dashData.repo_key || '').startsWith('github:') ? 'github.com' : 'gitcode.com';
```

此层涉及 API 契约变更，单独立项、和前端一起发，避免半截上线。

## 风险评估

- 第一层（前端）：纯展示层字符串清洗，6 处点状替换，无 API 契约变化，风险最低，可先行上线。
- 第二层（后端归一化）：只影响两个 branches 端点入口，对正常入参（无冒号 owner）零变化；双主部署需同步 m2 并分别重启。
- 第三层（契约变更）：动 dashboard 响应结构，必须与前端 406 行联动，单独发版有回归风险，排二期。
