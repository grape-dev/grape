# Spec: Issue #3891 — /pipeline 与主资源共用 issue 解析链路（外部托管仓 issue_id=null 不再 404）

> Generated by Coding Agent | 2026-11-23 | 基线 `arch-weekly-11-ljt`（头 `16d47d6ec`）
> 上游 Spec 见 Issue 评论 comment id 202994843（issue 阶段）；本文件是编码阶段的落地切片。

## Objective

- 要构建什么：让 `GET /api/issues/{owner}/{repo}/{number}/pipeline` 与主资源
  `GET /api/issues/{owner}/{repo}/{number}` 对同一条 issue 使用**同一个**存在性解析助手
  （内部登记优先 → owner/repo/number 回落 VCS），外部托管仓既有 issue（内部 `issue_id=null`）
  的 `/pipeline` 返回 200 + 空 pipeline（`status="unknown"`、`segments=[]`）。
- 为什么：生产 Loki 该路径 404 达 107 次/小时（单客户端按 8 个编号轮询），而主资源同编号返回 200；
  子资源 404 与主资源 200 自相矛盾，调用方误判「issue 不存在」，轮询既不停也不降级。
- 用户：Agent（VOD/issue/coding 等）、grape CLI 使用方、直接调用平台 REST 的客户端。
- 成功标准：验收标准全部通过；已登记 issue（内部行存在）的 `/pipeline` 返回**结构不变**。

## Scope

### In Scope

1. `src/domains/runtime/routes/issues.py`：抽出统一解析助手 `_resolve_issue_presence()`
   （内部登记 → VCS 回落 → `exists`/`missing`/`unknown` 三态 + 来源标记）；
   `get_issue_detail` 与 `get_issue_pipeline` **都**改为调用它。
2. 编号归一单一入口 `_normalize_issue_number()`：去 `#` 前缀、纯数字去前导零、字符串 ident
   （gitee `IK*`）原样透传——与 #3719 的 `_num_from_issue_id` / `normalize_issue_ident`
   同口径（#3055 内核判据），两端口径一致。
3. `/pipeline` 空 pipeline 语义：解析到外部托管仓既有 issue → 200 + 空 pipeline，
   并附可判别的 `diagnostics`（`exists` / `has_pipeline_data` / `reason` / `source`）。
4. 错误语义可判别：仅在明确 `missing`（VCS 侧 404）时 404 `reason="issue_not_found"`；
   VCS 无法核实（无 token/网络）时 404 `reason="internal_sync_missing"`——与主资源同语义；
   404 body 增量补 `error_code`（保留 `code`/`message`，向后兼容）。
5. `/pipeline` 解析**只读**：不触发 `ensure_issue_task` 补建内部行（避免轮询写入放大），
   补建仍只在主资源 detail 路径发生（`backfill=True`）。
6. 测试：新增 `tests/runtime/test_issue_3891_pipeline_shared_resolution.py`，覆盖
   编号 42/119–125 两端一致、真不存在 404 可判别、已登记 issue 不回归、`/pipeline` 不写库；
   既有 `test_issues_api.py::TestIssuePipeline` 保持通过（补 patch 防真实外呼）。

### Out of Scope

- 外部托管仓 issue 的 `issue_id` 回填与事件同步入库（独立事项，避免与本端点语义修复耦合）。
- 客户端轮询策略改造（服务端语义修复后由客户端自行停止/降级）。
- 主资源既有返回字段结构的破坏性变更；`/pipeline` 对已登记 issue 的返回结构变更。

## Technical Approach

### 方案概述

「这条 issue 到底存不存在」只由一个助手回答，主资源与 `/pipeline` 共用同一答案与同一 404 语义；
「有没有 pipeline 数据」是另一个正交维度，用 `diagnostics.exists` / `diagnostics.has_pipeline_data`
表达。这样 200/404 不再取决于调用的是哪个端点。

### 实现路径

1. `_normalize_issue_number(number)`：`normalize_issue_ident()` 归一（内核唯一判据），
   纯数字再去前导零；非法/非数字形态原样透传（保持既有 IK* 与兜底路径行为）。
2. `_resolve_issue_presence(owner, repo, repo_keys, number, user, *, stage_map, status_map,
   group_map, backfill)`：ledger（stage/status/events 三表）命中 → `exists/ledger`；
   未命中按 `_vcs_issue_lookup()`（#672 通道）回落 → `exists/vcs` + VCS 原文；
   仍 miss → `_sync_missing_issue_row(..., backfill=)` 核实三态。
   `_sync_missing_issue_row` 增 `backfill` 形参：`False` 只核实体、不补建。
3. `get_issue_detail`：改用助手；VCS 原文命中 → 保持既有 `source="vcs"` 形状返回；
   `synced=True` → 重读四张映射（行为与改动前一致）；`missing`/`unknown` → `_detail_404`。
4. `get_issue_pipeline`：改用同一归一与助手（`backfill=False`）；`segments` 为空且内部未登记时：
   `exists` → 补 `diagnostics` 返回 200；否则 `_detail_404`（与 detail 同 reason）。
5. `_detail_404` 增量补 `error_code`（= reason），其余字段不变。

### 关键设计决策

| 决策 | 选项 | 选择 | 理由 |
|------|------|------|------|
| 解析口径 | 两端各自解析 / 共用助手 | 共用 `_resolve_issue_presence` | 从根源消除 200 与 404 矛盾 |
| 外部托管仓无 pipeline | 404 / 200 空 pipeline | 200 空 pipeline + `diagnostics` | 与主资源一致，客户端可停止轮询 |
| 空 pipeline 可判别字段 | 无 / `diagnostics{exists,has_pipeline_data,reason,source}` | `diagnostics`（仅回落路径新增） | 已登记 issue 结构不变，新增为增量 |
| 404 判别 | 仅 message / 增加 error_code | `reason` + `error_code` | 客户端可编程判别，`code`/`message` 兼容 |
| `/pipeline` 是否补建内部行 | 补建 / 只读 | 只读（`backfill=False`） | 轮询端点不得产生写入放大；回填另案 |
| 编号归一 | 各自 `isdigit`/`int()` / 内核判据 | `_normalize_issue_number`（内核判据） | 遵循 #3055/#3719 单一入口，防 IK* 掉队 |
